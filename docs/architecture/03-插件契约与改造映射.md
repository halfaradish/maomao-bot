# 03 · 插件契约与改造映射

面向写业务插件的人。本文定义重构后插件**需要知道的三件事**（清单怎么产生、可以声明什么、横切能力从哪来）、调度的归属，以及 38 个存量插件各自要做什么。

**已拍板：不做框架式 SDK。** 插件清单由节点内省 NoneBot 注册表自动导出；声明只用于补内省看不到的语义；横切关注点走全局中间件。**插件不 import 任何 diting 包也能被路由与灰度**——这是本方案与"自研 SDK"最根本的区别。

---

## 1. 为什么不走 SDK 路线

| 原设想（框架式 SDK） | 问题 | 现在怎么做 |
|---|---|---|
| `business_command()` 注册 matcher 的同时登记触发词 | 声明与行为是**两份真相**，必然漂移；而漂移的失败模式正好打在目标上：漏声明 → 新命令网关不认识 → 流量回 prod → 灰度期用户看到"功能不存在"，灰度验证失真 | **内省**：直接从 matcher 读触发词，不可能漂移（§3） |
| 38 个插件按契约重写 | 拿到插件级灰度的前置成本 = 重写 38 个正在线上跑的插件；且 38 次改生产代码 = 38 次回归风险 | 内省让 **~97% 的 matcher 零改动**参与插件级灰度（§7） |
| SDK 是唯一框架入口 | 第三方插件永远进不来；插件也搬不回普通 NoneBot | 标准 NoneBot 写法即可；第三方插件加提取器就能接（§3.5） |
| `ctx.perm` / `ctx.reply` / `ctx.log` | 每个插件都要记得调用，漏一处就是一个洞；插件作者还要学一套与官方文档对不上的 API | **全局中间件**：一次实现、全体生效、无法遗忘（§5） |
| `@job` 只声明处理器 | 需要新建一套任务派发链路，并把"任务能否发生"绑到中控可用性上 | 保留 APScheduler 原生写法，排程元数据登记在中控（§6） |

**代价说清楚**：内省依赖 NoneBot 内部结构（§3.4 给出完整依赖清单与治理方式），而框架式 SDK 不依赖。这是有意接受的取舍——换来"零重写"与"不可能漂移"。

## 2. 插件要提供什么（两类，都可选）

| 需求 | 来源 | 是否必须 |
|---|---|---|
| 触发词（命令 / 关键词 / 正则） | 内省自动导出 | **否**——用标准 matcher 就有 |
| 语义元数据（`canary_policy` / `critical` / `topics` / 权限点 / opaque 补声明 / 排程登记） | `PluginMetadata.extra["diting"]` | **否**——缺省值安全 |

```python
from nonebot.plugin import PluginMetadata

__plugin_meta__ = PluginMetadata(
    name="check_up", description="考勤", usage="...",
    extra={"diting": {
        "critical": False,
        "topics": ["check_up_notify"],           # 推送目标（改为 subscriptions，见 04 §4.8）
        "perm_points": ["check_up:notify"],
        "perm_groups": [
            {"name": "check_up_notify", "display_name": "考勤通知", "perms": ["check_up:notify"]},
        ],
        "jobs": {                                # 排程登记（§6.2）
            "send_check_on_work_msg": {"target": "topic:check_up_notify"},
        },
    }},
)
```

字段与缺省值：

| 字段 | 缺省 | 说明 |
|---|---|---|
| `routable` | 由内省推导（有 message 类触发 → true） | 仅在需要"有命令但不参与插件级灰度"时显式写 `false` |
| `canary_policy` | `allow` | 写 `deny` **加严**；中控的 deny 名单（`ctl_settings.canary_deny_plugins`）有最终否决权（01 §4.5） |
| `critical` | `false` | 加载失败是否导致节点 `not_ready` |
| `regex_routing` | `true` | 置 `false` 表示该插件的正则不参与路由（正则预算保护） |
| `topics` | `[]` | 推送/订阅主题，对应 `subscriptions.topic` |
| `perm_points` / `perm_groups` | `[]` | 声明式 provisioning 的输入（04 §4.7），由中控对账创建 |
| `triggers` | `[]` | **仅用于内省看不到的 matcher**（opaque 补声明），不写完整清单 |
| `jobs` | `{}` | 定时任务的排程登记（目标群来源），cron 与启停在中控侧（§6.2） |

**红线**：声明只能"补内省看不到的"或"把结论改严"（`routable=false`、`canary_policy=deny`）。**不允许把完整触发词清单抄进 `extra`**——那就是第二份真相，本方案的全部收益都建立在"只有一份"之上。

## 3. 插件清单（manifest）怎么产生：内省导出

### 3.1 提取算法

节点启动完成后（`on_startup` 末段）遍历：

1. `nonebot.plugin.get_loaded_plugins()` → 每个 `Plugin`（`name` / `metadata` / `matcher: set[type[Matcher]]`）
2. 每个 matcher 的 `matcher.rule.checkers`（`set[Dependent]`）→ 逐个看 `Dependent.call`
3. 按规则类型提取：

| 规则类 | 提取物 |
|---|---|
| `CommandRule` | `cmds`（命令元组，**aliases 一并在内**） |
| `KeywordsRule` | `keywords` |
| `RegexRule` | `regex` / `flags` |
| `StartswithRule` / `FullmatchRule` | `msg` / `msgs` |
| 其他（自定义 callable、`ToMeRule` 组合等） | 记入 **opaque** |

4. `matcher.type` 决定归类：message 类参与插件级灰度；notice / request / meta 归被动（随群路由，不参与插件级路由）
5. 定时任务：`nonebot_plugin_apscheduler.scheduler.get_jobs()` → `job.id` / `job.trigger`（§6）

**一个重要细节（已核实）**：`on_command("ban", rule=_is_word_boundary_command("ban"))` 这类"命令 + 自定义 rule"**照样能提取到命令**——`Rule.__and__` 会把 checkers 合并成一个扁平 `Rule`，`CommandRule` 对象仍在集合里（`group_ban/__init__.py:109` 是真实样本）。自定义 rule 只影响"这个插件还会不会真的命中"的精度，不影响"它声明了哪些命令"。

### 3.2 `routable` 的推导规则

- 有 ≥1 条 message 类触发 → `routable=true`
- 只有被动 matcher（notice / request / meta）→ `routable=false`
- `extra.diting.routable` 可覆盖（例：`cmd_list` 有 `help` 命令但希望固定由默认节点提供 → 显式 `false`）
- **混合插件**（既有命令又有被动监听，如 `auto_manage_group`）→ `routable=true`，只灰度它的命令；被动部分不属于插件级灰度的对象，随所在群的路由走

### 3.3 覆盖率报告（不让"看不清"静默存在）

manifest 带 `coverage` 段，中控在 WebUI 与告警里呈现：

- `matchers_total` / `derived`（已归类）/ `opaque[]`（含插件名、matcher 名、matcher 类型、原因）
- 处理原则：**被动插件的 opaque 不算问题**；**message 类 opaque 会告警**（可能含命令却无法参与插件级灰度）。处置二选一：在 `extra.diting.triggers` 补声明，或声明 `routable=false` 承认它不参与。
- P1.0 影子期就要产出第一份真实覆盖率报告（`00-总览.md §8` 的副产品之一）。

已知的 opaque 样本（全部核实过）：

| 插件 | matcher | 类型 | 处置 |
|---|---|---|---|
| `auto_manage_group` | `banned_word_detector` | message（自定义 rule） | 被动为主，声明 `routable=false` 或补 triggers |
| `logging_info` | `message_listen` | message（全量落库） | **废弃并删除**：写入职责上移到中控的事件流水（`01` §8.5）；顺序是先双写、再把消费者改指 `event_logs`、稳定后才删 |

### 3.4 依赖的 NoneBot 内部结构与治理

依赖清单（NoneBot 2.4.x 已核实）：

`Plugin.matcher` · `Matcher.rule: ClassVar[Rule]` · `Rule.checkers: set[Dependent]` · `Dependent.call` · `CommandRule.cmds` · `KeywordsRule.keywords` · `RegexRule.regex` · `PluginMetadata.extra` · `TrieRule`（网关分类器的语义参照，01 §4.4） · `nonebot_plugin_apscheduler.scheduler`

治理措施：

- 镜像 **pin** nonebot 版本；CI 增加 `tests/test_manifest_exporter.py`，在固定的 fixture 插件集上断言提取结果（命令/别名/关键词/正则逐条比对）；升级 nonebot **必须先过这个测试**。
- 节点启动写出本地 `data/manifest.json`，便于离线排障与人工核对。
- 真断裂时的退路：把受影响的插件改为 `extra.diting.triggers` 声明。**manifest schema 不变，架构不动**——产生方式是可替换的。

### 3.5 第三方插件

- 用标准 `on_command` / `on_keyword` / `on_regex` 的 → **自动可路由**，零适配。
- 自建 matcher 的（如 Alconna）→ 写一个提取器，或在 `extra.diting.triggers` 声明；两者都不做则落 `routable=false`（安全默认）。
- 第三方插件**不 import 任何 diting 包**是常态而非例外——这正是内省方案相对 SDK 方案的额外收益。

## 4. 网关怎么用这份清单

网关按 manifest 索引把消息归类到插件集合，用于插件级路由。契约与保真要求见 `01-路由与灰度.md §4`：分类器必须与 NoneBot 的判定**逐位一致**（复刻 `TrieRule.get_value` 语义），实现放在 `packages/contracts`，并配对拍测试与影子期回放对账。

## 5. 全局中间件：横切能力的唯一实现处

插件**不需要**为下列能力写任何代码；它们由节点运行时统一挂载：

| # | 中间件 | 挂载点 | 作用 | 语义 |
|---|---|---|---|---|
| 1 | 黑名单闸 | `run_preprocessor` | 对声明为只读的命令自动施加 `blacklist_guard` | fail-open（DB 抖动不封所有人），与现状一致 |
| 2 | trace 与结构化日志 | `run_preprocessor` + 发送钩子 | 注入 `node` / `version` / `plugin` / `trace_id`，发送动作带 trace | 插件继续用 `logger`，字段自动带上 |
| 3 | 慢 handler 计时 | `run_postprocessor` | handler 耗时超阈值（默认 500ms）记 warning 并计入 `node_slow_handler_total{plugin}` | 取代"人工检查清单"，见 `02 §1.3` |
| 4 | 兜底话术（degrade guard） | 最低优先级的 `on_message` | 命中"仅存在于另一节点的插件命令"时回 `degrade_reply_text` | 简单回滚的代价处理（01 §5.6），**不做成每个插件的义务** |
| 5 | 幂等键注入 | `run_preprocessor` | 由事件 id / `job_id:group_id:run_key` 派生，放进 `state` | 重试不重复扣费/不重复发消息 |
| 6 | 限流 | 网关令牌桶 + 节点兜底桶 | 键 `(群号, bot)`，语义与现状一致 | 主体在网关（§8），节点桶只防网关组件失效 |

**明确不做**：不封装 `Ctx`、不改发送方式（插件继续用 `matcher.finish` / `bot.send`，trace 由发送钩子注入）、不提供 `business_command` 之类的注册 API（它不增加任何能力，只会制造第二份真相）。

权限的**细粒度**校验仍由插件调用现有入口（`check_permission` / `permission_checker` / `blacklist_guard`，签名不变，见 `04 §5`）；不再有 SDK 包装层（`ctx.perm`），中间件只负责表中那些全局且粗粒度的部分。

**自己发送的消息**（`post_type=message_sent`）需要三项前置：NapCat 打开 `websocketClients[].reportSelfMessage`、适配器侧用 `Adapter.add_custom_model` 注册 `MessageSentEvent`（NoneBot 2.4.4 的 V11 适配器不认识这个 post_type）、网关把它归为**只记录、不路由**——详见 `01 §8.5`。事件落库由中控承担，节点不再写 `messages_event_logs`（`logging_info` 废弃）。

**发送出口的例外**：`group_send` 与 `shit_transport` 不走 WS，而是直连 NapCat 的 HTTP 控制 API（`QQ_CONTROL_PORT`，`01 §9.8`）——这两条调用没有 `trace_id`、不进决策日志、也不受网关限流约束；P3 评估改造。

## 6. 调度：排程元数据在中控，触发与执行在节点

**已拍板：不做"中控持有 cron 并派发"。** 三条理由：

1. 中控持有 cron 会把"定时推送能否发生"绑到中控可用性上，与 `02 §10` 的设计原则（中控挂不影响消息通路）冲突；
2. 中控派发还必须再配一条"中控不可达时节点兜底调度"的路径 + 一个切换判据，等于**维护两套调度实现**；
3. 节点本地方案同样能做到"被灰度的群由 dev 跑它的定时推送"（这正是细颗粒度灰度的目的），机制是"按路由算我的群 + 租约防双跑"。

### 6.1 归属划分

| 环节 | 归谁 |
|---|---|
| cron 与目标群的**登记**（数据） | 中控 `ctl_jobs`（可审计、WebUI 可改可启停） |
| **触发** | 节点本地 APScheduler（每个节点各自持有） |
| 目标群解析（topic → 群） | 节点（`subscriptions`，04 §4.8） |
| 按路由筛选"归我的群" | 节点（复用**与网关同一份**路由决策） |
| **防双跑** | Redis 租约（唯一的跨节点协调点） |
| **执行** | 节点（进程内，无 HTTP 跳转） |
| 结果与审计 | 节点上报中控 |

### 6.2 `ctl_jobs`：排程登记表

字段：`job_id`（**必须等于 APScheduler 的 job id**）、`plugin`、`schedule`（可空＝用代码里的默认）、`target`、`enabled`、`params`、`note`、`last_run_at`、`last_result`、`updated_by` / `updated_at`。

对账规则（节点启动时 + 排程变更广播时）：

| 情形 | 行为 |
|---|---|
| 表中有 & 节点有 | 用表里的 `schedule` / `target` / `enabled` 覆盖代码默认（**改 cron 不用发版**） |
| 表中有 & 节点无（插件未加载/已下线） | 告警，提示清理登记 |
| 节点有 & 表中无 | 按代码里的默认 schedule 运行，标记 `unregistered` 上报（WebUI 可见，提示登记）——**上线不会因漏登记而停摆** |
| `enabled=0` | 节点注销该 job（不触发） |

现存注册点已经全部带显式 id（如 `check_up.py:148` 的 `send_check_on_work_msg`、`like.py:344` 的 `job_subscribed_likes`、`plugin_usage_stats/scheduler.py:11` 的 `plugin_usage_stats_cleanup`、`sub_records/__init__.py:82` 的 `send_submissions_msg`），因此 `job_id` 的对应关系天然成立。

### 6.3 一次触发的完整过程

```
① 节点本地 APScheduler 到点触发（cron 或动态 run_date）
② 解析目标群：target=topic:<t> → subscriptions 里的群；
              groups:list:[...] → 写死群号；global → 无群概念
③ 按当前路由筛选：resolve_route(group_id, plugin) == 本节点 → 得到"我的群"
④ 逐个取租约：SET NX EX ctl:job_lease:{job_id}:{group_id}:{run_key}
   拿不到 → 跳过该群（另一节点正在执行或已经执行）
⑤ 执行 → 结果上报中控 POST /ctl/jobs/report
⑥ 幂等键 job_id:group_id:run_key（run_key = 日期或触发时刻整点）
```

- `resolve_route(group_id, plugin)` 与网关的 `resolve(event)` 是**同一份实现**（放在 `packages/contracts`），event 版是它的特例。这保证"定时推送的归属"与"消息的归属"永远一致——被灰度的群，其定时推送也跑 dev 的代码。
- 节点读的是与网关同一份规则快照 + override；Redis 不可用时用本地最后快照文件；两者都没有 → 跳过本次 + 告警（fail-closed）。

### 6.4 动态任务（`run_date`）

`contest_reminder`（赛前 1 小时）、`shadow_problem_view`（按记录时间）、`ack_manager` / `group_file_manager` / `todo_reminder` 的 `add_job` **保持进程内写法不变**：两个节点都会注册，租约决定谁执行；可选上报中控用于可视化。**不引入** `add_runtime_job` 之类的远程 API。

### 6.5 与"中控派发"方案的差异（为什么不选它）

| 维度 | 中控派发（否） | 本方案 |
|---|---|---|
| cron 与目标群数据 | `ctl_jobs` | `ctl_jobs`（相同） |
| 触发者 | 中控 APScheduler | 每个节点 |
| 执行体 | 节点（`POST /internal/job`） | 节点（进程内） |
| 关键路径 | **中控必须在线，否则任务不发生** | 节点在线即可；中控挂时任务照常 |
| 需新建 | 调度器 + 派发 + 重试 + **节点兜底调度 + 切换判据** | 2 个 helper + 一张登记表 |
| 改 cron | 改数据 | 改数据（相同） |
| 节点挂 | 该节点群跳过，需重试/重算 | 路由 override 把群交给另一节点，自动接管 |
| 本地开发 | 必须有假 dispatcher 或起中控 | `python bot.py` 即可跑 |

### 6.6 失败语义

| 故障 | 行为 |
|---|---|
| 中控不可达 | **任务照常触发**（节点用最后一次排程快照）；排程变更与结果上报不可用 |
| Redis 不可达 | 租约不可用 → 默认 **fail-closed**（跳过 + 告警 + 可手动补跑），`ctl_settings.job_lease_fail_mode` 可切 fail-open |
| 节点挂 | 其承载的群按路由 override 归另一节点，由该节点执行（与消息同源） |
| 两节点同时抢 | 租约保证只有一个执行；幂等键是第二道防线 |
| 租约残留（节点崩在任务中） | TTL 到期自动释放；任务需幂等（幂等键） |

### 6.7 要做 / 不做 / 废弃

- **要做**：`my_groups(target)`、`job_lease(...)`、`resolve_route(...)`、结果上报、`ctl_jobs` 表与 WebUI 页、"立即执行一次"按钮（`POST /internal/job`）。
- **不做**：中控侧调度器、`/internal/job` 的定时派发、节点兜底调度与切换判据（原设计里"中控不可达 5 分钟接管只读任务"整条删除）。
- **废弃**：用 env 开关错开调度的做法（`.env.dev` 的 `CHECK_UP_ENABLE=false`、`CLIST_SCHEDULE_JOB_ENABLE=false` 这类）。它与灰度目标直接冲突——灰度期间 dev 恰恰要跑它负责的群。

## 7. 38 个存量插件：需要做什么

就绪度分三档：

- **A 零改动**：内省即可参与插件级灰度；排程登记属数据层动作，不算改代码。
- **B 只需声明**：在 `extra.diting` 补 `routable` / `canary_policy` / `topics` / 权限点 / triggers。
- **C 需要改代码**：给的都是**能力或性能理由**，不再有"为了接 SDK"这一类。

| 插件 | 域 | 就绪 | 需要的动作 | 备注 |
|---|---|---|---|---|
| leaderboard | icpc | A | — | 建议作为首个灰度对象（只读、无状态） |
| clipboard | content | A | — | 依赖 Playwright 渲染（共用池，见 02 §1.3） |

## 10. 改造策略与删除纪律

| 阶段 | 安排 |
|---|---|
| P1 / P2 | **业务插件一行不动**。内省导出让插件级灰度在 P2 就能用；节点侧只加中间件与内部接口。此阶段两节点跑同一份代码，群级灰度不会造成行为差异 |
| P3a | 补齐声明（B 类）：`canary_policy` / `topics` / 权限点 / `routable=false`；登记 `ctl_jobs` |
| P3b | 排程与取群改造（C 类中的定时任务）：`get_bound_group_ids` → `my_groups`，接入租约；保留动态任务写法 |
| P3c | 真正的能力改造：`auto_manage_group` 拆分推理服务、`llm_scribe` 去同步阻塞、`siqi_auth` 删除、`shit_transport`/`vv` 的语义并入中央系统 |
| 验收 | 每批在 dev 节点跑 ≥3 天 + 灰度到测试群 ≥1 周，再上 prod |
| 删除 | 新实现上线 prod 且稳定 7 天后删除对应旧文件；`src/plugins/` 不做整体清空——**没有理由改造的插件保持原样**，直到它因为别的原因被重写 |

**不要做的事**：不要为了"以后好维护"提前重写能正常工作的插件。旧插件的 `matcher` 风格、`env_tag`、进程内缓存这些问题，由本方案在运行时统一处理（内省 + 中间件 + 快照），重写只在有具体能力/性能理由时才做。

## 12. 插件检查清单

每个插件**在被作为灰度对象之前**逐项确认：

- [ ] 在 WebUI 上确认 manifest 已上报，触发词与预期一致（内省结果）
- [ ] 覆盖率报告里该插件没有未处理的 message 类 opaque matcher（有则补 `triggers` 或声明 `routable=false`）
- [ ] 高危插件已进中控 deny 名单（或插件侧声明 `canary_policy=deny`）
- [ ] 有定时任务的：`ctl_jobs` 已登记（`job_id` 与 APScheduler id 一致），`target` 指向正确的 topic/群列表
- [ ] 有推送目标的：`topics` 已声明且 `subscriptions` 有对应群；`get_bound_group_ids` 已换为 `my_groups`
- [ ] 任务幂等：重跑同一 `job_id:group_id:run_key` 不产生重复副作用
- [ ] DB 读写不触碰 `env_tag`
- [ ] 长耗时操作（渲染、HTTP、LLM）有超时与失败兜底；**超过 50 ms 的 CPU 计算或同步 IO 必须 `asyncio.to_thread` 或外置服务**（02 §1.3）
- [ ] 日志能被中间件补上 `plugin` 字段；异常用 `logger.opt(exception=True)`
- [ ] 在 dev 节点通过 `/internal/selftest` 的 dry-run 断言
