### 1.1 compose 必改项（均对应当前缺失）

| 项 | 现状 | 新要求 |
|---|---|---|
| 重启策略 | 容器无 `restart:`（`docker-compose.yml:2-41`） | 所有服务 `restart: unless-stopped` |
| Redis 持久化 | 无卷、无 AOF（`:32-41`） | `appendonly yes` + 卷 + 密码移到环境变量 |
| Redis 密码 | 硬编码 `12345678` | 环境变量注入 |
| 健康检查 | 无 | 每个服务 `healthcheck` 打各自 `/healthz` |
| 节点源码挂载 | `./src:/app/src` + `./bot.py`（`:20-21`） | **删除**，节点跑确定版本的镜像 |
| 环境文件挂载 | `./.env.${ENVIRONMENT}`（`:24`） | 保留（配置仍需可改），但节点版本由镜像 tag 决定；改为每服务一份、显式指定，分层与命名见 §2.0 |
| 容器日志上限 | 无 `logging:` 段，json-file 默认不轮转，DEBUG 下无限增长 | 每服务 `logging: {driver: json-file, options: {max-size: "50m", max-file: "5"}}`；运行日志的正本在 `logs/<service>/`（`01 §8.4`） |
| 日志卷挂载 | `./logs:/app/logs`（`:16`），多服务会共用同一目录 | **每服务独立卷**：`./logs/<service>:/app/logs`，与服务名一一对应（`01 §8.4`） |

### 1.2 节点不再使用热重载

现状：`bot.py:85-173` 的 watchfiles watcher + `data/deploy/pull.lock` 哨兵，让宿主机代码变更后自动重启 worker。
新架构下必须砍掉，理由是**灰度要求"这个节点跑的到底是哪个版本"必须确定**——热重载会让镜像 tag 与实际运行代码脱钩，回滚时无法判断回滚到了什么。

- `HOT_RELOAD` 仅在 `ENVIRONMENT=local`（本地开发）保留。
- 节点版本 = 镜像 tag = `diting-node:<git-sha>`；运行中的 sha 通过心跳上报，WebUI 上可见。

### 1.3 语言选型与阻塞约束

| 层 | 语言 | 理由 | 要点 |
|---|---|---|---|
| gateway | Python 3.11+ asyncio（FastAPI/uvicorn 或纯 websockets） | 与中控共享规则引擎与 `packages/contracts`；单进程持有 NapCat 与各节点的连接 | `orjson` 解析、`uvloop`、前缀匹配优先于正则、正则总量预算（≤200 条）并跳过超长文本；**单 worker** |
| control | Python + FastAPI | CRUD + 调度 + WebUI 宿主，复用决策代码 | 调度显式指定 `Asia/Shanghai`、单实例 |
| node | Python + NoneBot（不换） | 38 个插件与 OneBot 适配器生态都在这 | 见下"阻塞约束" |
| 重型计算 | 同语言、独立进程或独立服务；推理用 ONNX Runtime | 要的是隔离与并行度，不是换语言 | BERT 违禁词判定由 torch 换 ONNX Runtime 通常有一个数量级提速，并能把 torch（数 GB）从节点镜像移出 |
| webui | TypeScript + React（不变） | 现状 | —— |

**为什么不给网关换语言**（估算量级，非实测）：

| 环节 | 量级 |
|---|---|
| QQ ↔ NapCat 往返 | 数十 ~ 数百 ms（不可控） |
| 网关单事件处理（解析几 KB JSON + 前缀比较 + 少量正则） | Python 0.2 ~ 0.5 ms；Go 0.05 ~ 0.1 ms |
| 节点侧 DB 查询 / 图片渲染 / LLM 调用 | 1 ~ 20 ms / 0.3 ~ 2 s / 秒级 |

省下约 0.3 ms，在几百毫秒到几秒的端到端耗时里既不可测也不可感。两个结构性理由更硬：

1. **单实现原则**：规则解析算法要被三处使用且必须逐位一致——网关执行路由、中控的生效预览（`01-路由与灰度.md` §7）、`/env why` 决策解释。跨语言意味着同一套层级排序、冲突裁决、override 叠加写两遍，一旦漂移就是"预览说走 dev、线上走 prod"。
2. **网关必须单进程**：它持有 NapCat 与各节点的 WS 连接和 `echo` 映射，因此用不上多核——"换编译型语言吃满多核"在这里不成立。Python 单进程 asyncio 做纯路由可处理几千事件/秒，而单账号群机器人的峰值通常在个位数到几十事件/秒，余量两三个数量级。

**阻塞约束（节点侧，硬要求）**：NoneBot 是单事件循环，任何超过约 50 ms 的 CPU 计算或同步 IO 都会拖住整个节点，进而导致心跳丢失、被判为异常、触发一次不必要的自动回滚（见 `01-路由与灰度.md` §5.2）。存量代码里已知的三处，在 P3 按需改造时必须处理（它们同时也是 `node_slow_handler_total` 的主要来源）：

| 位置 | 问题 | 处理 |
|---|---|---|
| `src/plugins/auto_manage_group/predict.py` | torch + transformers 在事件路径上跑 BERT 推理 | 改 ONNX Runtime；退一步至少 `asyncio.to_thread` + 固定线程池；理想是拆成独立推理服务 |
| `src/plugins/llm_scribe/src/infrastructure/persistence/db_connection.py` | 同步 `pymysql` 在异步循环里硬阻塞 | `asyncio.to_thread` 或改 `asyncmy` |
| `src/common/rendering/`（Playwright 池） | 浏览器操作耗时长、CPU 占用高 | 并发上限 + 超时；不与业务抢事件循环的 CPU 时间 |

**收益不止于延迟**：把 torch 从节点镜像移出后，镜像体积与构建时间会显著下降（现状冷构建约 28 分钟），日常发布更快——这比任何语言选择带来的收益都大。

**运行时治理（替代"人工检查清单"）**：节点运行时挂一个 `run_postprocessor` 计时中间件，handler 耗时超过 `ctl_settings.slow_handler_warn_ms`（默认 500 ms）即记 warning 并计入 `node_slow_handler_total{plugin}`（`01 §8.1`），配合心跳的 `loop_lag_ms_p95` 一起看。**不要让"哪段代码会阻塞"靠 review 记忆**——让它自己冒出来。

**监控补充**：节点心跳上报 `loop_lag_ms_p95`，中控连续 3 次收到 > 500 ms 即把节点标为 `suspect` 并告警，**不触发自动回滚**（阻塞是节点自身问题）。判定与指标见 `01-路由与灰度.md` §5.2、§8.1。

## 2. 配置与环境变量

### 2.0 配置分层与键归属（先读这一节）

#### 四层配置，各有各的介质

| 层 | 内容 | 介质 | 改一次的代价 | 谁维护 |
|---|---|---|---|---|
| A 编排 | 服务清单、端口、镜像 tag、卷、网络、重启与健康检查 | `deploy/compose/*.yml` + 键清单（**进 git**） | 重新部署 | 开发者 |
| B 启动与密钥 | DB / Redis 地址与口令、各 token、`NODE_NAME`、`LOG_FILE_PATH` | 每服务一份 `<service>.env`（**不进 git**，宿主 `0600`） | 重启该服务 | 运维 |
| C 业务配置 | 路由规则、override、限额、告警群、功能开关 | 中控库 `ctl_*` + Redis 快照，WebUI / `/env` 编辑 | 秒级热生效，不重启 | 值班与管理员 |
| D 插件参数 | 阈值、白名单、模板开关这类插件自己的旋钮 | 同上，`ctl_settings` 按插件命名空间；P3 从 B 层迁入 | 秒级热生效 | 值班 |

**判定规则只有一条：改完要不要重启进程？要 → B 层（env）；不要 → C/D 层（中控库）。**
按这条规则回看今天：`env.template` 的 114 个键里绝大多数是 C/D 类（`CHECK_UP_ENABLE`、`LIKE_AUTO_SEND_LIKE`、`AUTO_MANAGE_*`……），它们的每一次调整都要重启进程、两个环境各改一遍、且没有审计——这就是"配置"在本项目变成负担的原因。**运行期可变的业务参数不要放进 env。**

#### 单一来源 + 每服务投影

人工只维护**每环境一份** `deploy/env/<env>.env`，它是密钥与跨服务不变量（Redis 口令、节点 token 这类必须处处一致的值）的唯一来源——拆散就必然漂移。部署脚本按**键归属**把它渲染成每服务一份，服务只拿到自己需要的键：

```
deploy/env/
  dev.env                # 人工维护：密钥 + 跨服务不变量（不进 git）
  prod.env
  dev/
    gateway.env          # 生成物：只含网关需要的键
    control.env
    node-dev.env
  prod/
    gateway.env
    control.env
    node-prod.env
```

**为什么不共用一份**：服务边界要落在进程里，而不是只写在文档里——共用一份文件时，边界全靠自觉，而"网关能连业务库"这种事一旦成立，迟早有人从网关直接查库。
**为什么不各写各的**：不变量分散到多份文件后，漂移无法被发现。今天的实际漂移见 §2.4。

#### 键归属表

| 键（现名） | gateway | control | node-* | 说明 |
|---|---|---|---|---|
| `ONEBOT_ACCESS_TOKEN` | 拿 | — | — | NapCat ↔ 网关之间的凭证，只有网关校验它 |
| `NODE_TOKENS`（每节点一项） | 拿 | — | — | 节点连接时校验；节点侧用的是自己那一个（`ONEBOT_V11_ACCESS_TOKEN`） |
| `NODE_NAME` / `NODE_TOKEN` | — | — | 各自一份 | 节点身份与上报凭证，两个节点必须不同值 |
| `CTL_DB_URL` | — | 拿 | — | 控制面库，仅中控 |
| `BIZ_DB_URL` / `BOT_DB_*` | **不拿** | 拿 | 拿 | 中控是权限与事件流水的唯一写入者；节点读写业务表。**网关不持有业务库凭证**（`00` §4、`01` §8.5） |
| `CONTROL_URL` | 拿 | — | 拿 | 网关拉规则与运维名单快照；节点发心跳 |
| `OPS_ADMINS*` / `RATE_LIMIT_*` / `EVENT_LOG_SINK` | 拿 | — | — | 控制命令鉴权、限流、事件流水上报都在网关本地 |
| `WEBUI_JWT_SECRET` | — | 拿 | — | 缺失等于关掉 WebUI 登录（`src/common/jwt_utils.py:19` 会退化成随机密钥） |
| `LOG_FILE_PATH` | 拿 | 拿 | 拿（每实例不同值） | `01` §8.4 |
| 业务类（`ICPC_*`、邮件、图片目录等） | — | — | 拿 | 网关不碰业务 |

投影与校验都靠**每服务一个 pydantic 模型**（落在 `packages/common/config/`）：模型即归属表——渲染脚本只写模型声明的键，服务启动时按它校验，**缺键、类型错、键名拼错一律启动失败**（未声明的键出现在该服务的 env 文件里同样报错；进程环境里的无关变量忽略）。启动打印的"配置指纹"只含键名与非密值的哈希，不含任何明文值。

> **注意 `DRIVER` 是新增能力**：今天全环境都是 reverse-WS（`DRIVER=~fastapi`，仓库内没有任何 `ONEBOT_V11_WS_URLS`），**节点从不主动外连**。forward-WS 是本次新增的，P1.0 必须先用临时节点验证"与 reverse 路由并存时的行为"和"连接期 API 时序"（`00-总览.md` §8 第 1、3 项），再动线上节点。
>
> **废弃**：用 env 开关错开调度的做法（`.env.dev` 的 `CHECK_UP_ENABLE=false`、`CLIST_SCHEDULE_JOB_ENABLE=false` 这类）。它与灰度目标直接冲突——灰度期间 dev 恰恰要跑它负责的群（`03 §6.7`）。灰度上线后逐个清理这些开关，由 `ctl_jobs.enabled` 取代。
>
> 注意 `COMMAND_START`：新架构不再需要 `["dev-"]` 这类前缀隔离（路由解决了这件事）。建议两端统一为 `["/", ""]`，避免留下"两套命令语义"的历史包袱；**两端的 `command_start` / `command_sep` 必须与 manifest 上报值一致**，否则网关分类器与节点判定会漂移（`01 §4.4`）。

### 2.4 多环境共存、密钥纪律与现状盘点

#### 同一目录下跑多环境：三条命名空间 + 一条护栏

今天不冲突，只是因为**两份 clone = 两个目录**（`00` §1）；单仓之后同目录跑 dev 与 prod，冲突点有三个，全部用显式命名空间解决，不靠人记得：

| 冲突点 | 做法 | 反面（今天已有的实例） |
|---|---|---|
| 读哪份 env | 一律显式：`docker compose -p diting-<env> --env-file deploy/env/<env>/<service>.env -f deploy/compose/<service>.yml`；节点由容器内**那一份文件的名字**决定（NoneBot 默认读 `.env`），首选改成 `bot.py` 的 `init(_env_file=...)` 显式指定，两条路见下方注 | 隐式发现：`src/plugins/image_collection/config.py:10` 硬编码 `env_file=".env"`，读到的永远是那份 4 键基础文件；docker compose 自动加载 `./.env` 同理 |
| 容器 / 网络 / 卷 | `COMPOSE_PROJECT_NAME=diting-<env>`、`container_name=diting-<service>-<env>`，网络与卷名都带 env 前缀 | 现状靠脚本变量 `SUFFIX`（`scripts/docker-manager.sh:57`）拼容器名，网络 / 卷 / 日志路径没有覆盖 |
| 宿主路径与端口 | `./logs/<env>/<service>/`、`./data/<env>/...`；端口成对分配（gateway 8100 / 8110，control 8101 / 8111，node 6090 / 6095） | `./logs:/app/logs` 全环境共用（`docker-compose.yml:16`）；端口约定只写在 `docker-manager.sh:307-308` 的提示文本里 |
| **身份护栏** | 每个服务启动即上报 `{service, env, node_name, env_file, config_fingerprint}`；中控发现同一个 `NODE_NAME` 出现两个不同指纹 → critical 告警 | 无。同机双环境最可能出的错是"dev 读了 prod 的 env"，症状是"改 dev 影响了生产"，极难排查 |

把这件事做成结构性的而不是纪律性的：**宿主与仓库里不放名为 `.env` 的文件、也不放 `.env.<env>`**（仅 local 开发例外）。隐式发现的可怕之处不是读错，而是读错了还能跑起来。

> **不要把希望寄托在 `ENV_FILE` 上**（勘误）：NoneBot 的 `env_file` 是**类属性**（默认 `.env`）、`Env.environment` 默认 `prod`，两者都只能由代码给（`nonebot/config.py:319-325`、`:389-398`，`nonebot/__init__.py:298-310`），**没有 `ENV_FILE` 这个环境变量**——写进去只会变成一个被忽略的额外配置项。所以"节点读到哪份"只有两条路：
> ① **首选，改 `bot.py` 一行**：`init(_env_file=os.getenv("DITING_ENV_FILE", ".env"))`，容器内的文件名与宿主渲染物同名（`/app/config/node-<node>.env`），隐式发现彻底消失；
> ② **不改代码**：容器内固定放一份 `/app/.env`（由宿主渲染物只读挂载；容器是隔离沙盒，宿主上仍不许有共享 `.env`），此时**必须不设 `ENVIRONMENT`、容器内不放 `.env.<env>`**，否则 NoneBot 会把 `.env.<environment>` 叠加上来（`nonebot/__init__.py:300` 的 `_env_file = _env_file or f".env.{env.environment}"`）。
> 两条路都要顺手**删掉 `ENVIRONMENT` 这个键**——它正是"运行期算出该读哪份文件"的间接层。

#### 密钥纪律

| 项 | 要求 |
|---|---|
| 进 git | A 层（compose 与键清单）进 git；B 层（值）不进——落地规则见下一节 |
| 进镜像 | **当前没有护栏**：`Dockerfile:75` 是 `COPY . .`，而 `.dockerignore` 未排除 `.env*` → 在宿主构建会把含密钥的 env 打进镜像层。需补一行排除 |
| 权限 | 宿主上 `0600`、目录 `0700`；容器内只读挂载（现状 `docker-compose.yml:24` 已是 `:ro`） |
| 硬编码 | `docker-compose.yml:37` 的 redis `--requirepass 12345678`（已进 git）与 `src/config/local_config.py:87` 的默认 `'123456'`（让"忘配"变成"用弱口令跑起来"）两处要清 |
| 轮换 | 因为每服务投影，轮换点唯一：改 `deploy/env/<env>.env` → 重渲染 → 滚动重启；轮换记录进 `ctl_audit` |
| 不引入 Vault | 单机单账号机器人，无合规要求，而代价是多一个"必须活着否则机器人起不来"的组件。升级路径：需要时用 systemd `LoadCredential=` 或 docker secrets 把值换成文件挂载，**读取接口不变**（仍是"读一个值"），现在不必提前付这笔钱 |

#### B 层的值放主机本地仓（无远端）

B 层的值是"人维护、机器读"，它需要版本、diff 与回滚，但不需要远端。落地形态是**主机上的一个无远端 git 仓库**：`deploy/env/` 自己是一个仓，值只存在于主机与离线副本里；主仓只跟踪渲染脚本与键归属模型（§2.0）。往远端推（包括自建私密 GitLab）的收益是分发与评审，**不是保密**——代价是秘密永久进入历史与每个 clone。出现第二台运行主机、或第二个需要独立改配置的人时再谈，别为了"看起来正规"提前付这笔钱。

**忽略规则必须显式写，现成的那条挡不住。** 主仓 `.gitignore:146` 的 `.env*` 继续保留（它保护仓库根那份基础 `.env`），但它要求文件名**以** `.env` 开头，而 `dev.env` / `gateway.env` 是 `.env` **结尾**——不显式忽略，`git add -A` 会把它们提交到 GitHub / Gitee 镜像上。

| 在哪 | 忽略什么 | 不做的后果 |
|---|---|---|
| 主仓 `.gitignore` | `/deploy/env/`（前导斜杠锚定仓库根，不误伤别处同名路径） | 内含 `.git` 的目录被记成 gitlink：主仓只存一个它自己远端没有的 commit 指针，别人 clone 下来是空目录；或明文直接进公开镜像 |
| `.dockerignore` | `deploy/env/` | `Dockerfile:75` 是 `COPY . .`：本地仓整份（含 `.git` 历史）进构建上下文，镜像层与构建缓存里就是明文 |
| 本地仓自己的 `.gitignore` | 渲染产物（`dev/`、`prod/`）与任何解密密钥 | 每服务投影出的明文又进一次版本管理，等于白折腾 |

**顺序是先加忽略、再 `git init`。** 反过来会在主仓留下 `warning: adding embedded git repository` 与一个取不回的指针：

```bash
echo "/deploy/env/" >> .gitignore        # 1) 先在主仓忽略
mkdir -p deploy/env && cd deploy/env     # 2) 再在主机上建本地仓
git init
git config user.name diting-ops && git config user.email ops@localhost   # 不配这两项，提交会直接失败
printf 'dev/\nprod/\n' > .gitignore      # 渲染产物不进任何仓库
git add .gitignore dev.env prod.env && git commit -m "init env source"
```

也不要用 submodule 代替：没有远端就没人取得到那个 SHA，对别人只是空目录，效果与忽略相同，只多一层概念。

**三条护栏**：

| 护栏 | 做法 | 防的是什么 |
|---|---|---|
| 禁止推送 | 本地仓放一个永远失败的 `pre-push` 钩子（`echo 禁止推送 >&2; exit 1`） | 哪天顺手 `git remote add` 再 push，秘密就离开主机了 |
| 不跑 `git clean -fdx` | 写进 runbook 明令禁止 | `-x` 的本意就是连忽略的文件一起删：一条命令清掉本地仓与全部历史（今天的 `.env.*` 同样有这个风险，只是丢的是单个文件） |
| 离线副本 | 源文件（**不含 `.git`**）放密码管理器或加密介质 | 无远端 = 无异地备份，主机全丢即凭证全丢；不带 `.git` 是因为历史里可能留着已轮换的旧口令 |

**行尾必须是 LF**：给本地仓加一条 `*.env text eol=lf`。在 Windows 上编辑极易带 CRLF，而 systemd 的 `EnvironmentFile=` 会把 `\r` 当成值的一部分——口令或 token 会"看起来一模一样却校验失败"，`cat` 出来肉眼分辨不了。

**放哪**：默认就放在工作树内的 `deploy/env/`。若想要更硬的结构保证（不怕误 `add`、误 `clean`、误打包），把它挪到工作树外（如 `/srv/diting/env`），主仓只留一个被跟踪的 README 说明位置，渲染脚本的源路径改成参数——代价是多一条约定要维护。

> 说明性文件不要放在被忽略的目录里：`deploy/env/` 整个被忽略，写在那里的 README 新克隆的人看不到。渲染脚本留在主仓（如 `deploy/render-env.py`），本地仓的说明写在它自己的 README 里。

## 3. NapCat 侧的唯一改动

NapCat 只改 QQ 侧的 WebSocket 客户端列表，其余（token、协议、端口）不变。
**勘误**：这个版本的 NapCat 用的是 `network.websocketClients` **数组**（每个元素一个独立目标），不是某些实现里的 `reverseWSUrls`（见 NapCat 源码 `packages/napcat-onebot/config/config.ts:74-79`）。

```jsonc
// onebot11_<qq>.json
{
  "network": {
    "websocketClients": [
      {
        "name": "gateway",
        "enable": true,
        "url": "ws://<host>:8100/onebot/v11/ws",
        "token": "<ONEBOT_ACCESS_TOKEN>",
        "messagePostFormat": "array",
        "reportSelfMessage": false,
        "reconnectInterval": 5000,
        "heartInterval": 30000
      }
    ]
  }
}
```

| 阶段 | `websocketClients` 内容 |
|---|---|
| P1.0 影子期 | **两项**：现有节点 + 网关（网关 observe-only，只记录不投递） |
| P1.1 接管入口 | **只留网关那一项**（旧节点那项必须删除） |

`messagePostFormat: "array"` 是 NoneBot 期望的消息段格式；`token` 与网关的 `ONEBOT_ACCESS_TOKEN` 一致。

> **接管时必须删干净旧节点那一项**：留着两项会让每个事件被投递两次（网关一份、旧节点一份），这正是排障手册里"一条消息被处理两次"的成因。

## 4. 落地路径（P1.0 影子期 → P1.1 接管 → P1.2 群级切换 → P1.3 自动回滚）

四个子阶段，每阶段都有明确产出、验收标准与回退点。**P1 全程不碰业务插件**——群级路由不需要 manifest，这是它能快速落地的根本原因；插件级路由留到 P2，靠节点内省导出清单实现（`03 §3`），**不需要插件改造**。

### 4.1 P1.0 影子期（零风险，先做）

已核实 NapCat 支持多路 `websocketClients`，因此可以并联观察、完全不动线上：

1. **建库**：创建 `diting_ctl`（同 MySQL 实例），由中控自带迁移建表（`ctl_nodes` 等，见 01 §2）。
2. **起网关与中控**，网关以 **observe-only** 启动：接收事件、算路由决策、写决策日志，**不投递、不发消息**。
3. **在 NapCat 里加第二个 client** 指向网关（§3 表格第一行）。此时线上行为完全不变。
4. **跑 2~3 天**，同时验证 `00-总览.md` §8 的 9 项（含配置隔离与指纹，§2.0/§2.4），积累真实流量的决策日志，并用 `messages_event_logs` 回放对账。
5. **产出**：协议验证结论 + 决策日志样本 + 临时节点的 manifest 真实样本。

**退出条件**：9 项全过且无异常。**回退**：删掉 NapCat 里那一项即可，线上无感。

### 4.2 P1.1 接管入口（整条路径上唯一的风险点）

6. **改造节点**：加全局中间件（`03 §5`）与内省导出器（manifest 上报）、加 `/internal/*` 与 `/healthz`、注册 `NODE_NAME`、driver 改 `~fastapi+~websocket`；管理面暂留（P2 再迁）。
7. **切网络**：先让节点以 forward-WS 连上网关并确认可达 → 再把 NapCat 的 clients **换成只剩网关**（§3 表格第二行）→ 观察 30 分钟。
8. **验默认路由**：确认 `default_node=prod`、无规则时全部流量落在 prod；用 `/env why` 抽查 3 条真实消息的决策。
9. **观察 24 小时**：`gateway_events_total{node="prod"}` 与业务量吻合，`dropped` / `degraded` 均为 0。

**回退**：把 NapCat 的 clients 改回指向旧节点（节点侧保留 reverse 路由一个版本周期作为退路）。

### 4.3 P1.2 群级手动切换（里程碑 M1）

10. 中控上线群级规则 + `/env` 控制命令 + 审计（规则模型见 01 §2，命令清单见 01 §6），WebUI 先出只读总览页。
11. **验收 M1**：一条命令把测试群切到 dev、再切回来，**全程不重启任何进程**、秒级生效、操作有审计记录。

**到这里原始需求已闭环**（命令/WebUI 手动切换 + 方便回滚）。

### 4.4 P1.3 健康与最小自动回滚（里程碑 M2）

12. 节点心跳（含 `loop_lag_ms_p95`）+ 中控状态机 + override（只对 `target=dev` 的规则生效）+ 防抖 + 告警到 `825332714`。
13. **验收 M2**：kill 掉 dev 节点容器 → 30 秒内 dev 的群回到 prod，**prod 承载的流量零变化**，告警到达管理群；重启后 `/env resume dev` 恢复。

> **前置条件**：P1.3 之前必须完成"把阻塞移出事件循环"（§1.3）。否则节点被重计算阻塞 → 心跳丢失 → 触发**误回滚**，你会把"节点自己堵住"误判成"新功能有 bug"。

### 4.5 P2 / P3 与收尾（新架构验证通过前后）

**P2（里程碑 M1.5）插件级灰度**：节点内省导出 manifest 后，`scope=plugin` / `scope=group_plugin` 规则即可生效——**不需要任何插件改造**（`03 §3`、`03 §7`）。
验收：把一个只读插件（建议 `leaderboard`）在测试群灰度到 dev，`/env why --group <群> --text "<该插件的命令>"` 显示走 dev；同时确认未被灰度的插件流量不落到 dev（分类器保真，`01 §4.4`）。

**P3 按就绪度推进**（`03 §7`）：先补声明（B 类）与排程改造（C 类里的定时任务），真正的重写只在有具体能力或性能理由时做——不再有"为了接 SDK 而重写"这一类工作。

14. 逐步扩灰度，最终把 prod 也切到新架构；确认稳定后按已拍板前提**废弃旧的两份 clone 与旧容器**，`dev-` 前缀配置一并删除。
15. 更新 `docs/diting-deploy.md` 指向本文，旧文档标记为历史。

> 已拍板前提：**旧的两份 clone（含 NapCat 分流配置）在新架构验证通过之前不动**。

## 5. 发布与回滚 runbook

### 5.0 部署窗口（计划内重启）

发布要重启容器，而重启期间"没有心跳"与"节点挂了"在传输层无法区分。**缺了这层声明，每次发 prod 都会触发一次全量接管**（`01 §5.4` 已把默认节点故障改成自动接管），所以它不是可选优化。

- **谁开**：真正在执行部署的那一方——P1 阶段是宿主执行器（`diting-agent.sh` 本来就知道自己在部署，调 `POST /ctl/deploy/begin` / `/end`）；P2 移交中控编排后由中控自己开。机制不变，只换调用者。
- **窗口内**：该节点不做健康判定升级（不进 `suspect` / `unhealthy`）、不触发自动回滚与接管、告警降级为"计划内部署"通知；窗口内的状态变化**不计入 `locked` 的抖动统计**（否则连发两次部署就可能把节点锁成 `locked` 等人工 resume）。
- **流量**：窗口开启时自动把该节点的引流规则改投默认节点，窗口结束且节点 `ready` 后自动恢复（复用 override 机制，`kind=deploy`，带 TTL）。这样"部署"与"灰度不中断"不再矛盾——中断是自动的、有界的。
- **超时兜底是这层唯一的风险**：TTL 默认 5 分钟（发布只拉镜像，不构建）；窗口内持续探执行器进度，进度停滞即提前关窗；**TTL 到期或关窗后仍无心跳 → 立即按 `unhealthy` 处理并告警**。否则"部署卡死"会变成"永久静音"。
- **两条边界**：手工 `docker restart` / `stop` **不在**窗口内，仍按故障处理（窗口只对发起方声明的部署生效，这样"有人上服务器乱动"依然会被发现）；窗口内新版本起来但自检不过（`not_ready`）→ 记 `ctl_deployments` 失败并明确报"部署失败"、建议动作是回退镜像 tag，**不写 incident、不计入自动回滚统计**（修复动作与"节点自己挂了"完全不同，不该混成一类）。

### 5.1 日常发布（不改行为，只上代码）

1. push 分支 → CI 构建 `diting-node:<sha>`（见 §9）。
2. 部署到 **dev 节点**（零流量或仅灰度流量）：触发宿主执行器 → 拉镜像 → 起容器。
3. 观察自检：`/env node` 应显示 `ready`，插件加载失败列表为空，`version`/`git_sha` 与预期一致。
4. 未开灰度 = 对用户无影响，可以停在这里等人工验证。

### 5.2 灰度

```
/env route dev --plugin leaderboard --groups 123456 --note "积分榜改版验证"
```
- 立刻生效（秒级），`/env why --group 123456 --text "过题积分榜"` 应显示走 dev。
- 观察窗口自定（建议 ≥30 分钟），关注 `gateway_degrade_reply_total` 与节点错误日志。

### 5.3 回滚

| 情形 | 操作 | 效果 |
|---|---|---|
| 主动回滚（功能有问题） | `/env rollback --rule <id>` 或 WebUI 一键 | 该规则删除，流量回默认节点 |
| 回滚最近一次全部改动 | `/env rollback --last` | 规则表回退到上一版本 |
| 冻结整节点 | `/env freeze dev --reason "..."` | dev 的所有规则改投 prod，规则本身保留 |
| 节点异常 | 无需操作 | 自动 override（01 §5.3），告警群收到通知 |
| 恢复 | `/env resume dev` | 清除 override |

### 5.4 上线 prod

1. dev 验证通过 → 合并 `master` → CI 构建 → 触发 prod 部署。
2. prod 部署走**部署窗口**（§5.0）：窗口内不计故障、不触发接管，该节点的引流规则自动改投、结束自动恢复。窗口内它承载的流量短暂不可用（现状同等）；要求零窗口时启用第三节点 `standby-1`：先把默认节点临时指向 standby，部署 prod，验证后再指回（规则模型天然支持，无需改代码）。
3. 上线 prod 后，删除指向 dev 的灰度规则——此时新功能已两端具备，删除只是恢复默认路由。

### 5.5 紧急处置矩阵

| 症状 | 第一动作 | 后续 |
|---|---|---|
| dev 节点发疯（刷屏、报错风暴） | `/env freeze dev --reason "..."` | 抓 dev 日志定位，修好再 `/env resume` |
| prod 节点挂了（默认节点） | 无需操作：链路断开 >10s 或心跳 `unhealthy`（30s）即**自动全量接管到 dev**，告警含 `git_sha` 差异与拒绝清单（`01 §5.4`） | 查 prod 容器；恢复后自动回切（稳定 60s 且未 `locked`）；它若反复异常会被标 `locked` 并保持接管，转人工。接管期间高危插件按名单拒绝，用户看到"故障恢复期间暂停"而不是被未验证代码执行 |
| 计划内重启被误当故障（或部署卡住） | 看 `/env` 与告警里是否带"计划内部署"标记；核对 `ctl_deployments` 的 deploying 阶段与窗口 TTL | 未标计划的按故障处理（这是有意的：手工 `docker restart` 不该有豁免）；窗口到期仍无心跳即按 `unhealthy` 走接管流程 |
| NapCat 挂了 | 与本期架构无关，按现有手册 | 恢复后网关自动重连；断链超过去抖窗口时节点连接会被主动断开并在恢复后重连，自愈钩子重跑一次（`01 §9.4`） |
| 网关挂了 | 全部消息不通（单点） | 见 §10 单点风险；重启即从 Redis/快照恢复规则 |
| 中控挂了 | 消息仍正常（网关有快照） | 规则改不了、心跳不记录；重启中控即可 |

## 6. 共用业务库的纪律（必须执行，否则灰度会炸）

两个节点共用一份库、跑不同代码版本，**schema 是唯一的硬耦合点**。

### 6.1 迁移三段式

| 阶段 | 允许 | 何时 |
|---|---|---|
| expand | 加表、加列（可空或带默认）、加索引 | 随时，包括灰度窗口内 |
| migrate | 数据回填、双写 | 回填脚本必须幂等、可重入 |
| contract | 删列、改类型、重命名、加非空约束 | **仅当两端都已是新代码**（prod 也升级完） |

**灰度窗口内只允许 expand**。违反这条会造成"dev 改了 schema，prod 的旧代码读到就崩"。

### 6.2 迁移的唯一入口

- 工具：Alembic（替代现在的 `Base.metadata.create_all`，`src/common/database.py:79-87`）。
- 执行者：中控的 migration job（`POST /ctl/deploy/migrate`），用 MySQL `GET_LOCK('diting_migrate')` 或 Redis 锁保证单执行。
- 记录：迁移前后写 `ctl_deployments`（revision、执行人、耗时、结果）与审计。
- 拦阻：迁移前自动备份，失败即中止（§7）。

### 6.3 节点侧 schema 校验

节点启动时把自己的 `schema_revision` 与允许区间比对（由镜像内置 `EXPECTED_SCHEMA_MIN/MAX`，随发布更新）：

- 在区间内 → 继续启动。
- 越界（prod 代码遇到新 schema）→ `not_ready` + 告警，**不参与路由**，避免带着不兼容假设写脏数据。

### 6.4 env_tag 摘除计划

现状：`src/common/database.py:23-33` 的 `current_env_tag()`，多数业务表带 `env_tag` 列。

| 阶段 | 动作 |
|---|---|
| P3a | 运行时（`packages/plugin-kit` 的 DB 封装）统一注入固定值（`prod`），使两节点读到同一份数据；新表不再建该列 |
| P3b | 各插件重写时不再读写该列 |
| P3c | 两端同为新代码后，一次性 drop 列（contract 阶段） |

## 7. 备份与恢复

| 场景 | 做法 |
|---|---|
| 规则生效前 | 开启灰度（首次出现 `target != default_node` 的规则）时，中控自动触发一次逻辑备份并记入审计 |
| 迁移前 | 强制备份，失败中止 |
| 日常 | 依赖 MySQL 主机的定时备份（现状：仓库内无备份脚本，需补） |
| 恢复演练 | 每季度一次：把备份恢复到临时库，跑一次数据一致性巡检（插件关键表行数、最近 24h 业务记录） |

备份实现优先用 `mysqldump --single-transaction`（对 InnoDB 无锁），落在宿主机 `data/backups/` 并保留 14 天。

## 8. 现有部署机制的归宿

总原则（已拍板）：**新架构验证通过之前，旧的两份 clone 与旧容器原样不动**（含 NapCat 分流配置）；验证通过后**整体废弃**，所有服务转到新架构。"过渡期"指 P1~P2 期间。

| 现有资产 | 过渡期 | 验证通过后 |
|---|---|---|
| `scripts/diting-agent.sh`（宿主机执行器）+ systemd 单元 | 沿用（每节点一份实例，现状已支持 `--name dev`） | **废弃**：部署改由中控编排（镜像 tag 驱动，不再 `git pull` 进工作区） |
| `scripts/docker-manager.sh` | 沿用 | 废弃（端口/容器名映射由 compose 的每节点服务取代） |
| 两份 clone + 两个容器 | **沿用且不动** | **废弃**（单仓多服务，节点按 env 起容器） |
| `bot.py` 的 watchfiles 热重载 + `pull.lock` 哨兵 | 新节点不使用（仅 local 开发保留 `HOT_RELOAD`） | 同左 |
| `src/api/**`（管理 API） | 暂留（P2 迁中控） | 废弃 |
| `webui/`（React SPA） | 暂留 | 迁中控托管（产物仍由多阶段 Dockerfile 构建） |
| `nonebot_plugin_apscheduler` 在各插件里的注册 | 靠 env 开关错开（`.env.dev` 关掉 `check_up` 等），代码里没有任何锁 | **保留在节点**（触发与执行在节点）；排程元数据登记到中控 `ctl_jobs`，Redis 租约防双跑（见 `03 §6`） |
| `/diting` 部署命令 | 保留 | 并入 `/env deploy` |
| `.env.dev` 的 `COMMAND_START=["dev-"]` | 保留（旧节点仍在用） | 删除（路由替代；dev/prod 已是同一个 QQ 号，两端统一 `["/", ""]`） |

## 9. CI（当前完全缺失）

现状：无 `.github/`、无 CI 配置；构建靠宿主机 `docker compose build`（冷构建约 28 分钟）。

P4 目标：

1. push 到 `dev/*` → 构建 `diting-node:<sha>` 与 `diting-node:dev-latest` → 推镜像仓库。
2. 合并 `master` → 构建并推 `diting-node:<sha>` + `diting-node:prod-latest`。
3. 部署动作仍由宿主机执行器完成（拉镜像 + 起容器 + 探活），CI 不直连生产。
4. CI 里加最小质量门：`ruff`（或 `flake8`）+ `import` 冒烟（`python -c "import src.plugins"` 级别的可导入检查）。
5. **契约测试（不可省）**：`tests/test_manifest_exporter.py`——在固定 fixture 插件集上断言内省提取结果（命令/别名/关键词/正则逐条比对），**升级 nonebot 必须先过**；`tests/test_classifier_parity.py`——把真实 NoneBot 判定与网关分类器跑同一语料的对拍测试，差异为 0 才算过（`01 §4.4`）。

## 10. 单点与容量

| 组件 | 是否单点 | 现状应对 | 备注 |
|---|---|---|---|
| gateway | 是（新增） | `restart: unless-stopped` + 无状态化（规则来自 Redis/快照，重启即恢复）+ healthcheck | 后续可加热备：第二个网关实例监听同一入口，用 keepalived/反代切换 |
| NapCat | 是（既有） | 保持现状（`restart: always` 已有） | |
| MySQL | 是（既有） | 主机级备份 | |
| Redis | 是（既有） | 升 AOF + 卷；网关有本地快照兜底 | 新架构下 Redis 挂了只影响"规则实时生效"、限流精度与**定时任务租约**（默认 fail-closed，跳过并告警）；不影响消息通路 |
| control | 是 | `restart` + 网关不依赖它做决策 | 中控挂 = 改不了规则、收不到告警、**定时任务照常触发**（排程已下发到节点，见 `03 §6.6`）；消息照常 |

容量：单账号群机器人场景，网关单实例的处理上限远高于实际（事件为文本级，单条毫秒级）。压测目标：1000 事件/秒；两节点各 250 次并发 API 调用，回包全部按重写映射归位（无串包、无孤儿），并覆盖乱序、超时与一次上行断链的结算（`01 §9.6`）。

## 11. 排障手册

| 症状 | 排查 | 处置 |
|---|---|---|
| 全部群都不回话（疑似默认节点故障） | `/env` 第一屏是否显示"prod 故障中，全量由 dev 代管"；`gateway_failover_active`；`/env node` 看两节点状态 | 未接管：查 `emergency_takeover` 是否被关、接管者是否 `ready`、是否命中部署窗口（`02 §5.0`）；已接管但用户说"功能没了"：多半命中拒绝清单，看 `gateway_failover_denied_total{plugin}` |
| 用户看到"该功能在故障恢复期间暂停" | 这是接管期的拒绝清单话术（`01 §5.6` 第二类），不是 bug | 默认节点恢复后自动消失；若认为该插件不该在名单里，走中控改 `canary_deny_plugins`（进审计） |
| 用户说"机器人没反应" | `/env node` 看两节点状态；`curl gateway:8100/healthz`；`/env decisions --node prod --tail 20`（这是**决策日志**，不是节点运行日志） | 若节点 `unhealthy`，看它自己的运行日志 `logs/node-<实例名>/`；若网关无事件，查 NapCat 与网关 WS |
| 一条消息被处理两次 | 检查 NapCat 的 `websocketClients` 数组是否还残留旧节点地址（§3 勘误：这个版本用的是数组，不是 `reverseWSUrls`）；检查是否有人手改了节点 driver | 清理 NapCat 配置，只保留网关 |
| 灰度不生效 | `/env why --group <群> --text "<原文>"` 看命中层级与规则；再看 manifest 覆盖率报告 | 多半是层级写错（群规则压住了插件规则）、该插件 `routable=false`、或它的 matcher 是 opaque 未声明（`01 §4.3`） |
| 插件级灰度"漏判"（该走 dev 的消息去了 prod） | `/env why` 显示未命中插件 → 核对 manifest 里该命令的触发词；跑分类器对拍测试 | 触发词缺失：查该 matcher 是否 opaque；触发词存在但分类器判错：属最高优先级 bug（`01 §4.4`） |
| 定时任务没跑 | `/env node` 的 jobs 与 `ctl_jobs` 登记是否一致；`node_job_runs_total{result}`；`resolve_route` 是否把该群判给本节点 | 未登记则登记（或确认 `enabled`）；租约失败看 `node_job_lease_lost_total`（Redis 不可用会 fail-closed 跳过）；判给别的节点属正常分流 |
| 定时任务重复推送 | `node_job_lease_lost_total`；两个节点各自的"我的群"结果；Redis 租约键 `ctl:job_lease:*` | 租约键的 `run_key` 口径不一致（日期 vs 整点）是常见原因；确认 `job_id` 与 APScheduler id 一致（`03 §6.2`） |
| 回滚不生效 | `/env` 看 override 是否 active；看 `ctl:rules:version` 是否递增 | 网关规则缓存未刷新时，重启网关（会从快照恢复，不影响消息） |
| 节点起不来 | 容器日志；`GET /healthz` 返回的 `plugin_report` | `critical` 插件加载失败会阻止 ready；先修插件或摘掉 `critical` |
| 心跳丢失 | `/env node` 的 `last_seen_at`；节点到中控网络 | 恢复后自动重连；`locked` 状态需人工 resume |
| 节点反复被判 `suspect` 但心跳正常 | `/env node` 看 `loop_lag_ms_p95`；节点日志里是否有长耗时插件 | 按 §1.3 把阻塞任务移出事件循环（线程池或外置服务），不要靠回滚解决 |
| 新命令在 prod 回了"灰度测试中" | 正常：dev 独有功能 + 回滚状态 | 修好后 resume dev，或把代码上线 prod |
| 规则改了但行为没变 | `/env why` 对照；看 `ctl_route_rules.valid_until` 是否已过期 | 过期规则不生效，需重建 |
| 决策日志对不上运行日志 | 用 `trace_id` 串：网关侧 `ctl:decisions` ↔ 节点日志字段（`01 §8.4`） | trace 未透传时先查事件是否被网关降级处理 |
| 节点连着但没有 bot（`/env node` 看着在线，节点却不发消息、也不跑群同步） | 看 `gateway_node_conn_state` 是否卡在 `handshaking`；再看 `gateway_napcat_link_up` 与 `self_id` 是否已知 | 上游未就绪时属正常等待；上游正常仍卡住就是合成 connect 的 bug（`01 §9.3`） |
| 重连窗口内消息丢失 | `gateway_events_dropped_total{reason}` 与 `gateway_event_buffer_depth` | `buffer_overflow` 调大 `NODE_BUFFER_MAX_EVENTS`；`buffer_expired` 调大 `NODE_BUFFER_SECONDS`；都没有则看是否命中 `no_target` |
| NapCat 抖了一下，两端是否都重连了 | 节点日志里三处 `on_bot_connect` 副作用是否各跑一次 | 抖动被放大成反复全量爬取时，调大 `NAPCAT_LINK_DEBOUNCE_SECONDS`（`01 §9.4`） |
| 某条发送在决策日志里查不到 | 先怀疑 HTTP 旁路：`group_send` / `shit_transport` 不走网关（`01 §9.8`） | 属已知例外；要进日志必须改成经网关调用 |
| 节点发送报 `ApiNotAvailable` 或 `WebSocket call api ... timeout` | 前者是节点 WS 正处于 `draining`/重连窗口；后者是 `echo` 未归位，查 `gateway_api_proxy_orphan_total` | 孤儿回包按 bug 处理（`01 §9.6`） |
| 改了 dev 的配置却影响了生产（或反之） | 对照各自 `/healthz` 的 `env_file` 与 `config_fingerprint`；看中控有没有 `NODE_NAME` 冲突告警 | 说明还有隐式发现（名叫 `.env` 的文件）或共用了源文件；按 §2.4 的命名空间整改 |
| 两个服务的日志混在同一个文件里（或某天的日志整段消失） | 核对各自的 `LOG_FILE_PATH` 与卷挂载是否指向同一目录（`01 §8.4`）：loguru 没有跨进程锁，`rotation` 会让两个进程互相破坏对方的文件 | 改成每服务独立目录/卷；变更后确认新文件只被一个进程写过 |
| WebUI 消息日志页不再更新（或群活跃度停在某一天） | 事件流水是否在落库（`ctl_event_persist_lag_seconds`）；该页是否已改指 `event_logs` 并补上 `post_type='message'` 过滤（`01 §8.5`） | 双写期内老表仍在增长属正常；**删除 `logging_info` 之前必须先完成消费者切换** |
| 迁移失败 | `ctl_deployments` 看阶段与错误；检查是否有人在灰度窗口做了 contract | 回滚到备份（迁移前已自动备份） |

## 12. 故障演练清单（上线前必须做一遍）

1. kill 掉 dev 节点容器 → 30s 内自动 override，灰度流量回 prod，告警到群；重启后 `/env resume dev` 恢复。
2. 让 dev 节点某个 `critical` 插件启动失败 → 节点 `not_ready`，**从未承载任何流量**，告警精确指出插件名。
3. 断开 Redis → 消息通路仍正常；规则改动不可用并明确报错；Redis 恢复后自动重新同步。
4. 断开中控 → 消息正常；`/env` 命令返回"中控不可达"而不是静默失败。
5. 断开 NapCat → 告警 critical；恢复后网关自动重连，事件继续。
6. 重启网关 → 规则从快照恢复，10 秒内恢复服务，无规则丢失。
7. 规则冲突演练：故意建两条指向不同节点的同层规则 → 决策走默认节点 + `route_conflict_total` 报警。
8. 回滚演练：灰度一个插件 → 用 `/env rollback --rule` 撤回 → 确认 prod 侧回复降级话术而不是报错。
9. 阻塞演练：在 dev 节点临时注入一个阻塞事件循环 1 秒的插件 → 节点被判 `suspect` 并告警（`loop_lag_ms` 上升），但**不触发自动回滚**；摘掉后自动恢复 `ready`。
10. 分类器对拍：跑 `tests/test_classifier_parity.py`，同一语料下网关分类器与 NoneBot 判定差异必须为 0；再用影子期决策日志与 `messages_event_logs` 回放对账（P1.1 接管后可升级为按 `trace_id` join `event_logs`，连被丢弃的事件也能对上，`01 §8.5`）。
11. 覆盖率演练：给一个插件临时加一个自定义 rule 的 message matcher → 覆盖率报告出现 message 类 opaque 并告警；补 `triggers` 声明或声明 `routable=false` 后告警消失。
12. 调度演练（中控无关性）：断开中控 → **定时任务照常触发**（节点用最后一次排程快照），恢复后能收到排程变更与结果上报。
13. 租约演练：把两个节点的同一个任务调到同一时刻触发 → 只有一个节点执行，另一个记 `skipped` 且无重复推送；kill 掉执行中的节点 → 租约 TTL 到期后可补跑。
14. 插件级灰度演练：灰度 `leaderboard` 到 dev → 只在测试群内生效，其他群的同类命令仍走 prod（确认分类器不漏判、不多判）。
15. 上游断链演练：kill NapCat 超过 `NAPCAT_LINK_DEBOUNCE_SECONDS` → 两节点连接被断开、3s 后重连并停在 `handshaking`；NapCat 恢复后各自收到合成的 `lifecycle/connect`，三处 `on_bot_connect` 副作用各跑一次，无重复爬取风暴（`01 §9.3`、`§9.4`）。
16. 缓冲演练：停掉 dev 节点 30s 再恢复 → 期间命中 dev 的事件进缓冲（`gateway_event_buffer_depth` 上升），恢复后按序投递且 `buffered_ms` 正确；再把 `NODE_BUFFER_MAX_EVENTS` 临时调小，确认超限部分记 `dropped:buffer_overflow` 并告警。
17. echo 重写演练：两节点各 250 次并发 API 调用，期间插入一次上行断链 → 回包全部归位、在途请求被主动结算（节点立刻拿到失败结果而不是干等到 `api_timeout`）、`gateway_api_proxy_orphan_total` 保持 0（`01 §9.6`）。
18. meta 吸收演练：确认节点侧收不到任何 meta 事件，但消息收发、群列表刷新与限速补丁全部正常，连续跑 24h 无异常（`01 §9.7`）。
19. 配置隔离演练：把 dev 节点指向 prod 的源文件（或把它的 `env_file` 指错）→ 启动指纹与 `NODE_NAME` 冲突告警必须报出来，而不是静默用错配置跑起来；改回后确认告警消除（`02` §2.4）。
20. 默认节点故障接管演练：kill prod → 链路断开信号（>10s）先触发接管、心跳信号（30s）兜底，全量流量切到 dev，告警带 `git_sha` 差异与拒绝清单、`/env` 第一屏显示接管中；期间命中拒绝清单的命令收到"故障恢复期间暂停"而不是被 dev 执行（`gateway_failover_denied_total` 上升），对应插件的定时任务跳过；重启 prod → 稳定 60s 后自动回切；再让 prod 抖动一次 → 确认粘滞生效（保持接管并标 `locked`，不来回切）。
21. 部署窗口演练：在灰度生效期间发一次 dev → 该节点流量在窗口内自动改投、告警是"计划内部署"而不是 critical、窗口结束自动恢复引流、无 incident；再把窗口 TTL 临时调到 30s 并故意让部署卡住 → 确认窗口到期后按 `unhealthy` 处理并告警。
22. 接管与发布的交互（最容易被忽略）：在 prod 上做一次正常发布 → 确认**不触发**接管（部署窗口生效）；再手工 `docker restart` prod（不在任何窗口内）→ 确认按故障走接管流程。这一步验的是"豁免只对声明过的部署生效"，也是这套机制唯一容易破的地方。
