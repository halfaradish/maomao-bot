# 01 · 路由与灰度

本文是网关与中控的实现契约。所有字段名、枚举值、算法步骤都以本文为准。

---

## 1. 为什么需要一层"规则"

「把流量切到 dev」这句话有两种实现：改 NapCat 的转发目标（笨重、要重启、只能整体切），或者在入口处决定每条事件去哪个节点（轻、秒级、可细到某个群）。
后者就是本节定义的规则层：**规则不改代码、不重启、不碰容器，只改一个路由决策。**

规则要同时满足四个需求：

| 需求 | 对应设计 |
|---|---|
| 按群灰度 | `scope=group` 的规则 |
| 按插件灰度 | `scope=plugin` 的规则 |
| 群规则优先级高于插件规则 | 解析时的层级排序（§3） |
| 异常时只回滚灰度流量 | override 只作用于 `target=dev` 的规则（§5） |

---

## 2. 数据模型

控制面数据统一放在 **`diting_ctl` 库**（与业务库同实例，独立库名，避免与业务表混在一起被误迁移）。

### 2.1 `ctl_nodes` — 节点注册表

| 字段 | 类型 | 说明 |
|---|---|---|
| `name` | VARCHAR(32) PK | 逻辑名：`prod` / `dev` / 未来的 `standby-1`。**路由规则只引用这个名，不引用容器名或主机名** |
| `kind` | ENUM | `node` / `gateway` / `control`。**网关也在这里登记**（复用同一套心跳与状态展示），但它只有状态、不参与路由——这样 `/env` 总览与告警有唯一的状态来源，中控也能知道网关死活（§8.2） |
| `display_name` | VARCHAR(64) | 展示名 |
| `enabled` | TINYINT(1) | 运营开关：置 0 表示"计划内下线"，不产生故障告警 |
| `state` | VARCHAR(16) | `starting` / `ready` / `suspect` / `unhealthy` / `not_ready` / `locked` |
| `version` | VARCHAR(64) | 应用版本（镜像 tag） |
| `git_sha` | VARCHAR(40) | 提交号 |
| `schema_revision` | VARCHAR(64) | 启动时自检到的数据库 revision |
| `plugin_report` | JSON | 插件加载结果（§4.1） |
| `last_seen_at` | DATETIME | 最近心跳 |
| `registered_at` / `updated_at` | DATETIME | |

### 2.2 `ctl_route_rules` — 灰度与默认路由规则

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | |
| `scope` | ENUM | `group_plugin` / `group` / `plugin` / `global` |
| `group_id` | BIGINT NULL | `group_plugin`、`group` 必填 |
| `plugin` | VARCHAR(64) NULL | `group_plugin`、`plugin` 必填，值取自 manifest 的 `plugins[].name` |
| `target_node` | VARCHAR(32) | 目标节点逻辑名 |
| `priority` | INT | 同层内的优先级，**越大越优先**，默认 0 |
| `enabled` | TINYINT(1) | |
| `valid_until` | DATETIME NULL | 到期自动失效（用于"临时压测一周"这类规则） |
| `note` | VARCHAR(255) | 人写的理由，强制填写 |
| `created_by` / `created_at` / `updated_at` | | |
| `revision_id` | BIGINT | 该行所属的规则版本，见 2.3 |

约束（写入时校验，不满足直接拒绝）：

- `scope=group_plugin` → `group_id` 与 `plugin` 均非空
- `scope=group` → `group_id` 非空、`plugin` 为空
- `scope=plugin` → `plugin` 非空、`group_id` 为空
- `scope=global` → 两者皆空（用于"临时全量引流 dev"与"显式默认节点"）
- `target_node` 必须存在于 `ctl_nodes` 且 `enabled=1`

### 2.3 `ctl_rule_revisions` — 规则版本（不可变）

每次规则变更（新增/修改/删除/启停）生成一个版本，内容是**变更后的全量规则快照**：

| 字段 | 说明 |
|---|---|
| `id` | 自增，同时作为"规则版本号"下发（Redis `ctl:rules:version`） |
| `created_at` / `created_by` | |
| `action` | `create` / `update` / `delete` / `toggle` / `rollback` |
| `summary` | 人读的一行摘要，如「plugin=email → dev，群 123,456」 |
| `snapshot` | JSON：全量规则数组 |

作用：WebUI 上的 diff 与「回滚到上一版」，以及网关重启后从最新版本恢复。

### 2.4 `ctl_overrides` — 强制改投

| 字段 | 说明 |
|---|---|
| `id` | |
| `source_node` | 被改投的节点（如 `dev`） |
| `fallback_node` | 改投目标（如 `prod`） |
| `kind` | `auto`（异常自动）/ `manual_freeze`（人工冻结） |
| `reason` | 文字理由 |
| `incident_id` | 若由异常触发，关联 `ctl_incidents.id` |
| `active` / `created_at` / `cleared_at` / `cleared_by` | |

**语义（严格对齐需求）**：override 是"把 `target=source_node` 的规则改投到 `fallback_node`"的映射。它**只影响指向该节点的规则**，指向其他节点的规则完全不受影响——这就是「仅命中灰度规则的流量切回 prod，非灰度流量保持原路由不变」。

同一时刻一个节点最多一条 active override；`manual_freeze` 优先于 `auto`，人工恢复时两者一并清除。

### 2.5 `ctl_incidents` — 异常事件与告警状态

它同时是 §8.2 的**告警状态表**（不是事件流水）：一条告警从进入到恢复只有一行，进入与恢复各发一次通知。

| 字段 | 说明 |
|---|---|
| `node` / `kind` / `severity` | `kind`: `plugin_load_failed` / `schema_mismatch` / `heartbeat_lost` / `link_down` / `flapping` / `manual`（节点级）与告警侧新增的 `control_self` / `gateway_link` / `napcat_link` / `control_unreachable` / `buffer_drop` / `orphan_echo` / `coverage` / `job_registry` / `lease` / `deploy_failed` / `backup_failed` / `config_conflict`；`severity`: `critical` / `warning` / `info` |
| `dedup_key` | 告警身份，形如 `node:dev:unhealthy` / `gateway:napcat_link` / `control:self`（§8.2）。同键进入时是**更新**而不是新行 |
| `alert_state` / `last_notified_at` | `active` / `resolved`；最近一次通知时刻，用于"持续期不重复、按 `alert_remind_minutes` 提醒"（§8.2） |
| `detail` | JSON（失败的插件名、缺失心跳秒数、指标值等） |
| `auto_action` | 本次自动做了什么：`override_created` / `alert_only` / `none` |
| `started_at` / `resolved_at` | |

### 2.6 `ctl_audit` — 审计

`actor_type`（`qq` / `webui` / `system`）、`actor`、`action`、`target`、`before`/`after`（JSON）、`reason`、`trace_id`、`created_at`。
**所有**改规则、改 override、改节点开关、执行回滚的动作都必须落这张表，包括自动动作。

### 2.7 `ctl_settings` — 键值配置

`default_node`（默认 `prod`）、`auto_resume`（默认 `false`）、告警目标三键（`alert_group_ids` / `alert_mention_qqs` / `alert_emails`——**告警收件人的唯一来源**，§8.2；env 里不放告警目标，只有引导用的 seed，见 §8.2）、`alert_remind_minutes`（持续告警的提醒间隔，0 = 不提醒）、`degrade_reply_text` / `failover_deny_reply_text` / `no_target_reply_text`（三类文案，见 §5.6）、`emergency_takeover`（**默认 `true`**：默认节点故障后允许自动接管；关掉即退回"降级话术 + 等人修"，见 §5.4）、`heartbeat_interval_seconds`（5）、`suspect_after_seconds`（15）、`unhealthy_after_seconds`（30）、`canary_deny_plugins`（JSON 数组：高危插件禁止被引流，**有最终否决权**；三个执行点——写规则时校验 + 网关投递前过滤 + 节点侧 `failover_guard`——见 §4.5）、`slow_handler_warn_ms`（500，见 `02 §1.3`）、`snapshot_poll_seconds`（15：快照版本轮询间隔，**Redis 不可用时的陈旧上界就是它**）、`snapshot_stale_warn_seconds`（300：快照长时间未刷新的告警阈值；两者见 `04 §4.3`）、`job_lease_ttl_seconds` / `job_lease_fail_mode`（`closed` / `open`，见 `03 §6.6`）、`ops_admins`（运维名单持久化，见 `04 §4.10`）等。

### 2.8 `ctl_deployments` — 部署与迁移记录

一行 = 一次发布 / 回滚 / 迁移。它同时是 `/env deploy --status` 的数据源、`--rollback` 取"上一次成功 sha"的来源，以及部署窗口（`02 §5.0`）与进度停滞判据（`02 §5.7`）的载体。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | 对外即 `deployment_id` |
| `kind` | ENUM | `deploy` / `rollback` / `migrate` |
| `target` | VARCHAR(32) | `ctl_nodes.name`，或 `gateway` / `control`——**带外发布也落这张表**（`02 §5.6`），这样"谁在什么时候把生产换成了哪个 sha"只有一处可查 |
| `from_sha` / `to_sha` | VARCHAR(40) | **记 sha 不记 tag**——"这次发的是什么"必须可查（§6.2）；`--tag` 解析后的实际值进 `to_sha` |
| `tag` | VARCHAR(64) NULL | 人写的镜像 tag，仅供回执展示，不作判据 |
| `phase` | ENUM | `pending` / `pull` / `start` / `selfcheck` / `ready` / `failed`（§6.2 的 `/env deploy --status` 按它展示） |
| `phase_updated_at` | DATETIME | 阶段最后推进时刻。**进度停滞判据用它**（`02 §5.7`） |
| `window_id` | VARCHAR(64) NULL | 关联的部署窗口（`02 §5.0`）；网关 / 中控的带外发布为 NULL（它们不在业务路由里，没有窗口） |
| `schema_revision` | VARCHAR(64) NULL | `kind=migrate` 时的目标 revision（`02 §6.2`） |
| `requested_by` | VARCHAR(64) | QQ 号或 `system` |
| `started_at` / `finished_at` | DATETIME | |
| `result` | VARCHAR(32) | `running` / `success` / `failed`（`02 §11` 说的"deploying 阶段"即 `result=running`） |
| `error` | TEXT NULL | 失败原因原文（`02 §11` 排障要看它） |
| `note` | VARCHAR(255) | 人写的理由（`/env deploy --note`） |

约束与语义：

- **`--rollback` 取"上一次 `kind=deploy` 且 `result=success` 的记录**（§6.2），因此失败必须可靠落库，不能只留在日志里。
- **一次部署只有一行**，`phase` 原地推进；同 `target` 同时只允许一行 `result=running`（`ctl:deploy_lock:<target>`，§6.2 的幂等）。
- **失败不写 `ctl_incidents`**（`02 §5.0` 已定）：它是部署记录，不进故障与自动回滚统计。
- 阶段推进与终态由 `02 §5.7` 的接口写入（`/progress` 与 `/end`），不由人工改。
- §9.10 把 `ctl_deployments` 的**既有列含义**列入"不允许变更"的跨版本契约（只加可选列是允许的）。

### 2.9 `ctl_decisions` — 决策日志落库

**归属：网关产生、中控落库**——与事件流水同一分工（§8.5）。网关不持有中控库凭证（`02 §2.0`），因此它只写 Redis Stream；四类必落的部分经 HTTP 上报中控，由中控批量插入。

- 全量实时：Redis Stream `ctl:decisions`（**网关写**），保留 24h，供 WebUI 实时页与 `--follow` 排障。
- 落库：仅**降级、冲突、投递失败、控制命令**四类必落 `ctl_decisions`（保留 30 天），避免高频写库。上报失败不阻塞投递——与 `§8.5` 的 `EVENT_LOG_SINK` 共用同一队列与背压策略（队列满丢最旧并计数）。

| 列 | 说明 |
|---|---|
| `id` | BIGINT PK |
| `trace_id` | 与 `event_logs.trace_id` 同值，两张表可按它 join（§8.5） |
| `ts` | 决策时刻 |
| `group_id` / `user_id` | 可空（私聊无 `group_id`） |
| `text_digest` | 消息文本哈希，**不存原文**（§8.3） |
| `plugins` | 分类器判定的插件集合（JSON 数组；冲突时会有多个，§3.2 ④） |
| `rule_id` / `layer` | 命中规则与层级（§3.2 ③④） |
| `node` | 最终目标节点 |
| `override` / `conflict` / `failover` | 三个布尔标记（§3.2 ④⑥） |
| `latency_ms` | 入站到投递的耗时 |
| `delivery_result` | §9.5 的词表：`delivered` / `buffered` / `dropped:<reason>` |
| `buffered_ms` / `revised` | 仅经缓冲后投递才有（§9.5） |

索引：`(ts)`、`(trace_id)`、`(node, ts)`、`(delivery_result, ts)`。

`ctl:decisions`（Stream）与 `ctl_decisions`（表）是同一份数据的两个介质，字段一致：**排障优先用 Stream**（全量、实时、24h），**对账与统计用表**（只含四类、30 天）。

### 2.10 下发到网关与节点的配置子集

`ctl_settings` 的键并非每个服务都要读。网关与节点**不持有中控库凭证**（`02 §2.0`），因此它们需要的那部分必须随快照下发——这一节就是那份清单。

| 消费者 | 需要的键 | 用途 |
|---|---|---|
| **网关** | `default_node`、`emergency_takeover`、`canary_deny_plugins`、`degrade_reply_text`、`failover_deny_reply_text`、`no_target_reply_text`、`alert_group_ids`、`rate_limit_enabled`、`rate_limit_capacity`、`rate_limit_refill_rate`、`rate_limit_per_group`、`rate_limit_max_wait_seconds` | 路由兜底、接管开关、投递前拒绝过滤、三类本地话术、控制命令回执推管理群、限流主体（§11.3） |
| **节点** | `canary_deny_plugins`、`failover_deny_reply_text`、`slow_handler_warn_ms`、`job_lease_fail_mode`、`job_lease_ttl_seconds`、`rate_limit_enabled`、`rate_limit_emergency_stop`、`rate_limit_auto_stop_threshold`、`rate_limit_auto_stop_time_window`、`delay.*`（按插件命名空间，§11.4） | `failover_guard`（§5.4）、慢 handler 阈值、任务租约、急停（§11.3）、回复延迟（§11.4） |
| **中控** | 其余全部 | 它是写入者，直接读表，不需要下发 |
| 独立通道 | `ops_admins` | 走 `ctl:ops_admins`（§6.3），不并进这里 |

**机制：一个快照接口、三个版本号。** 快照内容 = `{rules, overrides, settings_subset, manifest_union, rules_version, settings_version, manifest_version}`；任一版本号变化即**全量重载**。刷新路径与陈旧上界完全复用规则快照那一套（§3.1、`04 §4.3`）：Redis pub/sub 广播（亚秒）→ 中控 HTTP 轮询（`snapshot_poll_seconds`，默认 15s）→ 每 30 分钟全量对账。

**快照里还有一份不是"配置"的东西：manifest 并集**（§4.1）。网关用它跑分类器（把消息归类到插件，§4.4），节点用它的**差集**跑兜底话术（§5.6）。它有独立的 `manifest_version`，由中控在每次拉取节点 manifest 后按"并集是否变化"递增（默认 60s 拉一次）——复用同一个快照接口与刷新路径，不另开通道。

- **为什么不合并成一个版本号**：settings 变更若也生成一条 `ctl_rule_revisions`，会污染规则历史与 WebUI 的版本 diff——那张表的语义是"规则快照"，不该被一次文案改动写入。
- **优先级**：**快照为准，env 只是首启兜底**。快照到达前用 env 的值，到达后以快照为准；env 改动要重启才生效，快照改动秒级生效。
- **决策 14 的唯一例外**：`CONTROL_UNREACHABLE_REPLY_TEXT` 这类"**中控不可达时才会用到**"的文案只能放 env（`02 §2.1`、`02 §2.3`）——C 层的读取路径就是中控，中控不可达时读不到它。除此之外不放 env。
- **编辑入口**：C 层目前只有 **WebUI**（§6.2 的命令清单是查询与规则类，没有设置类命令；要不要加 `/env set` 属 P2 增量）。所有写入进 `ctl_audit`，并递增 `settings_version`。

## 3. 路由解析算法

### 3.1 输入

- 事件（OneBot V11 原始 JSON）、消息纯文本、`group_id`（私聊为空）
- 最新规则快照（网关内存，按版本号失效），含 **`ctl_settings` 的配置子集**（清单见 §2.10）。刷新与权限快照同机制（`04 §4.3`），三条路径：Redis pub/sub 广播（亚秒）→ **中控 HTTP 轮询版本号** `snapshot_poll_seconds`（默认 15s，**不依赖 Redis**）→ 每 30 分钟全量对账。**Redis 挂掉只让生效变慢（≤15s），不改变正确性**；中控也不可达时用本地 `RULE_CACHE_FILE`（`02 §2.1`）并触发陈旧告警（§8.2）
- 当前 active override 映射
- `default_node`

### 3.2 步骤

```
resolve(event) -> Decision{node, rule_id, source, override, conflict, failover, trace_id}

① 控制命令短路
   文本命中控制命令 且 发送者在管理员名单 → {kind: control}，本地执行，不投递

② 归类到插件集合 P
   P = classifier.match(event)         # 只含 routable=true 的插件
   顺序：command（命令前缀，含别名）→ keyword → regex
   语义必须与 NoneBot 的判定逐位一致（§4.4）
   限制：正则只跑未声明 regex_routing=false 的插件的 patterns，
        总条数上限 200（超限启动告警）；超长文本（>2000 字符）只做命令前缀匹配

③ 收集候选规则（enabled=1 且未过期）
   scope=group_plugin  且 group_id 匹配 且 plugin ∈ P  → 层 0
   scope=group         且 group_id 匹配                → 层 1
   scope=plugin        且 plugin ∈ P                   → 层 2
   scope=global                                        → 层 3

④ 取最高层（层号最小的非空层）的候选集合 C
   · C 内 target 一致           → 取该 target；命中规则 = C 中 priority 最大者
   · C 内 target 不一致（冲突） → 若 default_node ∈ targets，取 default_node；
                                 否则取 priority 最大者，并标记 conflict=1
   冲突一律落库并打指标 route_conflict_total

⑤ 无任何候选 → default_node（source=default）

⑥ 叠加 override
   target ∈ active_overrides → target = fallback_node，标记 degraded=1
   若该 override 的 kind=emergency（默认节点故障接管）→ 同时标记 failover=1
   （failover=1 是节点侧拒绝闸的输入：接管期间的流量带着它投递，§5.4、§9.5）

⑦ 目标节点健康兜底（§5.4）
   目标不可用 → 按策略改投或降级（可能再次进入⑥）
```

### 3.3 为什么这样排序

- 层 0 > 层 1 > 层 2 > 层 3 直接实现「**群规则优先级高于插件规则**」：只要有一条命中该群的规则，插件级规则就没有机会生效。
- `group_plugin`（既指定群又指定插件）比纯 `group` 更具体，所以放在最前——它解决的是"只在 A 群灰度 email 插件，A 群其他功能仍走 prod"。
- 同层用 `priority` 再决定：`scope=group` 层里可以同时有"群 A → dev"和"群 A → prod"两条（不同 priority），便于用一条高优先级的 prod 规则临时压制灰度。

### 3.4 举例

设有规则：① `group_plugin(群 100, email) → dev`；② `group(群 100) → prod`；③ `plugin(email) → dev`；④ `global → prod`（默认）。

| 事件 | 命中 | 结果 |
|---|---|---|
| 群 100 发 `邮件 查询` | 层 0 命中 ① | dev |
| 群 100 普通聊天 | 层 1 命中 ②（层 0 无候选） | prod |
| 群 200 发 `邮件 查询` | 层 2 命中 ③ | dev |
| 群 200 普通聊天 | 层 3 命中 ④ | prod |
| 群 300 发 `查分`（插件 `leaderboard`，无规则） | 只有 ④ | prod |

### 3.5 边界情形（逐条定死）

| 情形 | 处理 |
|---|---|
| 私聊消息（无 `group_id`） | 群规则不适用，只走插件规则与默认节点 |
| `on_notice` / `on_request` / `meta_event` | 被动流量：不归类插件，只走群规则（若有 `group_id`）与默认节点 |
| 一条消息同时命中多个插件且目标不同 | 冲突 → 取默认节点（prod），落库 + 打指标 |
| 文本过长（> 2000 字符） | 只做命令前缀匹配，不跑正则，避免正则在长文本上回溯 |
| 规则指向的节点被 `enabled=0` 关闭 | 视为该规则不存在（回落到下一层），并告警提示规则需清理 |
| 规则指向的节点不存在 | 同上（写入时已校验，历史数据兜底处理） |
| 群规则存在但群已被踢/不在白名单 | 不影响路由（路由不做权限判断，权限仍在节点内） |

## 4. 插件识别与插件清单（manifest）

### 4.1 清单契约（节点上报）

**已拍板：清单由节点内省 NoneBot 注册表自动导出，声明只用于补内省看不到的语义——不做框架式 SDK，插件不改写法也能被路由与灰度。** 产生方式、提取算法与治理见 `03-插件契约与改造映射.md §3`。

节点启动完成后（`on_startup` 末段）通过内部接口暴露自身 manifest；中控定期拉取（默认 60s）并**合并两个节点的并集**（dev 有新插件时，其触发词也必须能被识别，否则新命令永远不会被引到 dev）。并集**随快照下发**（§2.10），网关与节点都拿得到：网关用它跑分类器（§4.4），节点用它的差集跑兜底话术（§5.6）。

合并时**必须校验两节点的 `command_start` / `command_sep` 一致**：它们决定命令前缀的展开方式（§4.4 第 2 步），不一致就不存在"正确的并集"。不一致时报 critical 并**保持上一份并集**——不要拿一份混了两种前缀的清单去路由（`02 §2.3` 已要求两端必须一致）。

```jsonc
{
  "node": "dev",
  "version": "1.3.0-dev",
  "git_sha": "abc1234",
  "schema_revision": "2026_09_18_email_v2",
  "generated_at": 1758000000,
  "nonebot_version": "2.4.4",              // 内省与分类器依赖它，版本不符要告警
  "command_start": ["/", ""],              // 分类器据此展开命令前缀（与节点配置一致）
  "command_sep": ["."],
  "coverage": {                            // 清单的健康自述（§4.3）
    "matchers_total": 74,
    "derived": 72,
    "opaque": [
      {"plugin": "auto_manage_group", "matcher": "banned_word_detector",
       "type": "message", "reason": "自定义 rule 不在已知规则类型内"}
    ]
  },
  "plugins": [
    {
      "name": "email",                     // 必须是稳定的逻辑名，等于路由规则里的 plugin 值
      "domain": "notify",
      "routable": true,                    // 推导：有 message 类触发 → true；可被 extra 覆盖为 false
      "canary_policy": "allow",            // allow | deny（只能加严；中控 deny 名单有最终否决权，§4.5）
      "critical": true,                    // true 时加载失败会导致节点 not_ready
      "source": "derived",                 // derived=内省可得 | declared=主要依靠声明
      "triggers": [
        {"type": "command", "tokens": ["邮件"], "aliases": [["email"]], "source": "derived"},
        {"type": "keyword", "values": ["内推码"], "source": "derived"},
        {"type": "regex", "pattern": "^搬史\\s+", "source": "declared"}
      ],
      "jobs": [                            // 定时任务（内省自 APScheduler，与 ctl_jobs 对账）
        {"job_id": "send_check_on_work_msg", "schedule": "cron:10 30 0 * * *", "source": "derived"}
      ],
      "topics": ["email_notify"],          // 推送目标主题（与 subscriptions 对账）
      "perm_points": ["email:send"],
      "perm_groups": [                     // 中控对账创建
        {"name": "email_users", "display_name": "邮件用户", "perms": ["email:send"]}
      ]
    }
  ]
}
```

- `triggers[].type` 的取值域固定为五种：`command` / `keyword` / `regex` / `startswith` / `fullmatch`——与 `03 §3.1` 的提取表、§4.4 的复刻表**一一对应**。新增类型必须同时改分类器与对拍测试（属 §9.10 不允许的变更）。
- `routable=false` 一票否决：即使写了 `scope=plugin` 的规则，解析时也不会命中（被动插件是"全域流量"，按群灰度才对它有约束力）。
- **被动监听不写进 `triggers`**：`on_notice` / `on_request` 与不带命令的 `on_message` 不产生触发词。因此"既有命令又有被动监听"的插件（如 `auto_manage_group`）仍然 `routable=true`——它的**命令**可以被插件级灰度，它的**被动部分**则随所在群的路由走。
- `triggers[].source` 区分 `derived`（内省得到）与 `declared`（人工补声明）：大量 `declared` 说明内省有盲区，应优先修提取器而不是继续声明。
- `jobs` / `topics` / `perm_points` / `perm_groups` 是节点上报的**供对账的事实**：中控据此维护 `ctl_jobs`（`03 §6.2`）、`subscriptions`（`04 §4.8`）与权限点的声明式 provisioning（`04 §4.7`），插件不再直写权限表；四处手搓 `ensure_perm_group`（清单见 `04 §3.1`）收口到这里。
- `canary_policy=deny` 的插件（不可逆/高危）在**写入规则时**直接拒绝，并被 `/env route` 与 WebUI 双重拦截；中控侧的 deny 名单见 §4.5。
- `critical` 只影响健康判定，不影响路由。

### 4.2 清单怎么来：内省导出 + 声明覆盖

- **内省导出（主路径）**：节点遍历 NoneBot 注册表，从 matcher 本身读触发词——`Plugin.matcher` → `Matcher.rule.checkers` → `Dependent.call` → `CommandRule.cmds`（含 aliases）/ `KeywordsRule.keywords` / `RegexRule.regex` / `StartswithRule` / `FullmatchRule`；定时任务从 `nonebot_plugin_apscheduler.scheduler.get_jobs()` 读。**声明与行为是同一份东西，不存在漂移。**
- **声明覆盖（补充）**：`PluginMetadata.extra["diting"]` 只用于补内省看不到的语义（`canary_policy` / `critical` / `topics` / 权限点 / opaque 补声明 / `routable=false`），**不允许抄一份完整触发词清单**。
- **不做**：不提供 `business_command()` 之类的注册 API——它不增加任何能力，只会制造第二份真相（`03 §1`）。

### 4.3 覆盖率报告与治理

manifest 的 `coverage` 段是中控判读清单完整性的依据：

- `opaque[]` 中的 **message 类** matcher 说明"该插件可能有命令却无法参与插件级灰度" → 中控告警并在 WebUI 展示；处置二选一：补 `triggers` 声明，或声明 `routable=false` 承认它不参与。
- **被动插件的 opaque 不算问题**（notice / request 不参与插件级路由）。
- 内省依赖的 NoneBot 符号（分公开与非公开两档）、版本 pin、CI 断言测试（`tests/test_manifest_exporter.py`）与断裂时的退路，见 `03-插件契约与改造映射.md §3.4`。

### 4.4 网关分类器：必须与节点判定逐位一致

网关不跑 NoneBot，因此分类器必须**复刻** NoneBot 的语义，才能保证"网关认为命中插件 X"与"节点上插件 X 真的会匹配"一致：

- **五种触发类型各有各的"取哪段文本"方式，复刻时必须逐个对上**——这是最容易写错、而且写错了不会报错的地方（只会让灰度悄悄失真）：

  | 类型 | 取哪段文本 | 判定 |
  |---|---|---|
  | `command` | **首个消息段**，且 `is_text()` 必须为真 | `lstrip` 后做**最长前缀**匹配；命中后 token 必须逐位相等；再按 `force_whitespace` 判空白（见下） |
  | `keyword` | `get_plaintext()`（**所有文本段拼接**） | 子串包含，**大小写敏感**——`KeywordsRule` 没有 `ignorecase` 参数 |
  | `startswith` | `get_plaintext()` | `re.match` 跑"转义后前缀的正则交替"，`ignorecase` 时加 `re.IGNORECASE` |
  | `fullmatch` | `get_plaintext()` | `ignorecase` 时两侧都 `casefold()`，再比集合成员；**空文本直接不匹配** |
  | `regex` | **`str(message)`**，即 CQ 码串 | `re.search(pattern, flags)`——注意它**不是** `get_plaintext()`：`^xxx` 这类锚点会被前导的 `[CQ:at,...]` 挡住，而正则也可以直接匹配 CQ 码本身 |

- **`command` 的四个步骤**（`TrieRule.get_value` + `CommandRule.__call__`，缺一不可）：
  1. 首段 `is_text()` 不为真 → 整条不匹配（所以 `@bot /ban` 里的命令**不**成立——这是与关键词/开头/全匹配最容易被忽略的差别）；
  2. 前缀集合 = manifest 的 `tokens` / `aliases` × `command_start` × `command_sep`：单段命令只用 `command_start`，多段命令用 `command_start × command_sep` 的笛卡尔积与 `sep.join(tokens)`；
  3. `cmd ∈ cmds`（token 逐位相等，不做大小写归一）；
  4. **空白判定**：`force_whitespace` 为 `None` **或没有参数**时直接通过；为 `str` 时要求命令与参数之间的空白**精确等于**该串；为 `bool` 时要求"有/无空白"。项目里有两处显式使用（`diting_deploy/commands.py:590`、`permission_manager/runtime.py:15`，都是 `True`）——**漏了第 4 步会让 `banxxx` 被误判成 `ban`**。
- **实现位置**：`packages/contracts`，被三处共用——网关执行路由、中控的生效预览（§7）、节点的 `my_groups`（`03 §6.3`）。这是"单一实现"原则的落点。
- **一致性保证**：① 对拍测试——把真实 NoneBot 的判定与分类器跑同一语料（含别名、`command_sep`、at/图片混合消息、空白变体），差异一律当 bug；② 影子期用真实流量回放对账（`00-总览.md §8`）。
- **风险定位**：这是全项目最关键的一个函数。分类错了不会报错，只会让灰度悄悄失真（漏判 → 新功能在灰度期看不到；多判 → 未被灰度的插件也被带进 dev）。

### 4.5 灰度策略与高危护栏

- **声明只能加严**：插件可以自报 `canary_policy=deny`；中控的 `ctl_settings.canary_deny_plugins` 名单**最终否决**——写入 `scope=plugin` / `scope=group_plugin` 规则时校验，命中即拒绝。
- 高危名单放在控制面（数据、热改、进 `ctl_audit`）：安全策略不该依赖被约束对象的自我声明，也不该为改一个名单发版。
- 建议初始名单（沿用存量插件的高危判定）：`mass_kick`、`group_ban`、`group_msg_del`、`group_send`、`shit_transport`、`diting_deploy`、`permission_manager`。
- 写入规则时的完整校验：`plugin` 必须存在于两节点 manifest 并集、不在 deny 名单、目标节点 `enabled=1`。
- **这份名单有三个执行点**：① 写规则时校验（上一条，防"把高危插件引流给 dev"）；② **网关投递前过滤**——默认节点故障后全量接管期间（§5.4），网关在投递前查同一份名单，命中即不投递、回"该功能在故障恢复期间暂停"；③ **节点侧 `failover_guard` 中间件**（`03 §5`）——按 matcher 所属插件拦截，回同一句话术。
  - 名单只有一份（`ctl_settings.canary_deny_plugins`），执行点三处。② 不能省：接管是默认节点的 fallback，根本不经过规则写入这一环。③ 也不能省，而且它是**唯一能覆盖被动 matcher 的一道**——网关的分类器只认触发词，而"违禁词检测"这类 `on_message` 根本没有触发词（§4.1 写明被动插件是"全域流量"），网关无从知道一条普通群消息会被哪个插件处理；只有节点自己知道，因为它就是 matcher。真实反例见 §5.4。

### 4.6 存量与第三方插件

- **存量 38 个插件**：内省让其中约 97% 的 matcher **零改动**即可参与插件级灰度（就绪度表见 `03 §7`），只有 2 处自建 rule 的 message matcher 需要补声明。
- **第三方插件**：用标准 `on_command` / `on_keyword` / `on_regex` 的自动可路由；自建 matcher（如 Alconna）加一个提取器或在 `extra` 里声明即可；什么都不做则落 `routable=false` 的安全默认。
- 因此**插件级灰度不再依赖任何插件改造**，P2 即可开始（`02 §4.5`）。

## 5. 健康状态机与自动回滚

### 5.1 状态定义

| 状态 | 判定 | 是否参与路由 |
|---|---|---|
| `starting` | 已注册，自检未完成 | 否 |
| `ready` | 自检通过 + 心跳正常 | 是 |
| `suspect` | 心跳缺失 ≥ 3 次（15s），**或事件循环延迟连续超标**（§5.2） | 是（仅告警） |
| `unhealthy` | 心跳缺失 ≥ 6 次（30s） | 否 → 触发自动 override |
| `not_ready` | 自检失败（关键插件加载失败 / schema 越界 / **启动时** Redis 不可达） | 否 → 触发自动 override |
| `locked` | 10 分钟内状态翻转 ≥ 3 次 | 否 → 需人工干预 |

```
starting ──自检通过──▶ ready ──缺失≥3──▶ suspect ──缺失≥6──▶ unhealthy
    │                   ▲                                     │
    └──自检失败──▶ not_ready                                  │
                        └──────────心跳恢复 + 稳定 60s─────────┘
                                   （auto_resume=true 时自动；默认需 /env resume）
    任意状态 ──10min 内翻转≥3次──▶ locked ──人工 resume──▶ ready
```

> **`not_ready` 里的 Redis 判据只作用于启动自检，运行期不重判。** 运行期 Redis 断开不改变健康状态与路由（节点继续承载流量，只是任务租约 fail-closed 跳过、限流精度下降），原因见 `02 §10`：健康判定的权威来源是节点 HTTP 心跳与中控内存/`ctl_nodes.last_seen_at`，把 Redis 拉进来会让一次 Redis 抖动同时打掉两个节点的路由——而 Redis 从来不在消息通路上。

### 5.2 两个独立的探测源

| 探测源 | 粒度 | 用途 |
|---|---|---|
| 网关侧 WS 链路 | 秒级（连接断开即刻感知） | 立即按 override 投递，不等中控；避免"心跳还没超时就先把消息丢给死节点" |
| 中控侧心跳 | 5s 周期，15s/30s 阈值 | 状态机与审计的权威来源；覆盖"链路在但进程假死"的情况 |

节点心跳内容：`{node, version, git_sha, schema_revision, uptime, plugin_report, counters:{events_handled, errors_by_plugin}, loop_lag_ms_p95, ts}`。

`loop_lag_ms_p95`（事件循环延迟 P95）是节点阻塞的先兆指标：节点连续 3 次上报 > 500 ms 时，中控把该节点标为 `suspect` 并告警，但**不触发自动回滚**。理由是阻塞通常来自节点自身的重计算或同步 IO（BERT 推理、同步数据库驱动等），回滚解决不了，反而会把"节点自己堵住"误判成"新功能有 bug"，产生没有必要的回滚。硬约束与存量问题清单见 `02-部署与运维.md` §1.3。

**启动静默期（对所有服务生效）**：任何服务启动后 60s 内的"不健康"不告警，先建立一次基线。缺了它，每次发布网关或中控都会自己触发一批告警（节点 3s 才重连、心跳本来就断续）。`02 §5.6` 里中控那条"自我豁免"是这条规则的特例，应当按通则实现而不是各服务各打一个补丁。

### 5.3 触发自动回滚的条件

1. 节点 `not_ready`（**插件启动失败**：`critical=true` 的插件加载失败、schema 校验不过、启动时 Redis 不可达；运行期 Redis 断开不算，见 §5.1 的注）
2. 节点 `unhealthy`（**心跳失联**：30s）
3. 网关链路断开持续 > 10s
4. （P4 可选）节点上报的某插件 5 分钟错误率超阈值 → 只取消该插件的灰度（`scope=plugin` 的规则降级），不动节点级

> 事件循环延迟超标**不在**此列：它只把节点标为 `suspect` 并告警（§5.2），因为阻塞是节点自身问题，回滚解决不了。
>
> **计划内重启也不在**此列：部署窗口内的重启（`02 §5.0`）不计故障、不触发本节任何动作。这一条是必需的——没有它，每次发 prod 都会因为"重启期间心跳缺失"触发一次全量接管。

触发后中控执行（一个事务）：

```
1) 新建 ctl_incidents（kind 对应异常类型，severity=critical）
2) 按异常节点分两种情况写 override：
   a. 异常节点不是 default_node → ctl_overrides{source_node=异常节点,
        fallback_node=default_node, kind=auto, incident_id}（本节点引流回默认节点）
   b. 异常节点就是 default_node → ctl_overrides{source_node=default_node,
        fallback_node=接管者, kind=emergency, incident_id}（判据与护栏见 §5.4）
3) 写 ctl_audit{actor_type=system, action=auto_rollback 或 emergency_takeover}
4) 递增规则版本号 → Redis pub/sub 通知网关（网关 1s 内生效）
5) 按 §8.2 发告警（`level=critical`、`dedup_key=node:<名>:<kind>`，出口走降级链；接管类告警的正文须含 `git_sha` 差异与拒绝清单）
```

### 5.4 override 生效范围与默认节点故障的接管

**非默认节点（灰度节点）异常**：只改投 `target_node = 异常节点` 的规则，`target_node` 是其他节点的规则**一条都不动**——效果是该节点的群/插件流量回默认节点（决策 2 的"简单回滚"）。

**默认节点本身异常（prod 挂了）**：取**自动全量接管**，不需要人工确认。

- **判据**：接管者必须 `ready`。与默认节点**同镜像 tag** 时是零代码差异的等价替换（首选）；不同 tag 时（dev 正在灰度）仍然接管，但按下面的拒绝清单封顶最坏情况。
- **触发与开关**：取两个信号中先到的那个——**网关侧链路断开持续 > 10s**（§5.2 的秒级探测源，通常先到）或中控侧 `unhealthy`（心跳失联 30s）、`not_ready`。前者让接管的空窗从 30s 缩到 10s 量级；两者之间的十余秒里，事件按 §9.5 进缓冲或回 `no_target_reply_text`。`ctl_settings.emergency_takeover` **默认 `true`** —— 它是 kill-switch（关掉即退回"降级话术 + 等人修"），不再是许可开关。计划内重启（部署窗口，`02 §5.0`）不触发。
- **拒绝清单**：接管期间把 `ctl_settings.canary_deny_plugins` 这份名单从"写规则时校验"扩展为**运行期过滤器**，**两个运行期执行点**（另一个是写规则时校验，见 `§4.5`）：
  1. **网关**：能归类到插件的事件（命令类）在投递前拦下，直接回"该功能在故障恢复期间暂停"。
  2. **节点**：`failover_guard` 中间件（`03 §5`）按 matcher 所属插件拦截。它**必须存在**——网关只能按触发词归类，而被动 matcher（`on_message` 的自定义 rule、`on_notice`）没有触发词、`routable=false`（`§4.1`），网关无从知道一条普通群消息会被哪个插件处理。**真实反例**：`auto_manage_group` 的 `banned_word_detector` 是 `on_message` + 自定义 rule（正是 `03 §3.3` 标定的 opaque），命中违禁词后执行 `set_group_ban(... 1 小时)`（`auto_manage_group/__init__.py:299`）。若只有网关一道，接管期间这段未验证代码可以直接禁言生产群成员——而这正是本护栏声称要防住的事。
  - 判据一句话——**凡不可撤销的动作，接管期间一律不交给未验证的代码**。
  - **输入**：节点侧闸门需要三样东西，都随它已经读的那份规则快照下发（`03 §6.3`，与 `resolve_route` 同源）——`canary_deny_plugins`、`failover_deny_reply_text`，以及"这条事件是不是接管流量"的标记（网关投递时写进事件体的 `_gateway.failover`，`§9.5`）。
  - **行为**：命中即不执行 handler。`message` 类回 `failover_deny_reply_text`；`notice` / `request` 类无法回话，静默跳过并计入 `node_failover_denied_total{plugin}`（`§8.1`）。定时任务走同一个闸门（`03 §6.6`）。
- **接管即通报**（替代原人工确认）：接管瞬间发告警，必须含 `git_sha` 差异、本次拒绝的插件清单、接管开始时间；`/env` 第一屏常驻显示"prod 故障中，全量由 dev 代管（已拒绝 N 个高危插件）"，直到默认节点恢复。
- **回切取自动 + 单向粘滞**：默认节点恢复且 `ready`、稳定 60s、且未 `locked` → 自动清除接管 override；若接管后短时间内它再次异常 → **保持接管**并把默认节点标 `locked`，不再自动回切，转人工。粘滞是必需的：每次来回切都让用户看到不同代码版本的行为，新代码若确有 bug 就是反复触发。
- **连带**：定时任务跟随同一个 override（节点读的是与网关同一份规则快照，`03 §6.3`），所以接管后 dev 接管这些群的推送；**被拒绝插件的定时任务同样跳过**（`03 §6.6`），已过点的任务不自动补跑。
- **接管期间的声明**：全量接管 = 灰度保护暂时失效（所有人都在跑未发布代码），这是本方案的已知代价，用拒绝清单封顶；因此**接管窗口内的运行数据不能当作灰度验收证据**——被拒绝的插件路径根本没被验证，用户的报障也会被归因到"prod 挂了"而不是"新代码有问题"。接管稳定运行是加分项，不替代正常灰度验收。

> **这是对原取向的反转**（原设计"默认不让 dev 接管"）。理由与代价记在决策 15（`00 §6`）：让系统在默认节点故障时完全沉默，比"能回话但可能在未验证代码上出错"更糟——群机器人的沉默会被当成机器人挂了/被封了。

### 5.5 恢复

- 默认人工：`/env resume dev` 或 WebUI 按钮 → 清除该节点 override（人工冻结一并清除）+ 写审计 + 广播。
- `auto_resume=true` 时：连续 6 次心跳正常 + `ready` + 稳定 60s 后自动清除，但仍记录 incident 与审计。
- 防抖：10 分钟内 `ready ↔ unhealthy` 翻转 ≥ 3 次 → `locked`，并**保持该节点的 override 不被自动清除**（异常节点是默认节点时即保持接管，是灰度节点时即保持引流关闭），直到人工 resume；人工 resume 后 5 分钟内禁止再次自动切回。

### 5.6 回滚与接管期间用户看到什么（简单回滚的代价处理）

三类"用户看不到功能"的原因不同，**执行点与文案都要分开，不要共用一句话**：

| 场景 | 执行点 | 文案键 | 默认文案（示例） |
|---|---|---|---|
| 回滚后 prod 缺 dev 的新命令（节点活着） | 节点（全局兜底话术 matcher，`03 §5`） | `degrade_reply_text` | 该功能正在灰度测试，暂时不可用 |
| 默认节点故障、接管期间命中拒绝清单（§5.4） | **网关**（命令类，投递前过滤）或**节点**（被动 matcher，`failover_guard`） | `failover_deny_reply_text` | 该功能在故障恢复期间暂停，请稍后再试 |
| 目标节点不可用且无接管者（单节点，或接管者也不可用） | **网关**（本地回，不经节点） | `no_target_reply_text` | 机器人暂时不可用，请稍后再试 |

- 第一类由**节点侧** matcher 判定，依据是 **manifest 并集与本地 manifest 的差集**（并集随快照下发，§2.10）。两个细节必须按这个来写：
  - **差集按触发词集合算**（type + 归一化后的 token / pattern），**不按插件名**——同一个命令可能被两个插件声明，按插件名算会误报"该功能不可用"，而实际上本地有插件能处理它。
  - **并集拿不到或版本过旧时静默**（不回话术），退化为今天的行为。**不猜**：误报"正在灰度测试"比沉默更糟。

  因此**回滚期间新旧命令都有一致话术**。
- 第二、三类的共同点是"没有节点能回答"，只能由**网关本地回**：网关不跑业务插件，但它持有文案（`02 §2.1` 的 `DEGRADE_REPLY_TEXT` 一类配置），回一句固定话术不需要插件能力。原设计只有第一类，"无路可走的流量回降级话术"在默认节点进程已死时其实发不出去——自动接管（§5.4）之后总有一个活着的节点在跑兜底 matcher，第一类才真正成立，而第二、三类始终要靠网关。
- 回滚或接管触发时，中控向受影响群的负责人（`ctl_settings` 配置）发一条说明，避免"功能突然消失"被当成 bug 上报。

## 6. 控制命令（网关本地执行）

### 6.1 为什么在网关

- 节点全挂也要能切回来。
- 避免"回滚命令被规则送到了出问题的节点"这类死锁。

**能离线执行的边界（必须知道）**：网关本地执行解决的是"**节点**全挂"，不解决"**中控**挂了"——规则与 override 的唯一写入点在中控（§6.4 的乐观锁、§2.3 的版本快照都要求单写者），网关也不持有中控库凭证（`02 §2.0`）。因此：

| 类别 | 命令 | 中控不可达时 |
|---|---|---|
| **读命令**（只用网关本地快照） | `/env`、`/env node`、`/env why`、`/env decisions`、`/env deploy --status` | **照常执行**，回执里标注快照时间 |
| **写命令**（必须经中控） | `/env route`、`/env rollback`、`/env freeze`、`/env resume`、`/env deploy`、`confirm` | **拒绝执行**，回 `CONTROL_UNREACHABLE_REPLY_TEXT`（网关本地文案，`02 §2.1`） |

一句话：**"节点全挂也能切回 prod"成立；"中控挂了也能切回"不成立**——后者是 `02 §10` 的已知边界，在这里显式写出，避免 §6.1 的理由被读成"网关能脱离控制面独立工作"。

**同一套边界也适用于权限面板**（`04 §4.7`）：读走节点本地快照、写必须经中控；中控不可达时写操作被拒并回同一句文案。两处不要各写一套说法。

### 6.2 命令清单

| 命令 | 作用 |
|---|---|
| `/env` | 总览：各节点状态与版本、当前 override、生效规则条数、最近 3 条事件 |
| `/env node` | 节点详情：版本/sha/心跳/插件加载失败列表/当前承载的规则 |
| `/env route dev --plugin email --groups 1,2 --note "..."` | 建 `group_plugin` 规则（多个群 = 多条规则，同一 revision） |
| `/env route dev --group 123 --note "..."` | 建 `group` 规则（整群引流） |
| `/env route dev --plugin email --note "..."` | 建 `plugin` 规则（全群灰度该插件） |
| `/env route prod --rule 42` | 把某条规则改回 prod（等价于删除规则，保留审计） |
| `/env rollback --last` | 回滚到上一个规则版本（整表快照） |
| `/env rollback --rule 42` | 删除单条规则 |
| `/env freeze dev --reason "..."` | 人工冻结：创建 manual override，dev 规则全部改投 prod |
| `/env resume dev` | 清除冻结/自动 override |
| `/env why --group 123 --text "邮件 查询"` | 决策解释：命中哪条规则、为什么、目标节点、是否被 override |
| `/env decisions --node dev --tail 20` | 该节点最近 20 条**决策日志**（含降级/失败） |
| `/env deploy node:dev [--tag <sha> / --latest] [--note "..."]` | 触发一次节点部署（幂等；同节点同时只允许一个在途）。**只对节点**——网关与中控的发布走带外（`02 §5.6`） |
| `/env deploy --status` | 最近一次部署的阶段与结果：`pull` → `start` → `selfcheck` → `ready`（取 `ctl_deployments.phase`，§2.8；接口见 `02 §5.7`） |
| `/env deploy node:dev --rollback` | 把该节点退到上一次成功部署的 sha（取 `ctl_deployments`） |

**读命令 vs 写命令**（决定中控不可达时能不能用，见 §6.1）：**读**——`/env`、`/env node`、`/env why`、`/env decisions`、`/env deploy --status`；**写**——其余全部（`route` / `rollback` / `freeze` / `resume` / `deploy` / `confirm`）。

**`/env rollback --last` 的范围（容易误读）**：它回滚的是 `ctl_rule_revisions.snapshot`，而该快照**只含全量规则数组**（§2.3）——**不含 override、不含 `ctl_settings`、不含 `ctl_jobs`**。所以"回到上一版"不会撤销一次冻结、也不会把某个配置键改回去：撤 override 用 `/env resume`，改配置走 WebUI / `ctl_settings`。另外回滚本身也是一次规则变更，会生成一个新版本（`action=rollback`），因此"回滚的回滚"就是再执行一次 `/env rollback --last`。

> 这条命令原名 `/env log`，改名与 `04` §4.5 的命令枚举同步。原因是一个真实存在的同名陷阱：它读的是**决策日志**（控制库里的路由事实），与节点的**运行日志**（异常栈、debug）是两回事。旧名字会让人以为这里能看到节点为什么报错，然后在"命令没报错、但也没有我要的东西"上白跑一轮——`02 §11` 里"用户说机器人没反应"那一条正是这种组合：`/env decisions` 看路由去了哪，节点的运行日志看它为什么没干活。运行日志的位置与采集策略见 §8.4，网关不代理它（要看栈就走文件/容器日志）。

**`/env deploy` 的语义**（P2 起替代 `/diting`；契约里已预留 `deploy` 子命令，`04` §4.5）：

- **只对节点**：网关与中控的发布必须带外（`02 §5.6`）——用一个可能已经挂掉的组件去发布它自己是不成立的。
- **tag 与回执**：`--tag` 缺省取该环境的 `-latest`，但**回执必须显示解析后的实际 sha**；`ctl_deployments` 记 sha 而不记 tag（否则"这次发的是什么"又不可知）。
- **确认与权限**：归入危险命令，与权限侧共用同一套 confirm token（引用回复 + 30s，`04` §4.5）；权限走运维名单。
- **幂等与并发**：同一节点同时只允许一个在途部署（`ctl:deploy_lock:<service>`），重复命令返回"已有在途部署 ID"而不是静默排队；执行器侧也要幂等（同 tag 已在跑就只做探活，不起新容器）。
- **失败不自动回退镜像**：部署失败（自检不过、起不来）停在该状态并明确报"部署失败"+ 建议动作，回退是显式命令 `--rollback`。理由与决策 2 一致：**流量回退是自动的（部署窗口已做到），代码回退永远是显式动作**，否则"谁把生产换回了旧版本"会变成无记录的事。
- **它与部署窗口的关系**：`/env deploy` 自己就是"声明式部署"，因此由它开部署窗口（`kind=deploy`，`02 §5.0`）；遗留的 `/diting` 经执行器执行，同样要开窗口——否则一次常规发布会被当成节点故障。
- **审计**：每次部署写 `ctl_audit`（谁、何时、哪个节点、from sha → to sha、结果）。

### 6.3 鉴权与审计

- **运维管理员名单由中控维护、网关只缓存**（已拍板：网关持有独立名单，不查业务权限库，且与操作组**完全独立**——**不做初始同步**）。中控通过 Redis 下发并带版本号（`ctl:ops_admins`），断连时网关用本地最后一次快照（`OPS_ADMINS_SNAPSHOT`），影子期可用 `OPS_ADMINS` 内联兜底。
- **三条护栏**（"完全独立"的代价，P1.2 起生效，详见 `04-权限与授权设计.md` §4.10）：① 中控写入必须拒绝清空名单，网关启动时名单为空必须告警——空名单 = 运维通道彻底关闭，且**没有权限库可兜底**；② 中控侧持久化落 `ctl_settings` 一条键（网关的快照文件只是缓存，不是真相）；③ 提供不依赖 QQ 面板与 WebUI 的离线恢复路径。
- **与业务权限的边界**：运维名单只管基础设施动作（`/env`、`/env deploy`），业务命令的授权仍走权限库；两边不互相授权，名单变更进 `ctl_audit`（业务权限变更进 `permission_audit`，两张表分开记）。
- 每条命令：先鉴权 → 执行 → 回执 → 同步推送到管理群。**审计的写入路径**：网关不持有中控库凭证（`02 §2.0`），因此写命令执行后由网关把 `{actor, action, target, before/after, trace_id, 命令消息 id}` **POST 给中控**，由中控落 `ctl_audit`。**不存在"执行了但审计没写"的窗口**——写命令本来就要求中控可达（§6.1），中控不可达时它根本不会被执行，不需要"本地缓冲 + 事后补记"这类机制。读命令不进 `ctl_audit`（它是查询不是变更），只进决策日志（§2.9 的 `ctl:decisions`）。
- 危险的批量操作（`/env route dev --plugin` 不带群、`/env freeze`）在群里要求二次确认（引用回复确认，30s 内有效）。**这套二次确认与权限侧的"群绑定到操作组"等危险操作共用同一个 confirm token 机制**（`ctl:confirm:*`，见 `04` §4.5 第 5 条）；对应地，`packages/contracts` 的命令契约需要在 P1.2 新增 `confirm` 子命令（该契约随 contracts 包一起落地，不做存量兼容）。

### 6.4 并发与幂等

- 规则写入走中控单写者 + 乐观锁（版本号），并发冲突返回"规则已被他人修改，请刷新后重试"。
- 所有写操作携带幂等键（命令消息 id），重复投递不产生重复规则。

## 7. 生效预览（WebUI 与 API 共用）

`POST /ctl/routes/preview` 请求 `{group_id, text}`，返回与线上完全相同的 `Decision`（走同一份代码路径），包括：命中的规则 id 与层级、是否被 override、是否因接管而改投（`failover`）、是否冲突、最终节点。

WebUI 的规则编辑器实时调用它——**"这条规则加上去，哪些流量会变"必须可预演**，否则线上灰度全靠猜。

## 8. 可观测性

### 8.1 指标（Prometheus，网关与中控各自暴露 `/metrics`）

| 指标 | 类型 | 用途 |
|---|---|---|
| `gateway_events_total{node,result}` | counter | 各节点承载事件量；`result` = `delivered` / `degraded` / `buffered` / `dropped`（丢弃原因细分见 `gateway_events_dropped_total`，§9.5） |
| `gateway_route_decision_total{node,rule_id}` | counter | 每条规则实际生效的流量 |
| `gateway_route_conflict_total` | counter | 冲突规则（应为 0，长期非 0 说明规则写错了） |
| `gateway_napcat_link_up` | gauge | 上行链路状态（§9.2）。**不要**用它直接触发节点连接断开——中间隔着去抖窗口 |
| `gateway_node_conn_state{node}` | gauge | 节点连接状态机（§9.3）：`connecting` / `handshaking` / `online` / `draining` |
| `gateway_node_conn_replaced_total{node}` | counter | 新连接顶掉旧连接的次数（§9.3）。滚动更新时看到 1 次属正常；短时间内连续多次说明重启循环或同机起了两个同 `NODE_NAME` 的实例 |
| `gateway_event_buffer_depth{node}` | gauge | 每节点事件缓冲深度（§9.5），接近 `NODE_BUFFER_MAX_EVENTS` 即预警 |
| `gateway_events_dropped_total{node,reason}` | counter | 丢弃计数，`reason` 取 §9.5 的词表 |
| `gateway_api_proxy_inflight` | gauge | 在途 API 调用数（§9.6），长期偏高说明上游 API 变慢 |
| `gateway_api_proxy_orphan_total` | counter | 回包无法归位（`echo` 查不到映射）的次数，**应为 0** |
| `gateway_event_sink_dropped_total{reason}` | counter | 事件流水在网关侧被丢弃（发送队列满 / 中控不可达，§8.5） |
| `ctl_event_persist_lag_seconds` | gauge | 事件流水从终结到落库的滞后（中控侧，§8.5） |
| `node_heartbeat_age_seconds{node}` | gauge | 心跳年龄 |
| `node_events_handled_total{node,source}` | counter | 节点处理的事件数，`source` = `live` / `inject`。`03 §9` 的应急注入必须单独可见，否则它会污染业务统计 |
| `node_loop_lag_ms{node}` | gauge | 事件循环延迟 P95，节点阻塞的先兆（§5.2） |
| `control_override_active{node}` | gauge | 当前有几个节点被改投 |
| `control_incidents_open` | gauge | 未处理异常数 |
| `gateway_failover_active{from,to}` | gauge | 接管是否生效：默认节点故障后全量由接管者代管时为 1（§5.4） |
| `gateway_failover_denied_total{plugin}` | counter | 接管期间被拒绝清单拦下、只回了暂停话术的事件数（§5.4、§4.5）。只统计**网关归类得到**的命令类 |
| `node_failover_denied_total{plugin}` | counter | 接管期间**节点侧** `failover_guard` 拦下的事件数（§5.4）。与上一条分开看：这条是被动 matcher 的**唯一可见性来源**；两条都长期为 0 才说明名单真的没命中过（若命令类命中而上一条为 0，说明节点快照没更新） |
| `gateway_degrade_reply_total` | counter | 降级话术触发次数（回滚的"体感成本"） |
| `gateway_rate_limited_total{group_id}` | counter | 出站 API 调用因限流被**丢弃**的次数（§11.2）。与上一条分开看：那个是回滚的体感成本，这个是刷屏的体感成本 |
| `gateway_manifest_opaque_matchers{node}` | gauge | 未处理的 **message 类** opaque matcher 数（>0 表示该节点的插件级灰度不完整，§4.3） |
| `node_job_runs_total{node,job,result}` | counter | 定时任务执行次数；`result` = `executed` / `skipped` / `lease_lost` / `error` |
| `node_job_lease_lost_total{node,job}` | counter | 未拿到租约（另一节点在执行，或 Redis 不可用，`03 §6.3`） |
| `node_slow_handler_total{plugin}` | counter | handler 耗时超过 `slow_handler_warn_ms` 的次数（`02 §1.3`） |
| `alert_sent_total{level,channel,result}` | counter | 告警出口降级链的成效（§8.2）：`channel` = `gateway` / `napcat_http` / `smtp`，`result` = `sent` / `failed`。**出现 `smtp` 就说明 QQ 通道当时不可用**，这是排查"为什么我没收到群消息告警"的第一眼 |
| `alert_active{level}` | gauge | 当前活跃告警数（与 `ctl_incidents.alert_state=active` 同源）；长期不降说明抑制规则没起作用 |

### 8.2 监管与告警（通道、生产者、收件人、触发清单、抑制）

**规定：只要还能发出 QQ 消息，就不用邮件。** 这改变了"带外"的定义——原设计里带外等于"离开 QQ"（只剩 SMTP），而 NapCat 还活着时没有道理绕开它；现在的带外是"**离开出故障的那个组件**"。网关挂了而 NapCat 还在，就直接从旁路 HTTP 控制口发到群；只有 QQ 这条路本身不可用（NapCat 挂、账号被禁言或风控、发送拿不到回执）才退到邮件。

#### 出口：一条降级链，不是每条告警各自挑通道

```
L1  正常通道    中控 → 网关 → 上行链路 → NapCat → 群     网关自己的告警用自己的上行链路直接发
L2  QQ 旁路     任何组件 → diting-notify → NapCat HTTP 控制口(6097) → 群
L3  邮件         diting-notify → SMTP
L0  外部探针     另一台机器探 /healthz（只覆盖整机与网络故障）
```

**降级判据是回执，不是"请求已发出"**：NapCat 返回 `retcode=0` 且有 `message_id` 才算送达，否则降到下一级。这条不能省——NapCat 进程活着但账号被禁言或被风控时，请求会被收下而不进群，"以为发了"是这里最难查的失败。整机或网络不可用是唯一覆盖不到的：SMTP 客户端与 NapCat 在同一台主机上，只有 L0 能发现（可选，一个外部定时探测）。

#### 生产者：谁先知道，谁负责发

原设计是"中控生成 → 网关投递"，于是**中控挂或网关挂都会让告警整体沉默**，而这两种恰恰最需要告警。改为按检测者下沉：

| 生产者 | 负责的判据 | 出口 |
|---|---|---|
| **网关** | 上行链路状态、每节点 WS 连接、事件缓冲与丢弃、echo 孤儿、事件流水上报失败（= 中控不可达）、启动时运维名单为空 | L1（自己的上行链路，不需要任何新凭证）→ L2 → L3 |
| **中控** | 健康状态机（`suspect` / `unhealthy` / `locked`）、接管与回切、部署窗口与部署结果、规则与排程对账、备份与迁移、控制库自身写入 | L1 → L2 → L3 |
| **节点** | **不发告警**：只上报事实（自检结果、`loop_lag_ms_p95`、慢 handler、manifest、排程对账输入） | ——（不持有任何出口凭证） |
| **宿主 watchdog** | 两个服务的 `/healthz`、容器重启循环、磁盘水位、整机可达性 | L2（先）→ L3 |

- 节点的异常由**就近的检测者**负责：链路级由网关秒级看到（不必等中控的 30s 心跳），语义级由中控判定。"节点不持有出口凭证"是一条纪律——跑业务代码的容器最不该握着能直接对外发消息的令牌。
- **网关 → 中控心跳**（`ctl_nodes` 里 `kind=gateway` 那一行）是这套判据的载体，内容用它本来就有的量：`{version, git_sha, uptime, napcat_link_up, node_conn_states, buffer_depth, inflight_calls, ts}`。只有网关知道 NapCat 死活，上行断链由它带上来；它自己不可达时，判据换成"中控的这条心跳超时"，反向由中控发。

#### 出口组件 `diting-notify`（宿主侧，凭证的唯一持有者）

- 唯一持有**告警出口**的凭证（宿主本地仓，`02 §2.5`）：**NapCat HTTP 令牌**与**告警专用的 SMTP 账号**——它与业务邮件那套（节点上的 `email_sender` / `email_delivery`，发给订阅者）分开，告警不该受业务邮件的配额与故障影响。中控、网关、watchdog 都只调它，它按 L1（可选）→ L2 → L3 依次尝试并按回执判成败——"哪条路成功"只有它知道。
- 网关自己发告警走的是**自己的上行链路**（不经过 `diting-notify`），这时必须用**独立命名空间的 echo**：节点进程的 echo 计数器都从 1 开始（§9.6），混用会污染 `gateway_api_proxy_orphan_total`（该指标定义为恒为 0）。
- 它同时是告警**状态**的兜底存放处（`dedup_key` 状态表）：中控挂了的时候，中控自己的表写不进去。

#### 级别与收件人

| 级别 | 含义 | 收件人 |
|---|---|---|
| `critical` | 用户可见行为受影响，或必须有人动手 | 管理群（`ctl_settings.alert_group_ids`）+ @ 告警名单；群不可达 → 邮件（`ctl_settings.alert_emails`） |
| `warning` | 先兆，需要有人看，不必立刻动手 | 管理群，不 @；群不可达 → 邮件 |
| `info` | 预期内或已自动完成的动作 | 管理群（可配置为只进 WebUI 与日志） |

- **告警目标只有一个来源：`ctl_settings`**（群号 / @ 名单 / 收件人）。按决策 14 的判定规则（要重启 → env，不要 → 中控库），改告警群不该重启中控，所以它不进 env。**迁移**：仓库里现有的 `DITING_DEPLOY_NOTIFY_GROUP`（部署事件镜像群，`env.template:232`，默认 `0`=关闭）若已启用，其值并入 `alert_group_ids`；部署结果的告警届时由中控的部署编排覆盖（`02 §5.7`），不必再保留"镜像"语义。
- **@ 名单不复用 `ops_admins`**：那是权限数据（能敲 `/env`），"告诉谁"与"允许谁做"是两件事，混用会让"加个运维"顺带改变告警行为。新增 `ctl_settings.alert_mention_qqs`，默认空（空即不 @）。
- **对外告知不算告警**：回滚/接管时给受影响群负责人的说明（§5.6）、用户看到的降级话术，都不进告警通道、不占 `ctl_incidents`。

**引导顺序（第一次部署时"第一条告警发给谁"）**：告警目标只有一个来源（`ctl_settings`），而 `ctl_settings` 由中控创建——所以必须按这个顺序落地，否则会卡在"目标还没配，所以告警发不出去；没收到告警，所以不知道要配目标"：

1. **P1.0 建库后**：中控首次启动时，若 `ctl_settings.alert_group_ids` / `alert_emails` 为空，用中控 env 的 `ALERT_GROUP_IDS_SEED` / `ALERT_EMAILS_SEED` 写入一次（`02 §2.2`）；此后这两个 seed 被忽略，**永不覆盖**已有值。
2. **两处都为空**（seed 没填、`ctl_settings` 也没写）：中控**照常启动**——消息通路与路由不受影响——但 ① 经 `diting-notify` 发一条 critical（走 `ALERT_FALLBACK_EMAIL`，`02 §2.5`），② WebUI 顶部常驻横幅"告警目标未配置"。**不做 fail-fast**：拒绝启动会把一个纯配置问题升级成管理面不可用，而"静默"正是本节要消灭的失败模式。
3. **运维在 WebUI 写入目标后**：横幅消失，告警进入正常路径；变更进 `ctl_audit`。

#### 状态型告警，不是事件流

每条告警是一个 `(主体, 类型)` 的**状态**：进入时报一次、恢复时报一次、持续期间不重复（`ctl_settings.alert_remind_minutes`，0 = 不提醒）。`dedup_key` 形如 `node:dev:unhealthy` / `gateway:napcat_link` / `control:self` / `redis:lease`，与 `ctl_incidents.dedup_key` 同值。

状态由生产者维护、落 `ctl_incidents`（`alert_state` = `active` / `resolved`）；中控不可达时由 `diting-notify` 的宿主状态表暂存，中控恢复后**只对账补记、不重报**。这也补上了原来 warning 级告警"只有日志、没有档案"的缺口。

#### 触发清单

**网关侧（链路与投递）**

| 触发 | 阈值 | 级别 |

#### 抑制规则（不写出来就会被吵到关掉）

| 抑制 | 效果 |
|---|---|
| 计划内部署窗口（TTL 5 分钟） | 该节点不进 `suspect` / `unhealthy`、不触发接管与回滚，告警降级为 info；窗口内状态变化不计入 `locked` 抖动统计（`02 §5.0`） |
| `ctl_nodes.enabled=0` | 视为计划内下线，不产生故障告警（§2.1） |
| 链路去抖 `NAPCAT_LINK_DEBOUNCE_SECONDS` | `up→down` 后 10s 内恢复不报（§9.2） |
| **启动静默期** | 任何服务启动后 60s 内的"不健康"不告警，先建立基线（`02 §5.6` 中控那条"自我豁免"是它的特例，统一成通则） |
| **父子抑制** | NapCat 断链时不再同时报两个节点离线（它们是它的结果）；中控不可达时不再报它下面的规则同步失败 |
| **同源合并** | `链路断开 → unhealthy → 全量接管` 是同一个 incident 的三个阶段，共用一个 `incident_id`，群里只看到一条进入 + 一条恢复 |
| `locked` | 枢纽状态：锁定后不再反复报，等人工 resume（§5.5） |

#### 告警正文与运维动作

每条只带三样：**服务名与主体**、**最后一次成功心跳时间**、**关键指标值 + `/healthz` 原文**（不含任何密钥）。收到之后的动作是"打开这条消息 + 敲 `/env`"，而不是去翻日志——与 §8.3 的 `text_digest` 是同一条纪律：告警正文里不出现群聊原文，需要时用 `trace_id` 回查。

> **为什么不再把"带外"定义为邮件**：三个组件各有一条不同的出口（网关用上行链路、中控用旁路、watchdog 用旁路），任何单点故障组合都有路可走；邮件退化为"QQ 通道自身不可用"时的最后一道，而不是默认兜底。

### 8.3 决策日志字段

`trace_id, ts, group_id, user_id, text_digest, plugin, rule_id, layer, node, override, conflict, latency_ms, delivery_result`。
`text_digest` 存哈希而非原文，避免把群聊内容长期留存在控制面；排障需要原文时由管理员在 WebUI 上临时开启"调试采样"（保留 1 小时）。**这是控制面的纪律，不是全局纪律**——业务库那边的 `event_logs.detail` 与老表一样存事件原文，两者的分工见 §8.5 的"介质边界"。
`delivery_result` 取 §9.5 的状态值（`delivered` / `buffered` / `dropped:<reason>`）；经缓冲后投递的记录 `buffered_ms` 与 `revised`（§9.5）。

### 8.4 运行日志与采集

**分层，不集中。** 三类东西不要混为一谈：**事实类**——决策日志（§8.3）与事件流水（§8.5 的 `event_logs`，历史档案是 `messages_event_logs`）——已经在库里，跨节点可查、可回放对账，保留期由业务定；**噪声类**——异常栈、第三方库 debug、启动信息——分服务写本地文件，靠 `trace_id` 临时串起来；**指标**走各自 `/metrics`（§8.1）。集中式日志栈现在不引入，触发条件见本节末。

四条现在就定死的规则：

1. **每个服务一个独立日志目录**：`logs/gateway/`、`logs/control/`、`logs/node-<实例名>/`（实例名就是决策日志里的 `node` 字段）。隔离必须由**部署单元**保证（每服务独立工作目录或独立卷），同时把服务名做成 `LOG_FILE_PATH` 的默认值（落在 `packages/common/logging`），不能只靠人工去改一个相对路径的配置值。现状是所有环境同一个 `logs/nonebot.log`（`.env.prod:194`、`.env.dev:184`、`.env.local:189`、`.env.docker:188`、`env.template:123`）：两个克隆在不同目录所以今天没出事，但网关 + 中控 + 两节点同机后就会撞上——loguru 没有跨进程锁，`rotation="00:00"` 会变成竞争，Linux 上先轮转的进程把文件改名、另一个继续写那个已改名的 inode（当天的日志进了归档，新文件只剩一个进程的输出），Windows 上 rename 一个打开中的文件直接失败。这些路径与其他配置项怎么存放（分层、键归属、多环境共存）见 `02-部署与运维.md` §2.0。
2. **文件 sink 写 JSON 行**（`serialize=True`），固定字段 `service` / `node` / `version` / `plugin` / `trace_id` / `group_id` / `event_id`（与 `03 §5` 的注入字段一致）；控制台保留人类可读格式。现状是文件 sink 也复用 `default_format`（`bot.py:45`），而它是 `MM-DD HH:mm:ss [LEVEL] name | message`（`nonebot/log.py:78-84`）——没有年份、没有时区、没有服务名，跨年与跨服务对账都有歧义，机器解析只能靠正则。字段 `service` 不能省：目录隔离在文件被拷走、被拼接、被打包发给别人之后就失效了。
3. **级别：prod 节点、网关、中控一律 `INFO`**，`DEBUG` 只在 `local` 或排障时显式开启并限时。依据：`nonebot/__init__.py:316-318` 在 DEBUG 级打印 `Loaded Config: {model_dump(config)}`，实测 `logs/nonebot.log:3` 里明文躺着 `onebot_access_token`、`bot_db_password`、`new_oj_redis_password`、`webui_jwt_secret` 等全部密钥——而所有环境今天是 `LOG_LEVEL=DEBUG` + `LOG_FILE_LEVEL=DEBUG`（`.env.prod:1,197`）。"不把敏感原文长期留存"与 §8.3 的 `text_digest` 是同一条纪律。
4. **保留期按证据类型分**：运行日志 7 天（对齐现状）；决策日志与消息落库在库里，**不随日志轮转**。两类证据的寿命本来就不同，不要互相抄。

容器 stdout 那一份副本由 docker 的 json-file 驱动接管，默认**不轮转**（`docker-compose.yml` 没有 `logging:` 段），DEBUG 下会无限增长——上限配置见 `02 §1.1`。

**什么时候才真的上集中式**：满足任意一条再考虑——部署到两台以上机器；"按 `trace_id` 跨服务看一条链路"成为日常操作；运行日志超过 1 GB/天；需要让非运维的人自己查。届时选 **Loki + Alloy/Promtail + Grafana**，不是 ELK：`nonebot_plugin_prometheus` 已经在用（`pyproject.toml:14`），Grafana 迟早要来，日志与指标放同一面板才能按 `node` / `trace_id` 联动，而 Loki 只需要 `service` / `node` / `level` 三个索引标签。因为规则 2 已经把文件做成 JSON 行，到那天接入成本接近零——这就是"现在不集中、但按集中式准备"。

### 8.5 事件流水（`event_logs`）与落库归属

**定位**：§8.3 的决策日志记"这条事件被路由到哪里、结果如何"；事件流水记"这条事件本身是什么"。它替代并扩展 `messages_event_logs`，覆盖**除 `meta_event.heartbeat` 以外的全部上报事件**，包括机器人自己发送的消息。

**归属：网关采集，中控落库。** 采集必须在网关——只有它看得全：节点只看到路由给它的那部分，而被丢弃的事件（`no_target` / `buffer_overflow` / `buffer_expired` / `revised_target_unavailable`）在任何节点上都不存在，今天在库里是纯空白。落库不进网关——`00 §4` 的边界写着"网关不写业务库"，`02 §2.1` 的网关 env 里也确实没有任何 DB 凭证，而中控本来就是业务库的单一写入者（`02 §2.2`）。

链路：网关在事件**终结时**（`delivered` / `dropped` / `degraded`）把 `{事件原文, trace_id, node, delivery_result}` 批量推给中控，中控批量插入。**投递永不等日志**：队列满丢最旧并计入 `gateway_event_sink_dropped_total{reason}`，中控侧滞后看 `ctl_event_persist_lag_seconds`（§8.1）。选终结时而不是入站时，是因为 `delivery_result` 到那时才已知——缓冲窗口 ≤10s，所以流水最多滞后 10s；网关崩溃时在途事件丢失，而那些事件本来也没投递出去，不影响行为。

**表结构**（业务库；命名沿用业务库习惯）：

| 列 | 说明 |
|---|---|
| `event_id` | 主键；网关入站时分配，重投递不产生第二行 |
| `trace_id` | 与决策日志同值，两张表可按它 join |
| `ts` / `received_at` | 事件自带时间戳 / 网关收到时刻 |
| `post_type` | `message` / `message_sent` / `notice` / `request` / `meta_event` |
| `sub_type` | `sub_type` / `notice_type` / `request_type` / `meta_event_type` 四者归一到这一列 |
| `self_id` / `group_id` / `user_id` | 可空（notice 与 request 未必都带） |
| `node` / `delivery_result` | 投给了谁、结果如何（词表同 §9.5） |
| `detail` | 事件原文 JSON |

索引：`(received_at)`、`(group_id, received_at)`、`(post_type, received_at)`、`(trace_id)`。

**meta 事件**：心跳不写（量最大、信息最少）；`lifecycle` / `enable` / `disable` 与未知 `meta_event_type` **要写**——它们是排障证据。这与 §9.7 的"网关吸收 meta"不冲突：吸收说的是不投递给节点，不是不落库。

**自己发送的消息（`message_sent`）有两个前置**，缺一个就永远记不到：

1. NapCat 侧打开 `websocketClients[].reportSelfMessage`（按连接开关，仓库里目前没有任何一处启用）。网关只有一个连接，改一处即可（`02 §3` 的示例配置已是 `true`）。
2. 网关把 `post_type=message_sent` 显式归为**只记录、不路由**：它匹配不到任何 matcher，不特殊处理就会变成一批 `no_target` 噪音与告警。

> **原设计的第三条前置（适配器侧注册 `MessageSentEvent`）已随"网关自实现协议"取消**（`02 §1.3`）：网关按 `post_type` 白名单处理原始 JSON，不需要适配器模型；而节点永远看不到这类帧（只记录、不路由），所以也没有第二处需要注册。附带记录，供将来若有服务复用适配器时参考：NoneBot 2.4.4 的 V11 适配器里**没有 `message_sent`**（全包 grep 为空；`MessageEvent.post_type: Literal["message"]`，`event.py:145`），未知 `post_type` 经 `json_to_event` 的 `for/else` 落到基类 `Event`（`adapter.py:441-449`），`message_id` / `raw_message` / `sender` 全进 `model_extra`——要用它得先 `Adapter.add_custom_model`（`adapter.py:405-412`）。

**权威性**：机器人自己发过什么，**以 `event_logs` 为准**。`qq_robot_messages`（`ack_manager`）继续服务回执与提醒，两者用途不同、不必合并；统计"机器人发了什么"时只认事件流水。

**与老表的关系**：`messages_event_logs` 冻结为历史档案（"时光机"），**不清理、不迁移、不删**。切换顺序必须是：

1. **双写期**（P1.1 接管入口起；P1.0 影子期只写决策日志，不写流水——那时还没有投递语义）：`logging_info` 照旧写老表，新链路写 `event_logs`——两张表互不冲突，不会出现 `IntegrityError`（`src/plugins/logging_info/message_dao.py:68-70` 把该分支注释掉了，落进 `except` 就是错误日志刷屏）。
2. **消费者改指新表**：`src/api/logs.py`（WebUI 消息日志页）、`src/api/groups.py`（群活跃度聚合——它现在只按 `group_id IS NOT NULL` 过滤，**必须补 `post_type='message'`**，否则 notice 会让统计静默虚高）、`llm_scribe`（现在按 `message_type='group'` 过滤，同样要补 post_type）。
3. **删除 `logging_info`**（遵循 `03 §10` 的删除纪律：新实现上线 prod 稳定 7 天后）。老表从此不再增长。需要跨两个时代连续查询时做一个 `UNION ALL` 视图，**不要回填**。

**介质边界（先看这一条，否则会以为它与 §8.3 的 `text_digest` 纪律矛盾）**：**控制面不留原文，业务库存原文**——这是分工，不是两条互相打架的纪律。

| | 控制面（`diting_ctl`） | 业务库 |
|---|---|---|
| 表 | `ctl_decisions`（§2.9） | `event_logs`（历史档案：`messages_event_logs`） |
| 存什么 | 路由事实 + `text_digest`（哈希） | 事件原文（`detail`） |
| 为什么 | 它是"这条事件去了哪、结果如何"的**索引**，排障靠 `trace_id` 回查原文，不需要自己再留一份群聊内容 | 它本来就是群聊记录的宿主——老表一直存原文，`event_logs` 只是延续；统计、时光机、内容检索都依赖原文 |
| 保留期 | 30 天（四类必落） | 见下 |

**保留期（已定）**：

- `messages_event_logs`：**不清理**（冻结为历史档案，已拍板）。
- `event_logs`：**默认不自动删除**，只监控增速；**以 12 个月为人工复核点**，届时按真实增速二选一——按 `received_at` 做**月度分区**，或滚动删除。复核动作与结论写 `ctl_audit`。
  - **为什么默认不删**：它与老表是同一类证据（还多含被丢弃、被降级事件的记录），自动删除会让"事后回溯一次灰度事故"变成不可能。存储成本先量化、再决定，比先删了再后悔划算。
  - **分区纪律**：**只加分区、不动列**（与 `02 §6.1` 的 expand 一致），因此分区在任何时刻都能做，不需要停机、不影响灰度窗口。
  - **复核点要看的第一个数字**：覆盖全事件后行数约为老表的 1.5~3 倍（notice 类比消息更密：戳一戳、撤回、名片、成员进退、文件上传、精华、运气王等）。

## 9. 网关状态机（连接、投递与 API 代理）

§3 定义了"这条事件该去哪个节点"，但没有定义网关**自己**的状态：连接怎么建、什么时候才算就绪、投递失败算什么、节点发出的 API 调用怎么把回包送回正确的人。本节把这些逐条定死。

**网关自实现 OneBot V11 协议**（不引入 NoneBot 作为依赖，选型与理由见 `02 §1.3`）：它同时是 NapCat 反向连接与各节点正向连接的**服务端**，因此本节的状态机、echo 映射、事件缓冲与失败结算都在网关进程内实现——这是"排他投递 + 多路复用"的必要条件。

本节的所有判据都来自 NoneBot 2.4.4 适配器与驱动器的既有行为（已逐处核对源码），不是可以自由设计的部分——**这些行为约束的是节点侧**：网关发出的每一条帧、每一个字段，都要让节点侧那个标准 NoneBot 适配器按预期动作，否则节点会以"静默丢弃"的方式失败。

### 9.1 三条通道

| 通道 | 方向 | 协议 | 谁发起 | 承载 |
|---|---|---|---|---|
| 上行链路 | NapCat → 网关 | reverse-WS（`/onebot/v11/ws`），**独占** | NapCat（`websocketClients` 数组里的一项） | 事件入站、API 调用出站 |
| 下行连接 | 节点 → 网关 | forward-WS（`/onebot/v11/node?node=<name>`），每节点一条 | 节点（`ONEBOT_V11_WS_URLS`） | 事件下发、API 调用上行与回包下发 |
| 旁路 | 节点 → NapCat | HTTP 控制 API（`QQ_CONTROL_PORT`，默认 6097） | 节点 | 两个插件的手工转发调用，**已知例外**，见 §9.8 |

**注意 forward-WS 是新增能力**：今天全环境是 reverse-WS（`DRIVER=~fastapi`，仓库内没有任何 `ONEBOT_V11_WS_URLS` 配置），节点从不主动外连。这一点在 `02 §4.1` 的 P1.0 里要先用临时节点验证。

### 9.2 上行链路状态

`napcat_link ∈ {down, up}`，网关进程内状态，不落库。

| 迁移 | 判据 |
|---|---|
| `down → up` | WS 握手成功（校验 `ONEBOT_ACCESS_TOKEN`）+ 读到 `X-Self-ID` 头 + 收到 NapCat 的 `lifecycle` / `sub_type=connect` |
| `up → down` | WS 关闭或读取异常 |

- `X-Self-ID` 是 OneBot v11 反向连接的固定头，网关**自己实现**这项校验（它不跑 NoneBot；节点侧适配器在 `adapter.py:247-254` 对入站连接做同样的强制校验，缺失即 `close(1008)`）。网关据此在**收到任何事件之前**就能确定 `self_id`，这是 §9.3 合成 connect 的输入之一。
- `heartbeat`（`heartInterval: 30000`，即 30s 一次）只用于刷新"上游新鲜度"，**不作为状态迁移判据**——链路的权威信号是 WS 本身。心跳丢失只说明 QQ 侧可能不健康，不代表连接断了。
- **去抖**：`up → down` 之后若在 `NAPCAT_LINK_DEBOUNCE_SECONDS`（默认 10s）内恢复，视为抖动，不执行 §9.4；超过阈值才执行。

### 9.3 节点连接状态

每节点一条，网关进程内状态，由 `gateway_node_conn_state{node}` 暴露。

```
connecting ──WS 接受 + token/node 校验──▶ handshaking ──合成 lifecycle/connect──▶ online
                                              │                                    │
                              上游 up 之前一直停在这里                             │
                                                                                   │
                        draining ◀── 上游断链 / 节点 enabled=0 / 网关重启 ─────────┘
```

| 状态 | 含义 | 是否投递 |
|---|---|---|
| `connecting` | WS 未建立（节点未启动，或正在 3s 重连循环里） | 否，进缓冲 |
| `handshaking` | WS 已建立，但**尚未**合成 `lifecycle/connect` | 否，进缓冲 |
| `online` | 已合成 connect，可投递 | 是 |
| `draining` | 准备断开（关闭 WS，节点 3s 后重连） | 否，进缓冲 |

**同名节点的重复连接：新连接顶掉旧连接（已拍板）。** 滚动更新时新容器先连上、旧容器尚未退出是常态，必须定死这种情形——否则会出现两条同 `node` 的连接，投递目标不确定（可能投给正在退出的容器），两套 echo 映射互相干扰。

| 步骤 | 行为 |
|---|---|
| 新连接通过 token / node 校验后，发现该 `node` 已有连接 | 旧连接进 `draining`：关闭 WS，在途 API 调用按 §9.6 结算为失败（`{"status":"failed","retcode":-1,"echo":<原 echo>}`），映射表项立即回收 |
| 新连接 | 进入 `handshaking`，等上游就绪后合成 `lifecycle/connect`（前置条件不变，见下） |
| 计数与可见性 | `gateway_node_conn_replaced_total{node}`（§8.1）；1 分钟内重复顶替 ≥3 次 → warning（疑似重启循环，或同机起了两个同 `NODE_NAME` 的实例） |

- **为什么是"顶掉"而不是"拒绝"**：滚动更新时旧容器可能仍在优雅退出，拒绝新连接会让新容器反复重试并停在 `connecting`（`RECONNECT_INTERVAL = 3.0` 的循环里），可用性从"谁活着"变成"谁先连上"；顶掉则让**最新建立的连接**胜出，与"节点无状态、可随时删掉重建"（`00` §4）一致。
- **与配置层身份冲突告警的分工**：`02 §2.4` 的 `NODE_NAME` + 配置指纹冲突告警管的是"两个环境读了错配置"，管不到连接层；这里管连接层，管不到配置。**两者都要有**。
- **不复用旧连接**：旧连接的节点进程可能已在退出，它的内存快照与事件缓冲都已不可信。`adapter.py:349-364` 里，节点在收到 `lifecycle` 且 `sub_type=connect` 之前不会创建 Bot、不会设定 `self_id`，**并且此前到达的一切事件都被静默丢弃，连一行日志都没有**。所以"节点 WS 一连上就投递"不是"可能丢几条"，而是"全部丢，且不可观测"。合成 connect 因此是协议要求，不是形式。

**合成 connect 的前置条件（已拍板）：`napcat_link == up` 且已知 `self_id`。**

- 上游不可用时节点停在 `handshaking`，不合成——避免制造"账号在线但 API 全失败"的假象。
- 这条护栏针对的是一个真实缺陷路径：`group_file_manager/hooks.py:53-57` 在 connect 时调 `get_group_list()`，失败只记一行 error、把列表置空后**继续**同步名册与全量爬取。若在上游不可用时合成 connect，群名册会空转，而且没有告警。
- `self_id` 取自 §9.2 的 `X-Self-ID` 头（或首个事件的 `self_id` 字段）。两个节点拿到的是同一个号（dev / prod 同号，`00-总览.md` §1.2）。

**connect 期的副作用清单（实测，重放即重跑）**：

| 位置 | 连接建立时做什么 |
|---|---|
| `src/plugins/group_file_manager/hooks.py:47-104` | 全量群列表同步入库（新群插入、群名更新）→ FK 迁移 → **全量爬取所有群的历史文件** → 注册 `daily_crawl`，并把当前 bot 实例作为参数捕获 |
| `src/plugins/group_card_changer/__init__.py:100-107` | 逐群 `set_group_card`（群与群之间 sleep 1s） |
| `src/plugins/rate_limiter_middleware/middleware.py:357-360` | 给该 Bot 实例打上 `bot.send` / `bot.call_api` 的限速补丁 |

因此**合成 connect 的时机同时决定了这三件事的发生时机**。重连抖动会被放大成全量爬取，这是 §9.4 必须去抖的原因。

### 9.4 上游断链：断开节点连接（已拍板）

`up → down` 持续超过 `NAPCAT_LINK_DEBOUNCE_SECONDS` 之后：

1. 所有节点连接进入 `draining` 并关闭 WS；在途 API 调用按 §9.6 结算。
2. 节点 3s 后重连（`RECONNECT_INTERVAL = 3.0`，`adapter.py:47`），回到 `handshaking`，事件开始进缓冲。
3. 上游恢复后，网关在节点重连时**重新合成** `lifecycle/connect`——于是 §9.3 的三处副作用各重跑一次。

**为什么断开，而不是保持节点连接**：今天节点的 bot 生命周期完全由"NapCat 能否连上"决定，而上面那三处副作用事实上承担了自愈职责——群名册靠它补齐（`daily_crawl` 只爬库里已有的群，**不新增群**）、群名片靠它在 NapCat 重登后重设、`daily_crawl` 捕获的 bot 实例靠它刷新。若保持连接不断开，这四项会退化为"仅进程启动时一次"，其中群名册会**静默变旧**（表现为：NapCat 掉线期间新入的群，机器人后续在群里不工作）。

**代价（明确接受）**：NapCat 反复抖动会让两端反复跑全量爬取。今天的直连模式下同样如此（NapCat 一断，两个节点各自重连并各自爬一遍），所以这不是新增风险；去抖窗口只是把"秒级抖动"挡在外面。

### 9.5 入站投递状态

```
routed ──目标 online──▶ delivered
   │
   └──目标非 online──▶ buffered ──flush（重算路由）──▶ delivered | dropped:<reason>
```

**缓冲为主、丢弃兜底（已拍板）**：

| 项 | 值 |
|---|---|
| 范围 | 每节点一条 FIFO，节点之间互不影响 |
| 入队对象 | `message` / `notice` / `request`（所有需要投递的事件） |
| 不入队 | 控制命令（网关本地执行）、被吸收的 meta 事件（§9.7）、API 回包（§9.6） |
| 条数上限 | `NODE_BUFFER_MAX_EVENTS`（默认 200），超出时丢**队首**（最旧的） |
| 时间上限 | `NODE_BUFFER_SECONDS`（默认 10s，覆盖 `RECONNECT_INTERVAL=3.0` 加一次握手），过期即丢 |
| flush 触发 | 节点进入 `online`，按 FIFO 顺序投递 |

**flush 时必须重算路由**：缓冲期间可能发生 override、自动回滚或规则变更；照旧投递会把事件送给刚被判不健康的节点，正好抵消回滚。因此 flush 时对每条事件重跑 §3.2 的解析，**只重算一次，不来回改投**：

- 重算后仍是本节点 → 投递，记 `revised=0`。
- 重算后是另一个 `online` 节点 → 投给新节点（排他投递仍然成立），记 `revised=1`。
- 重算后目标不是 `online` → 丢弃，记 `dropped:revised_target_unavailable`。

**丢弃原因词表**（写进决策日志与指标，不允许自由文本）：`buffer_overflow` / `buffer_expired` / `revised_target_unavailable` / `no_target`（规则不存在或目标节点被禁用，§3.5）。

**事件体附带**：投递时在事件 JSON 上挂 `"_gateway": {"trace_id", "buffered_ms", "revised", "failover"}`。这条路可行——NoneBot 基类 `Event` 是 `extra="allow"`（`nonebot/internal/adapter/event.py:14-18`），未知字段不会被丢弃，节点侧可用 `model_extra` 读回并注入日志（`03 §5` 的 trace 中间件）。`failover` 为布尔量，`true` 表示这条事件因 `kind=emergency` 的 override 改投而来（§3.2 ⑥），它是节点侧 `failover_guard` 的输入（§5.4）——**新增可选字段，符合 §9.10 的兼容规则**：旧节点忽略它，行为退化为"没有节点侧拒绝闸"，不报错。

**不做**：不跨节点迁移缓冲（重算后仍无家可归就丢，宁可丢也不乱序投递）；不做死信重放（要补跑用 `/internal/inject`，`03 §9`——注意它直连节点、不进这里的流水，且**同样过 `failover_guard`**）。

### 9.6 出站 API 代理与 echo 重写

节点发出的 API 调用必须经网关转发，且 echo 必须重写。这不是优化项，是正确性要求：

- 节点每次调用从**进程内**计数器取 seq（`ResultStore._seq` 初值 1，共享包 `nonebot/adapters/onebot/store.py:15`），因此两个节点在同一时刻发出的第 N 个调用，echo 都是 `"N"`——在共享的上行链路上**必然重复**。这是确定性事实，不是"需要验证是否冲突"。
- 节点只把"没有 `post_type` 字段的 JSON"当作 API 回包（`adapter.py:437-439`），且只接受**十进制字符串** echo（`store.py:23-28`）；匹配不上就静默丢弃，节点会一直等到 `api_timeout` 才抛 `NetworkError`。

| 环节 | 规则 |
|---|---|
| 上行（节点 → 网关） | 收到 `{action, params, echo}`，按 `(node, downstream_echo)` 登记 |
| 转发（网关 → NapCat） | 用网关自造的 `upstream_echo`（全局唯一）替换 echo 后转发 |
| 回包（NapCat → 网关） | 用 `upstream_echo` 反查归属，**换回该节点原始的十进制 echo** 再下发 |
| 结算 | 上行断开 / 节点 `draining` / 超过 deadline：网关**主动回一个失败结果**（`{"status": "failed", "retcode": -1, "echo": <原 echo>}`），让节点立刻失败，而不是干等到 `api_timeout` |
| 回收 | 映射表项在结算或回包后立即删除；只需进程内保存，不必持久化（网关重启会断开全部节点连接，见 §9.9） |

失败结果的形态是协议要求，不是约定：节点侧 `handle_api_result` 见到 `status == "failed"` 就抛 `ActionFailed`（`v11/utils.py:44-59`），插件因此立刻拿到异常、日志里能看到 `retcode=-1`——这正是我们要的"快速失败"。

连接期 API 也走这条路径：合成 `lifecycle/connect` 的**同一瞬间**节点就会发出调用（`group_file_manager` 的 `get_group_list`），因此网关必须在发 connect 之前就已经能代理 API（`00-总览.md` §8 第 3 项）。

**网关自己发起的调用**（§8.2 里它作为告警生产者的自报）走同一条上行链路，但必须用**独立的 echo 命名空间**：节点的 echo 是"从 1 开始的十进制字符串"（`store.py:15`），网关自发的 echo 一旦落进同一数域，回包就会被上面的映射表误判归属，还会把 `gateway_api_proxy_orphan_total` 从 0 打起来——而那个指标的定义是"永远为 0"。

### 9.7 meta 事件处置：网关吸收（已拍板）

依据是全包核查：除 §9.3 的 connect 判定外，nonebot 里**没有任何代码消费 `heartbeat` / `lifecycle`**（不更新 `bot.status`、没有心跳看门狗、没有超时判定），本项目 `src/` 也没有 meta 订阅与 `on_bot_disconnect`。所以把 meta 事件投给节点只是噪声，还会污染 `gateway_events_total` 的语义。

| `meta_event_type` | 处置 |
|---|---|
| `heartbeat` | 网关吸收（刷新上游新鲜度） |
| `lifecycle` / `sub_type=connect` | 网关吸收，并作为"上游就绪"信号；**节点侧那一条由网关按 §9.3 合成**，两者不是同一条事件 |
| `lifecycle` / `sub_type=enable` | 网关吸收（`adapter.py` 里 `sub_type` 是裸 `str`，无枚举约束） |
| `lifecycle` / `sub_type=disable` | 网关吸收，并视为上游不可用（按 §9.4 处置） |
| 未知 `meta_event_type` | 网关吸收 + warning 指标（`MetaEvent.meta_event_type` 是 `str`，未知类型仍能解析成 `MetaEvent` 而不报错——**不报错正是不能靠它兜底的原因**） |

### 9.8 已知例外：NapCat 直连 HTTP（旁路）

`QQControlConfig`（`src/config/local_config.py:66-72`，`QQ_CONTROL_HOST` / `QQ_CONTROL_PORT` 默认 6097 / `QQ_CONTROL_TOKEN`）指向 NapCat 的另一套 HTTP 控制接口，仓库里有两处在直接调用：

| 位置 | 调用 |
|---|---|
| `src/plugins/group_send/__init__.py:47-69` | `POST /forward_friend_single_msg` |
| `src/plugins/shit_transport/transport.py:82-100` | `POST /forward_group_single_msg` |

### 9.9 网关自身重启语义

网关重启 → 所有节点连接断开（`draining`）→ 节点 3s 后重连 → 网关等上游就绪后重新合成 connect（§9.3 的副作用各重跑一次）。规则、override、运维名单从 Redis 与本地快照恢复（`02 §10`）；在途 API 调用全部失败（节点侧立刻拿到失败结果，§9.6）。

因此网关重启对用户可见的影响 = 一次"节点重连"，与 NapCat 短暂重启同级。处置与单点风险见 `02 §5.5`、`02 §10`。

### 9.10 跨版本契约（发布顺序的前提）

节点与网关、节点与中控之间隔着一条**必须跨版本兼容**的线：灰度窗口里两个节点本来就可能跑不同 tag，而发布是逐服务替换容器，所以**任意两个版本一定会在某个时刻共存**。兼容性是常态要求，不是"最好有"。

- **允许**：只加可选字段（未知字段必须被忽略——`extra="allow"` 已核实，`_gateway` 就是这么进去的）、只加新接口、加新的指标标签。
- **不允许**：改字段语义、删字段、把可选改成必填、改 `echo` 映射与失败结算语义（§9.6）、改 `lifecycle/connect` 的合成时序（§9.3）、改 `ctl_nodes` / `ctl_deployments` 的既有列含义。
- **必须成对变更时**（做不到兼容）：**网关只能在灰度窗口之外发布**——它一挂两个节点同时受影响（§9.9）；节点可以逐个来，`standby-1` 这类第三节点的价值正在于此（`02 §5.4`）。
- 兼容性由 CI 的**协议兼容测试**兜底（`02 §9` 第 5 条的 `tests/test_contract_compat.py`，把本节的"允许/不允许"清单变成可执行断言），**升级 nonebot 或改协议必须先过**。

### 10.4 `/api/v1/*` 的兼容策略

## 11. 出站流量治理（限流与回复延迟）

限流与回复延迟都作用在**出站发送路径**上（现状都在同一个 `bot.call_api` 包装里），因此放在一起定死。两条结论先摆出来：**限流——网关做唯一实现，节点只留急停**；**回复延迟——留在节点，但语义要从"加延迟"改成"补齐到最早回复时刻"**（§11.4）。现状的实现与文档描述有几处出入，照搬会把坑一起搬过来。

### 11.1 现状（迁移的起点，全部实测）

| 事实 | 出处 |
|---|---|
| 实现共 **704 行**：`middleware.py` 521 + `__init__.py` 28 + `permissions.py` 26 + `config.py` 20，**外加算法本体 `src/common/rate_limiter.py`（109 行）** | —— |
| 算法是令牌桶，但**只等待、从不拒绝**：`acquire()` 在锁内 `await asyncio.sleep(needed / refill_rate)`，**锁一直持有到睡眠结束** → 同一个桶的等待者严格串行。默认 `capacity=5`、`refill_rate=2.0`（突发 5 条，之后 2 条/秒） | `src/common/rate_limiter.py:11-70` |
| **没有入站限流**。唯一的钩子是出站：monkey-patch `bot.send` / `bot.call_api`，且只拦截 5 个发送类 API | `middleware.py:343-345`、`:222-228` |
| 桶的键**只有群号**（`per_group=True` 时每群一个；**默认 `per_group=False`，全进程一个桶**），**没有 bot 维度** | `middleware.py:302-311` |
| 计数是**固定窗口**（首条消息锚定，`elapsed > 60s` 重置），阈值 20 条，只统计成功的群消息 | `middleware.py:82-96`、`:126-138` |
| 超阈值**不是"拉黑"**，而是把进程级的 `emergency_stop` 置真：之后每次发送 `raise RuntimeError`，必须人工敲「限速恢复」；默认的全局模式下**一个群刷屏会把所有群的发送一起停掉** | `middleware.py:143-147`、`:275-299` |
| 状态全在模块全局（桶、计数器、急停标志）；**进程重启会静默清空急停**；桶用 `defaultdict` 且**无淘汰**（每见过一个群多一个对象） | `middleware.py:44-53` |
| 7 个配置值**全是硬编码默认**，env 里一个都没有；且读取用的是**无前缀字段名**（`ENABLED` / `CAPACITY` / `PER_GROUP` …），与其他配置撞名的风险实打实 | `config.py:4-19`、`middleware.py:20-41` |
| 没有任何测试 | `test/` 内零命中 |

> **三处旧表述曾与实现不符（已按本节改写）**："键 `(群号, bot)`"、"节点保留更宽松的兜底桶"、"拉黑阈值"——实际是：键**只有群号**且默认全局一个桶、今天**只有一个桶**、也**没有拉黑**（是进程级急停）。留这段记录是为了让后来人知道这几处**为什么**这么改，别再改回去。

### 11.2 目标形态：谁在哪一层

| 层 | 做什么 | 为什么在这一层 |
|---|---|---|
| **网关** | 令牌桶 + **有界等待**，键 `(group_id, self_id)`，只对 5 个发送类 API 生效 | 只有网关看得见**两个节点的全部出站**；放节点上等于每节点一份桶，双节点放行量翻倍（`00 §1` 记录的现状问题） |
| **节点** | **只有急停开关**（不再保留兜底桶） | 急停是业务保护（防刷屏），必须能独立于网关于预。**兜底桶去掉**：它防的失效模式（网关限流组件自己失效）已被急停覆盖，留着只会让"为什么这条消息被延迟"变成两处排查，也违反决策 8 的单一实现原则 |
| **中控** | 不参与限流，只提供参数（`§2.10` 的下发清单） | 限流在消息通路上，不能引入跨服务同步调用 |

**等待语义：有界等待、超限丢弃**（这是与现状最本质的改动）：

| 参数 | 默认 | 说明 |
|---|---|---|
| `capacity` | 5 | 突发额度（对齐现状） |
| `refill_rate` | 2.0 /s | 稳态速率（对齐现状） |
| `per_group` | **true** | **默认与现状相反**——现状的全局默认会把一个群的刷屏扩散成所有群的延迟 |
| `max_wait_seconds` | 2 | 等待上限，超过即丢弃 |
| 超限行为 | 丢弃 + 计数 | 计入 `gateway_rate_limited_total{group_id}`；不回话（与现状一致：现状也只是等，不提示） |

- **为什么不取"无限等待"（现状）**：锁内睡眠搬到网关会变成**跨节点的队头阻塞**——一个刷屏群会让另一个节点的正常发送也排在它后面，而网关在两个节点的关键路径上。
- **为什么不取"立即丢弃"**：用户的一条命令被静默丢掉，比晚 1 秒回复更糟。有界等待把"轻微突发"变成"稍晚"，只把"持续刷屏"变成"丢弃"。
- **`max_wait_seconds` 必须显著小于节点的 `api_timeout`**（NoneBot 侧默认 30s，**实现前要核对本仓库的实际配置**）：网关在等令牌的同时，节点侧的 `bot.call_api` 也在计时——网关等得比节点久，节点会先抛 `NetworkError`，消息就以**异常**收场而不是干净地丢弃，插件看到的是"发送失败"。2s 对 30s 是安全的，但把这个值改大时要连带检查。
- **键为什么加 `self_id`**：现状没有 bot 维度是因为单 bot；两个节点共用一个 QQ 号时 `self_id` 相同，因此这不改变现有行为，只是把维度补全（将来多号不必重写）。
- **私聊的键**（现状没有定义）：私聊没有 `group_id`，**按 `user_id` 单独分桶**，不并进任何群桶。现状是"私聊不计数、但消耗全局桶"（`middleware.py:68-69`、`:108-109`）——在全局桶模式下那等于"私聊与所有群抢同一个桶"，与 `per_group` 默认翻转要修的是同一类问题。

**急停留在节点，但三处语义要修正**（照搬现状等于把坑搬过来）：

1. **作用域**：急停只在**触发它的键**上生效（`per_group=true` 时就是该群），不再有"一个群刷屏、所有群停摆"。
2. **不再随重启静默清空**：急停状态落 `ctl_settings`（含作用域与触发时间），节点启动时读回来——否则一次重启就把运维刚拉下的闸放开了。
3. **允许双节点各算一份**：急停计数**不要求跨节点一致**。引入共享状态会让 Redis 变成限流的关键依赖，而 `02 §10` 明确不让 Redis 进消息通路；节点侧本来就只是"网关失效时的下限保护"，宽松是它的设计目标。

**触发与恢复**：仍走 `rate_limiter:manage` 权限点（`rate_limiter_middleware/permissions.py:15-26` 已注册）；但**通知出口改为经 `diting-notify` 发一条 critical**（§8.2）——现状是直接 `_original_call_api` 发群，绕过了告警体系。

### 11.4 回复延迟（拟人化）

**现状（实测）**：延迟在同一个 `bot.call_api` 包装里，**每次发送前** `await asyncio.sleep(random.uniform(0.3, 1.0))`，由 `DELAY_ENABLED` 控制（默认开，`local_config.py:58-64`）。所以它是**全局、无差别、加在发送时刻**的。它有两个问题：一个是语义错，一个是粒度缺。

#### ① 语义错：它应该是"最早回复时刻"，不是"额外延迟"

拟人化想表达的是"**不要秒回**"——那是一个 deadline，不是一笔附加时间。现状是 `总耗时 = 插件运行时间 + 延迟`，两者只在"插件秒回"时才近似等价；插件本来就跑了 2 秒时，再睡 1 秒纯属多余。改成：

```
send_at   = received_at + T          # T 随机 ∈ [min, max]
实际等待  = max(0, send_at - now)     # 已经超了就立即发
```

- `received_at` 取**网关入站时刻**（`_gateway` 通道已经带 `trace_id`，顺带带上它即可，§9.5）。**事件在网关缓冲里等的时间也算**——用户感知的是"我发出消息到收到回复"的总时长，缓冲 10 秒的话他早就等够了，回复该立即发。
- 附带两个好处：慢插件不再被额外惩罚；**最坏延迟有了上界**（≤ T + 插件耗时），比现状更可预期。
- **边界：多条回复会连发。** 同一事件发多条消息时，"补齐到 T"会让它们集中在同一时刻爆出，而现状的"每次发送睡一次"反而拉开了间隔。所以完整规格是"第 N 条的最早时刻 = `received_at + T + (N-1) × gap`"（`gap` 默认 0.3s）。若认为这属于过度设计，最小版本是"补齐到 T"，但要接受多条回复连发。

#### ② 粒度缺：参数按插件命名空间配，而且不需要新机制

关键点是**发送时"是哪个插件在发"天然已知**——`03 §5` 的中间件本来就要做 trace 注入（"注入 `node` / `version` / `plugin` / `trace_id`，发送动作带 trace"），插件归属在发送钩子里就在手上。所以：

- 参数进 `ctl_settings`，按插件命名空间：`delay.<plugin>.min` / `delay.<plugin>.max` / `delay.<plugin>.enabled`，**缺省继承全局默认**（没配就用默认，因此"插件不改写法"依然成立）。进 `§2.10` 的节点下发清单。
- **哪些插件值得配**：真正需要"补延迟"的是**纯查询、秒回**的那类（帮助菜单、榜单这类查库快的）；渲染类（`clipboard` / `prd`）与 LLM 类（`llm_scribe`）本身就超过 T，**配了也等于不生效**——这恰好是"补齐语义"带来的好处：不必为慢插件做特殊处理，它们自动不受影响。

**放在节点，不放网关**：两层理由——"插件归属"只有节点知道（网关要反查就得跨服务）；而且延迟是**拟人化**不是**保护账号**，性质与限流不同，不该跟着搬到出口层。

| 项 | 什么时候做 |
|---|---|
