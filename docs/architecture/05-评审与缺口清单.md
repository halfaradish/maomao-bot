## 1. 总体结论

**设计质量高于一般架构文档**：它不描述理想架构，而是先把存量代码读到行号级别，再让每个决策带出处、代价与被否方案。抽查约 80 条引证，绝大多数精确到行；几条最有价值的诊断（群级缓存失效是死代码、`env_tag` 现状、内省覆盖率）**全部实测成立**。

**不均衡之处**：「为什么这么设计」写得很足，「怎么实现」在若干处是空的；另有 12 处写错或互相矛盾。最需要立刻处理的是 §2 的六条，其中 **P0-1（网关实现形态）** 决定 `01 §9` 整章要不要重写。

## 6. 核对方法与覆盖边界

**怎么核的**：四组并行核对（权限系统 / NoneBot 适配器与规则内部 / 部署与配置 / 插件与调度），逐条打开被引用的文件与行号，报告 `CONFIRMED / PARTIAL / WRONG`；关键结论二次实测（在 Python 里跑 `clear_pattern` 的子串匹配、用容忍空格的正则重算 env 键集合、统计 matcher 与 `get_bound_group_ids` 的实际调用点）。共核对约 80 条引证。

**已实测确认、可直接引用的结论**（记录在此以免重复验证）：

| 结论 | 核对结果 |
|---|---|
| 群级缓存失效是死代码（`clear_pattern("perm::{gid}:")` 匹配不到 `perm:{uid}:{gid}:{key}`） | 确认，`'perm::456:' in 'perm:123:456:like:subscribe'` 为 False |
| `.env.dev` 与 `.env.prod` 差 6 键、其中 5 个是死键且只在 prod | **完全正确**。注意其中 3 个写成 `KEY = value`（等号带空格），用严格正则统计会漏——这本身就是"无 schema、靠 `os.getenv` 散读"的实证 |
| 38 个插件；12 个插件注册定时任务；8 个插件 13 处 `get_bound_group_ids` | 逐项精确匹配 |
| 内省覆盖 ~97%（74 个 message 类 matcher，仅 2 个 opaque） | 实测 `on_command` 67 + `on_regex` 5 + `on_message` 2 = 74；opaque 正是 `banned_word_detector` 与 `message_listen`，与 manifest 示例的 `74/72` 一致 |
| 命令与自定义 rule 组合后仍可提取命令 | 确认（`Rule.__and__` 扁平合并） |
| meta 事件在 NoneBot v11 中无任何消费方 | 确认（v12 才有 status update 机制） |
| 适配器无 `message_sent`；`Event` 是 `extra="allow"`；`lifecycle/connect` 之前的事件被静默丢弃 | 全部确认 |
| 48 个注册权限点中 8 个从未被校验；3 处手搓 provisioning | 确认（后者另有 E-04 的第 4 处） |
| 容器无 `restart` / 无 `logging` 段 / 硬编码 Redis 口令 / `Dockerfile` 为 `COPY . .` 且 `.dockerignore` 未排除 `.env*` / `logs/nonebot.log:3` 明文转储密钥 | 全部确认 |
| 无迁移工具（`create_all` 引导）；`src/api/groups.py` 的群活跃度聚合无 `post_type` 过滤 | 确认 |
