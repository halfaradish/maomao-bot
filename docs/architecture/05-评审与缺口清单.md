# 05 · 评审与缺口清单

对 `00`~`04` 的独立复核结果。**本文不是新设计**，只做三件事：记录哪些结论已实测确认（不必再验）、列出尚未定义或互相矛盾的部分、给出建议的处理顺序。

**怎么用这份清单**：每条都是可勾选的待办。ID 稳定（`P0-*` 架构级缺口 / `P1-*` 实现契约缺口 / `E-*` 勘误），处理顺序见 §5。勾选时请在括号里补上处理者与日期，便于后续对账。

| 级别 | 含义 | 数量 |
|---|---|---|
| **P0** | 不补会卡住实现，或留下真实的安全/一致性风险 | 6 |
| **P1** | 不影响架构成立，但按"字段名以本文为准"的标准属于契约缺失 | 16 |
| **E** | 已写但写错了（含引用错误与自相矛盾） | 12 |

核对方法与覆盖边界见 §6。

---

## 1. 总体结论

**设计质量高于一般架构文档**：它不描述理想架构，而是先把存量代码读到行号级别，再让每个决策带出处、代价与被否方案。抽查约 80 条引证，绝大多数精确到行；几条最有价值的诊断（群级缓存失效是死代码、`env_tag` 现状、内省覆盖率）**全部实测成立**。

**不均衡之处**：「为什么这么设计」写得很足，「怎么实现」在若干处是空的；另有 12 处写错或互相矛盾。最需要立刻处理的是 §2 的六条，其中 **P0-1（网关实现形态）** 决定 `01 §9` 整章要不要重写。

## 2. P0 · 架构级缺口

- [ ] **P0-1 · 网关自身的实现形态未定义（是否复用 NoneBot 适配器）**
  问题：`01 §4.4` 写"网关不跑 NoneBot"，`02 §1.3` 的选型是"FastAPI/uvicorn 或纯 websockets"，都指向自实现协议；但 `01 §8.5` 的前置条件 2 要求"用官方扩展点 `Adapter.add_custom_model` 注册 `MessageSentEvent`"——网关不跑 NoneBot 就没有人消费这个适配器模型，该前置是空的（网关直接按 `post_type` 白名单处理原始 JSON 即可）。反向的读法同样成立：若网关复用适配器，`§9.6` 的 echo 重写就要与适配器进程内的 `ResultStore` 对抗。
  影响：`01 §9`（连接状态机、echo 重写、connect 合成、API 代理）的全部可行性论证都挂在这个未定的选择上；`§8.5` 前置 2 是否保留也取决于它。
  建议：在 `02 §1.3` 明确二选一并写明理由——**推荐自实现 OneBot V11 协议**（网关必须逐连接改写 echo、自行合成 `lifecycle/connect`，这两件事都不是适配器的用法），此时删掉 `01 §8.5` 前置 2、在 `§9.2` 注明"`X-Self-ID` 校验由网关自己实现"。
  证据：`01 §4.4`、`01 §8.5` 前置 2、`01 §9.6`、`02 §1.3`、`02 §2.1`（网关 env 无 `DRIVER` / `ONEBOT_V11_WS_URLS`）。

- [ ] **P0-2 · 拒绝清单拦不住"被动插件的不可逆动作"，但文档声称它保住了底线**
  问题：`01 §5.4` 声称接管期间"凡不可撤销的动作，一律不交给未验证的代码"，但运行期过滤是**投递前按插件归类**实现的，而被动 matcher 不产生触发词、`routable=false`（`01 §4.1` 自己写明"被动插件是全域流量"）。具体反例：`auto_manage_group` 的 `banned_word_detector`（`on_message` + 自定义 rule，正是 `03 §3.3` 标定的 opaque）命中违禁词后执行 `set_group_ban(... 1 小时)`。
  影响：接管期间任何一条普通群消息都会被投给 dev，**未验证代码可以直接禁言生产群成员**；而 `auto_manage_group` 不在 `01 §4.5` 建议的 7 个高危插件名单里。这是对用户可见、不可撤销的动作。
  建议：三选一并写进 `01 §5.4`——① 拒绝清单补一个**节点侧执行点**（接管态下由节点关闭被拒插件的强制动作，清单随规则快照下发）；② 把 `auto_manage_group` 加入初始名单并接受"只挡命令、挡不住被动"；③ 明确写成已知限制（当前写法是过度承诺）。
  证据：`01 §4.1`、`01 §4.5`、`01 §5.4`、`03 §7`；`src/plugins/auto_manage_group/__init__.py:163`（`on_message`）、`:276`（handler）、`:299`（`set_group_ban`）。

- [ ] **P0-3 · Redis 不可用时的"陈旧窗口"没有定义**
  问题：文档对 Redis 失效的推理很细（不把存活判定放进 Redis、租约 fail-closed、限流降级），但**权限与规则的陈旧上界完全没写**。`04 §4.3` 的失效依赖 Redis pub/sub，兜底是"启动全量 + 每 30 分钟对账"。
  影响：Redis 挂掉后，"撤销某人的管理员"最长 30 分钟不生效——这是安全语义，不是性能问题。规则侧同理：`02 §5.5` 只说"规则改不了"，没说已缓存规则的新旧。
  建议：在 `04 §4.3` 与 `01 §3.1` 各写明陈旧上界、降级路径（是否回落到 DB 轮询版本号）与告警项（进 `01 §8.2` 的触发清单）。
  证据：`04 §4.3`、`01 §3.1`、`01 §9.9`、`02 §5.5`、`02 §10`。

- [ ] **P0-4 · 同名节点的重复连接语义未定义**
  问题：`ctl_nodes.name` 是主键，但网关的连接表在进程内，`01 §9.3` 的状态机假设"每节点一条"。滚动更新时新容器先连上、旧容器尚未断开是常态。
  影响：会出现两条同 `node` 的连接，投递目标不确定；旧连接的 echo 映射与新连接混在一起。
  建议：在 `01 §9.3` 定死一种语义（推荐"新连接顶掉旧连接：旧连接进 `draining` 并结算在途 API"），并补一条指标（`gateway_node_conn_replaced_total`）。
  证据：`01 §9.3`、`01 §9.6`、`01 §2.1`、`02 §2.4`（`NODE_NAME` 冲突告警只覆盖配置层面）。

- [ ] **P0-5 · `diting-notify` 与宿主 watchdog 没有落地阶段**
  问题：`02 §2.5` 定义完整、`§10` 列为单点，但 `§4` 的 P1.0→P1.3 路径里**从未出现"建 diting-notify"**；而 `00 §8` 影子期的第 10 项验收要求跑 `02 §12` 的演练 23/27/28/29，这几条正是 L1→L2→L3 降级链的验证。另外 P1.3 步骤 12 写"告警到 `825332714`"（旧的硬编码群），与 `01 §8.2`"告警目标只有 `ctl_settings` 一个来源"冲突。
  影响：影子期无法通过第 10 项验收；按 `§4` 推进的人不会建这个组件，直到接管时才发现没有出口。
  建议：在 `02 §4.1` 的 P1.0 清单里加入"建 `diting-notify` + 宿主 watchdog + 写入 `ctl_settings` 的告警目标"；把 P1.3 步骤 12 的群号改为引用 `ctl_settings.alert_group_ids`。
  证据：`02 §2.5`、`02 §4.1`、`02 §10`、`00 §8` 第 10 项、`02 §12` 演练 23/27/28/29。

- [ ] **P0-6 · 控制命令的写入与审计路径依赖中控，但 `01 §6` 没有声明**
  问题：`02 §2.0` 的键归属表明确网关**不持有** `CTL_DB_URL`，`00 §5` 也写"不持有中控库凭证"；而 `01 §6.3` 写"每条命令：先鉴权 → 执行 → 写 `ctl_audit`"。网关只能经 HTTP 让中控代写，这条路径与**中控不可达时的语义**（拒绝执行并回"中控不可达"，还是本地执行后补审计）都没有写。
  影响：`/env` 的读命令可离线（走本地快照），但所有写命令（`route` / `freeze` / `resume` / `deploy`）都要求中控在线——"节点全挂也能切回 prod"成立，"中控挂了也能切回"不成立。这条边界只隐含在 `02 §10/§11`，`01 §6` 的论证（"节点全挂也要能切回来"）会让读者以为更宽松。
  建议：在 `01 §6.1` 增加"能离线执行的边界"一段，并在 `§6.3` 写明审计写入路径（网关 → 中控 HTTP）与中控不可达时的回执文案。
  证据：`01 §6.1`、`01 §6.3`、`01 §6.4`、`02 §2.0`、`02 §5.5`、`02 §10`。

## 3. P1 · 实现契约缺口

- [ ] **P1-1 · `ctl_deployments` 与 `ctl_decisions` 没有表结构**
  `01 §2` 给出了 `ctl_nodes` / `ctl_rule_rules` / `ctl_rule_revisions` / `ctl_overrides` / `ctl_incidents` / `ctl_audit` / `ctl_settings` 的字段表，`ctl_jobs` 在 `03 §6.2`，但 `ctl_deployments` 被 `01 §6.2`、`02 §5.0/§5.6/§6.2` 反复引用（sha、阶段、执行人、结果）却从未定义；`ctl_decisions` 只在 `01 §2.8` 描述了写入策略（"仅四类必落，保留 30 天"）。建议补齐两张字段表。

- [ ] **P1-2 · 部署窗口的"进度探活"没有接口**
  `02 §5.0` 要求"窗口内持续探执行器进度，进度停滞即提前关窗"，但只定义了 `POST /ctl/deploy/begin|end`，没有 progress 上报，超时兜底无法实现。建议补 `POST /ctl/deploy/progress {phase, detail}` 或改用 `ctl_deployments` 的阶段时间戳推断。

- [ ] **P1-3 · 限流上移网关只有一句话**
  `02 §2.1` 一个 `RATE_LIMIT_*`、`03 §8` 一句"令牌桶上移网关，键 `(群号, bot)`"，对应的是现有 343 行实现（群消息计数、拉黑阈值、`bot.send` / `bot.call_api` 双层补丁）。缺算法与参数、Redis 故障时的行为、与节点兜底桶叠加后的实际放行量、触发时的回复话术与指标。

- [ ] **P1-4 · WebUI 的信息架构与 API 端点清单缺失**
  决策 4（管理面全部迁中控）的工作量主体在这里，但只有 `02 §4.3` 一句"WebUI 先出只读总览页"。缺：页面清单与去向、`/ctl/*` 端点清单（现只定义了 `routes/preview`、`jobs/report`、`deploy/*`）、现有 `/api/v1/*` 的兼容策略。建议在 `02` 或新建一节给出"现有页面 → 新页面"的映射表。

- [ ] **P1-5 · 分类器保真清单漏了 `force_whitespace` 与 `ignorecase`**
  `01 §4.4` 声称与 NoneBot 判定"逐位一致"，但只列了 `TrieRule.get_value` 与 token 比较。`CommandRule.force_whitespace` 决定 "banxxx" 是否命中 `ban`，项目里有实际使用；`ignorecase` 同样影响 `StartswithRule` / `FullmatchRule` / `KeywordsRule` 的判定。建议补进 §4.4 的复刻清单。
  证据：`nonebot/rule.py:350-372`；`src/plugins/diting_deploy/commands.py:590`、`src/plugins/permission_manager/runtime.py:15`。

- [ ] **P1-6 · 文案配置双份且优先级未定**
  `degrade_reply_text` 同时出现在 `01 §2.7` 的 `ctl_settings` 与 `02 §2.1` 的网关 env（`DEGRADE_REPLY_TEXT`，"与中控配置同步，网关本地兜底"），谁覆盖谁没说，与决策 14 的"单一真相"相抵。建议明确"中控为准、env 只是首启兜底"，并说明同步机制。

- [ ] **P1-7 · 告警目标的引导顺序缺失**
  收件人只在 `ctl_settings`（`01 §8.2`），而 `ctl_settings` 由中控创建；首次部署时它为空，**第一条告警发给谁**没有答案。另：`ALERT_GROUP_IDS` 取消后，现有取值怎么迁进 `ctl_settings` 也没写。建议补 `ALERT_*_SEED` 或明确引导顺序（先建中控 → 写 `ctl_settings` → 再启用告警）。

- [ ] **P1-8 · `ENVIRONMENT` 的删除与 `env_tag` 迁移耦合，两处没有互相引用**
  `02 §2.4` 要求"顺手删掉 `ENVIRONMENT`"，而 `current_env_tag()` 取的是 `get_driver().config.environment`，NoneBot 的 `Env.environment` **默认值是 `prod`**（`nonebot/config.py:395`）。删掉这个键的副作用就是两个节点的 `env_tag` 立刻都变成 `prod`——这正是 `02 §6.4` P3a 想要的效果，但文档把它当配置清理放在 P1.0、把注入当代码改造放在 P3a。若在旧 dev clone 停用前就删，会让同一份数据被写两个 tag。
  建议：把这一步重定性为**一次数据切换**并入 `§6.4`，注明"必须在旧 dev clone 停用之后执行，且要核对数据"。
  证据：`02 §2.4` 勘误注、`02 §6.4`、`src/common/database.py:23-33`、`nonebot/config.py:389-398`。

- [ ] **P1-9 · `event_logs` 保留期未定，且与 `text_digest` 纪律冲突**
  `01 §8.3` 明确"不把群聊内容长期留存在控制面"，但 `event_logs.detail` 存的是**事件原文**（含群消息全文），落在业务库、增长率 1.5~3 倍、保留期"尚未定"，而老表是"不清理"。这不是错误，但需要把"原文留存"的取舍、保留期决策时间点与容量预案写清（`01 §8.5` 已给"先跑一个月"的建议，建议同时写明最坏情况的处置）。

- [ ] **P1-10 · `expires_at` 在物化快照下的到期机制未写**
  快照是全量物化 + 版本号失效（`04 §4.3`），而版本号只在写入时递增；过期授权需要惰性判断或定时重载，否则"临时授权到期"不会生效。建议在 `04 §4.3` 写明（推荐判定时比对 `expires_at`，并让过期本身也递增一次版本以触发对账）。

- [ ] **P1-11 · 兜底话术依赖的"manifest 并集"怎么下发到节点没写**
  `01 §5.6` 说第一类降级话术由节点侧 matcher 依据"manifest 并集与本地 manifest 的差集"判定，`01 §4.1` 说中控合并并集，但并集如何到达节点没有定义。建议补一条：并集随规则快照（或独立快照）下发。

- [ ] **P1-12 · `/internal/inject` 的语义未定义**
  `01 §9.5` 与 `03 §9` 都提到用它补跑，但没说注入的事件是否经网关、是否进决策日志与事件流水。直连节点会绕过 trace、限流与流水。建议明确"仅应急、直连节点、记独立来源标记"，并说明它不进 `event_logs` 的后果。

- [ ] **P1-13 · 单仓多服务的依赖分层与边界强制未定义**
  每服务独立镜像如何分离依赖（现为单一 pyproject + `requirements.txt`）、`services/*` 不得 import `apps/*` 用什么工具强制（决策 7 只说"由 CI 强制"）都没写。另：`03 §3.4` 要求"pin nonebot 版本"，但真正生效的是 `requirements.txt` 的裸 `nonebot2[fastapi]`，而 `pyproject.toml` 是 `^2.4.4` 的宽范围——**pin 的落点要说清并改对文件**。

- [ ] **P1-14 · 测试策略偏薄，且目录命名与现状不一致**
  只定义了 `tests/test_manifest_exporter.py` 与 `tests/test_classifier_parity.py` 两个契约测试；网关状态机、echo 重写、健康状态机、部署窗口、拒绝清单过滤都没有测试要求。仓库现有约定是 `test/`（单数、零散脚本），文档写的是 `tests/`。建议在 `02 §9` 补一张"哪些行为必须有测试"的清单。

- [ ] **P1-15 · 权限面板写操作在中控不可达时的语义未写**
  `04 §4.7` 说面板的读取走节点本地快照、写操作 POST 到中控，但没写中控不可达时的回执与失败语义（与 P0-6 同源）。建议与 P0-6 一并处理。

- [ ] **P1-16 · 规则版本回滚的范围容易被误读**
  `01 §6.2` 的 `/env rollback --last` 回滚的是 `ctl_rule_revisions.snapshot`，而 `01 §2.3` 明确该快照**只含全量规则数组**——不含 override、`ctl_settings`、`ctl_jobs`。建议在 `§6.2` 注明"只回滚规则，不动 override 与配置"，避免被当成"回到上一版全部配置"。

## 4. E · 勘误表

- [ ] **E-01 · `FullmatchRule` 的属性名**：`03 §3.1` 写 `msg` / `msgs`，实际两个类都是 `msg`（`nonebot/rule.py:148`、`:258`）。按 `getattr(rule, "msgs")` 实现会取不到值。
- [ ] **E-02 · 引用了不存在的实现文件**：`04 §4.10` 与 `04 §4.5` 用 `services/gateway/diting_gateway/ops_admins.py:63-67` 作为"网关侧实现已经如此"的证据，全树不存在该文件，只在文档自身出现。本目录自称"不是实现说明"，应删掉或标注为"计划中的路径"。
- [ ] **E-03 · `siqi_auth` 不是"无任何引用"**：`04 §3.3` 写"无任何外部引用方（死代码）"，但 `siqi_auth/plugin.py:5-9` 引用 `siqi_client`，`src/common/__init__.py:21-23` 导出它，且它以 `plugin_dirs` 方式被运行时加载。准确说法是"业务上无人调用"——删除前仍需确认。
- [ ] **E-04 · 手搓 `ensure_perm_group` 漏了第 4 处**：`04 §3.1` 写"3 处手搓变体"，另有 `fakemsg/core.py:62-76`（同文件 `:43`、`:98` 还有重复查询）。
- [ ] **E-05 · 日志卷路径自相矛盾**：`02 §1.1` 写 `./logs/<service>:/app/logs`，`02 §2.4` 写 `./logs/<env>/<service>/`——少一层 env，同机双环境会撞。统一为 `./logs/<env>/<service>/`。
- [ ] **E-06 · 影子期验证项数不一致**：`00 §8` 写"10 项"，`02 §4.1` 两处写"9 项"。以 `00 §8` 的表为准（实为 10 行）。
- [ ] **E-07 · 交叉引用落空**：`01 §9.10` 说"兼容性由 CI 的契约测试兜底（`02 §9` 第 5 条）"，但该条只定义了 manifest 导出与分类器对拍两个测试，**与协议字段兼容无关**——协议兼容目前没有任何测试定义。

## 6. 核对方法与覆盖边界

**怎么核的**：四组并行核对（权限系统 / NoneBot 适配器与规则内部 / 部署与配置 / 插件与调度），逐条打开被引用的文件与行号，报告 `CONFIRMED / PARTIAL / WRONG`；关键结论二次实测（在 Python 里跑 `clear_pattern` 的子串匹配、用容忍空格的正则重算 env 键集合、统计 matcher 与 `get_bound_group_ids` 的实际调用点）。共核对约 80 条引证。

**已实测确认、可直接引用的结论**（记录在此以免重复验证）：

| 结论 | 核对结果 |
|---|---|
| 群级缓存失效是死代码（`clear_pattern("perm::{gid}:")` 匹配不到 `perm:{uid}:{gid}:{key}`） | 确认，`'perm::456:' in 'perm:123:456:like:subscribe'` 为 False |
| `.env.dev` 与 `.env.prod` 差 6 键、其中 5 个是死键且只在 prod | **完全正确**。注意其中 3 个写成 `KEY = value`（等号带空格），用严格正则统计会漏——这本身就是"无 schema、靠 `os.getenv` 散读"的实证 |
| 38 个插件；12 个插件注册定时任务；8 个插件 13 处 `get_bound_group_ids` | 逐项精确匹配 |
| 内省覆盖 ~97%（74 个 message 类 matcher，仅 2 个 opaque） | 实测 `on_command` 67 + `on_regex` 5 + `on_message` 2 = 74；opaque 正是 `banned_word_detector` 与 `message_listen`，与 manifest 示例的 `74/72` 一致 |
| 命令与自定义 rule 组合后仍可提取命令 | 确认（`Rule.__and__` 扁平合并） |
| meta 事件在 NoneBot v11 中无任何消费方 | 确认（v12 才有 status update 机制） |
| 适配器无 `message_sent`；`Event` 是 `extra="allow"`；`lifecycle/connect` 之前的事件被静默丢弃 | 全部确认 |
| 48 个注册权限点中 8 个从未被校验；3 处手搓 provisioning | 确认（后者另有 E-04 的第 4 处） |
| 容器无 `restart` / 无 `logging` 段 / 硬编码 Redis 口令 / `Dockerfile` 为 `COPY . .` 且 `.dockerignore` 未排除 `.env*` / `logs/nonebot.log:3` 明文转储密钥 | 全部确认 |
| 无迁移工具（`create_all` 引导）；`src/api/groups.py` 的群活跃度聚合无 `post_type` 过滤 | 确认 |

**顺带记录两条对设计有利的事实**：① 38 个插件里 **37 个已有 `__plugin_meta__`**（只有 `image_collection` 没有），`extra["diting"]` 有现成落点；② 内省真正依赖的规则类都在公开模块 `nonebot/rule.py`，比 `03 §3.4` 的风险描述更稳。
