# 04 · 权限与授权设计

面向写权限系统与业务插件的人。本文定义权限子系统的**现状缺陷、目标设计与迁移顺序**，并显式记录两条已定策略。
配套阅读：`01-路由与灰度.md`（审计与 override 的写法参照）、`03-插件契约与改造映射.md` §5（全局中间件与权限入口）。

---

## 1. 结论

| 项 | 处置 |
|---|---|
| 数据模型（权限点 / 权限组 / 成员 / 绑定 / 黑名单） | **保留**，只加列（`role`、`effect`、`expires_at`） |
| `user_whitelist` / `group_whitelist` | **删除**，语义并入"操作员"（§2.1） |
| 求值路径 | **重写**：五步链 + 一次快照 + 可解释（§4.2） |
| 缓存 | **重写**：节点内存快照 + 版本号，替代进程内 60s TTL（§4.3） |
| 审计 | **新增**：所有写入路径共用一个 `permission_audit`（§4.4） |
| 管理面鉴权 | **重写**：JWT 只证明身份，端点逐一声明权限点（§4.6） |
| 写入路径 | **收口**：中控是唯一写入者（§4.7） |
| 入口 API `check_permission` / `permission_checker` / `blacklist_guard` | **签名不变** → 38 个业务插件零改动（§5） |

**为什么必须改**：缓存是进程内的（`src/common/permission/cache.py:4` 明写"单进程 bot 场景适用"）。新架构有两个节点，灰度期间"某群走 dev、其它走 prod"，同一用户的权限判定在两个节点上最长 60 秒不一致；而权限数据是**刻意跨环境共享**的（`docs/diting-deploy.md` §4.3 ③）。此外它不是"能不能更优雅"的问题：§3 的 A 类全部是可复现的 bug，C 类是零审计。

## 2. 两条已定策略（不是缺陷，不要"修"）

### 2.1 白名单 = 管理员

**现状**：`user_whitelist` / `group_whitelist` 命中即 `return True`，且**不区分 perm_key**（`src/common/permission/checker.py:123-131`）。这与管理员已经等价——管理员命令的判定 `check_permission(event, ADMIN_PERM_KEY)` 走的正是这条普通路径。两套表、两条判定链表达同一件事。

**决定**：删掉两张表，白名单条目一律落为"操作员"。

**迁移映射**

| 旧数据 | 新归属 |
|---|---|
| `user_whitelist.user_id` | 加入操作组（现名 `perm_admin`）的成员 |
| `group_whitelist.group_id` | 绑定该 QQ 群到操作组（即 §2.2 的"全群管理员"） |
| 两张表 | 两端切到新代码后 drop（contract 阶段）；迁移前自动备份，逐条写审计 |

**三个连带影响（必须知道）**

1. **"加白名单"从此等于"设管理员"**。WebUI 白名单页改为"管理员"页（或并入操作组详情）；QQ 面板 `白名单` 命令保留为别名、内部落到操作组；`/api/v1/permissions/whitelist/*` 作为 deprecated 别名保留一个版本再移除。**UI 文案必须写清"这是管理员"**，否则运维会以为只是"免黑名单"。
2. **原白名单成员现在也豁免黑名单**。今天是第 3 步（在黑名单 1、2 步之后），所以"被拉黑的白名单用户"是被拒的；并入操作员后变成放行。这是"白名单 = 管理员"的直接推论，属刻意结果，但操作组成员请保持克制。
3. **群功能开关要跟着迁一次**。`src/plugins/auto_manage_group/group_checker.py:46-51` 现在用"群白名单 → 功能全开"兜底；白名单删掉后该语义由新的 `group_features` 表承担。

   **已拍板：先对齐、再渐进收紧**（不做"全部留空、人工按需开启"）。

   - **对齐**（迁移脚本自动做）：对每个原白名单群，把 `permission_points` 里当前已注册的全部群级 feature_key 批量写 `enabled=1`，行为与迁移前逐条等价。**不这么做就是"迁移即功能回退"**，用户侧会立刻看到违禁词检测、加减员管理等一起失效。
   - **收紧**（人工，迁移后）：给运营一张"该群实际开启的功能"清单，复核后关掉不需要的。
   - **此后新增功能不再自动对该群开启**（更符合"功能开关"的直觉，是有意的轻微变化）。

   注意这也意味着：原白名单群在新语义下是"群绑定到操作组"，即**全群管理员**——与今天的实际行为一致（白名单对任意 perm_key 放行），不是收窄也不是扩大。对齐清单的 feature_key 来源是 `permission_points`（由插件的 `perm_points` 声明投影而来），迁移脚本不要硬编码插件名单。

### 2.2 群绑定 = 全群管理员

**这是有意的授权方式**，保留，不设硬性禁止：把 QQ 群绑定到权限组，即让该群成员在该群语境下获得该组权限；绑定到操作组就是"全群管理员"。

两条边界必须写准，避免误读：

- **作用域是群语境**：群消息里判定通过；**私聊（`group_id=None`）只认直属成员，不认群绑定**（`checker.py:64-66`、`153-159`）。
- **它同时带来黑名单豁免**，因为那是管理员语义的一部分。

因为该操作"一次影响全群"，要求三条，**已全部拍板**：

1. **审计必做并单列一类**（`permission_audit.action=bind`，`target_type=group_binding`）。
2. 面板/WebUI 上给出明确提示："此操作会让该群全部成员获得管理员权限"。
3. **加二次确认**：引用回复确认，30s 内有效。机制与 `01-路由与灰度.md` §6.3 里危险 `/env` 命令用的二次确认**是同一套**（同一个 confirm token 契约，见 §4.5 第 5 条），不要各写一套。

## 3. 现状缺陷（全部有代码证据）

### 3.1 A 类：确定性缺陷（bug，不是权衡）

| # | 缺陷 | 证据 | 处置 |
|---|---|---|---|
| A1 | **群级缓存失效从未生效**：判定 key 是 `perm:{uid}:{gid}:{key}`，群级失效却调用 `clear_pattern("perm::{gid}:")`，而 `clear_pattern` 是**子串匹配** → 没有任何 key 含 `perm::` → 群黑名单/群绑定变更**零失效**，最长 60s 内旧判定继续生效。`.claude/skills/perm-system-guide/SKILL.md:530` 还把这套机制描述成有效，属文档与实现相反 | `cache.py:39`、`checker.py:72`、`permission_manager/guard.py:22`、`api/permissions/blacklist.py:143,168`、`whitelist.py:143,168` | §4.3 快照 + 版本号：**版本自增即失效** |

### 3.4 D 类：与新架构的冲突

- **D1** 进程内缓存 × 双节点 = 判定不一致（最长 60s）——这是"必须改"的硬理由。
- **D2** 管理面迁中控后，写入点会变成第三个。
- **D3** 网关的运维名单（已拍板独立维护）若不设计边界，就是第二个身份真相（§4.10）。
- **D4** 权限点前缀（`plugin:action`）与插件 manifest 的 `plugin` 字段是同一个"插件标识"，需统一为单一来源。
- **D5** 路由变更设计了完整审计与版本回滚，权限变更却查不到——二者重要性相当。

## 4. 目标设计

### 4.1 表结构

**删除**：`user_whitelist`、`group_whitelist`。

**保留并加列**：

| 表 | 变更 |
|---|---|
| `permission_points` | 不变（要求代码声明为准，DB 是投影；启动时对账：新增、改名、下线标记） |
| `permission_groups` | 加 `role ENUM('normal','operator')` —— 把"哪个组是管理员组"从**命名约定**变成**显式类型**，不再靠 `perm_admin` 这个名字认 |
| `permission_group_perms` | 加 `effect ENUM('allow','deny')`（默认 `allow`）与 `expires_at`（NULL = 永久） |
| `group_perm_bindings` | 不变，但**只保留"授权"一重语义**（§4.8） |
| `user_blacklist` / `group_blacklist` | 不变 |
| `permission_group_members` | 不变 |

**新增**：

| 表 | 用途 | 关键列 |
|---|---|---|
| `group_features` | 群功能开关（替代 `is_group_feature_enabled` 借用绑定表） | `qq_group_id`、`feature_key`、`enabled`、`updated_by`、`updated_at`；唯一键 `(qq_group_id, feature_key)` |
| `subscriptions` | 推送目标（替代 `get_bound_group_ids("<权限组名>")`） | `topic`、`qq_group_id`、`created_by`；唯一键 `(topic, qq_group_id)`；`topic` 由插件在 manifest 里声明 |
| `permission_audit` | 审计（§4.4） | 见下表 |

### 4.2 求值链与 Decision

**五步链**（替代现有七步，§2.1 删掉白名单两步、新增显式 deny 一步）：

| 步 | 条件 | 结果 | 说明 |
|---|---|---|---|
| 0 | 主体是操作组（`role=operator`）的直属成员，或其所在群绑定到操作组 | **allow** | 豁免黑名单（步 1/2），这是刻意语义（B3） |
| 1 | `user_blacklist` 命中 | deny | |
| 2 | `group_blacklist` 命中（仅群语境） | deny | |
| 3 | 命中 `effect=deny` 且未过期的授权 | **deny** | 新增能力：per-key 拒绝，优先于 allow |
| 4 | 直属权限组成员 ∪ 群绑定权限组中，存在 `effect=allow` 且未过期的该 perm_key | allow | 群绑定仅在群语境生效（§2.2） |
| 5 | 以上都不命中 | **deny** | 默认拒绝 |

配套要求：

- **一次快照**：整条链在一个事务（快照建立时）内完成，消除 A3。
- **可解释**：返回 `Decision{allow, reason_code, matched[]}`，`reason_code` 取值固定（`operator` / `user_blacklist` / `group_blacklist` / `explicit_deny` / `member_grant` / `binding_grant` / `default_deny` / `degraded_fallback`）。`/env why`、WebUI、排障面板共用同一套解释——**"为什么这个人能执行这条命令"必须能回答**。

### 4.3 缓存与一致性

权限数据是**配置**（几百行），不是业务数据 → 直接物化到节点内存：

```
PermissionSnapshot {
  version: int
  operator_groups: frozenset[int]
  user_members:    dict[int, frozenset[int]]     # user_id    -> 权限组
  group_bindings:  dict[int, frozenset[int]]     # qq_group   -> 权限组
  grants:          dict[int, dict[str, Effect]]  # 权限组     -> {perm_key: (effect, expires_at)}
  user_blacklist:  frozenset[int]
  group_blacklist: frozenset[int]
}
```

- 判定 = 纯内存查表，微秒级、零 DB 压力（覆盖现有"每条只读命令都要查库/查缓存"的路径）。
- **一致性**：中控持有单调递增 `perm_version`；每次写入 `INCR` 并广播 `{version}`；节点拉取后**全量重载快照并原子替换**（数据量小，全量最简单可靠）；启动时全量加载 + 每 30 分钟对账一次。
- **版本自增即失效**：不再需要"记得清理哪些 key"，A1/A4/C6 一并消失。
- **会话态分家**：JWT 撤销集合、WebUI 临时登录码、登录限流计数搬到独立的 Redis 命名空间（`auth:*`），与判定缓存无关（修 A2）。
- **降级**（按场景声明，不再散落在调用点）：
  - 权限点判定（`permission_checker` / `check_permission`）：Redis 与 DB 都拿不到 → **fail-closed**。
  - 只读命令的黑名单闸门（`blacklist_guard`）：DB 抖动 → **fail-open**（保留现有产品语义：不该因 DB 抖动让所有只读命令对所有人失效）。
  - 快照拿不到但 DB 可用 → 直查 DB（返回 `reason_code=degraded_fallback` 并打指标）。

### 4.4 审计

`permission_audit`：

| 列 | 说明 |
|---|---|
| `id` / `ts` | |
| `actor_type` | `qq` / `webui` / `system` / `plugin` |
| `actor_id` | QQ 号；`system` 用于自动播种、迁移 |
| `action` | `add` / `remove` / `update` / `toggle` / `bind` / `unbind` / `migrate` / `auto_seed` |
| `target_type` / `target_id` | `user` / `group` / `permission_group` / `group_binding` / `feature` / `subscription` / `blacklist` |
| `before` / `after` | JSON（变更前后） |
| `reason` | 人写的理由（危险操作必填） |
| `trace_id` | 与路由决策日志同构，便于串联 |

**所有写入路径共用**这张表：中控 API、QQ 面板（经中控）、插件声明式 provisioning、迁移脚本、启动自愈。WebUI 增加"权限变更历史"页（按 actor / target / 时间过滤）。

### 4.5 护栏与恢复

1. **写入前置校验**：任何授予/撤销/删除操作后必须仍存在 ≥1 个有效操作员，否则拒绝——防自锁（修 B4 的后果）。
2. **启动自检**：操作组缺失 / 无成员 / 无对应管理权限点 → 从 `SUPERUSERS` 重新播种 + 写审计 + 告警（修 B5 的矛盾行为）。
3. **离线恢复命令**：不依赖 WebUI 与 QQ 面板（例如 `python -m <pkg>.recover --qq <号>`），用于两条在线通道都进不去的场景。
4. **危险操作分类**（强制审计 + 告警，理由必填，**且需二次确认**）：
   - 授予/撤销管理权限点
   - 增删操作组成员
   - 删除操作组、修改其 `role`
   - **群绑定到操作组**（一次影响全群，§2.2）
5. **二次确认只有一套机制**：发起危险操作 → 中控签发一次性 confirm token（绑定"发起人 + 操作摘要 + 过期时间"，30s）→ 机器人回复提示并引用该消息 → 发起人**引用回复**确认 → 中控校验 token 后执行。token 存 Redis（`ctl:confirm:*`，TTL 即过期），不用内存。
   - 同一套机制同时服务两类操作：**权限侧**（上表四类）与**路由侧**（`01` §6.3 的 `/env freeze`、不带群的 `/env route --plugin`，以及 `/env deploy`——它一次换掉整个节点的代码，`01` §6.2）。两侧的确认逻辑必须收口到同一份实现，否则会长出两套行为不一致的确认流程。
   - 契约落点：`packages/contracts` 的命令契约（`diting_contracts.commands`）需要包含 `confirm` 子命令（`node` / `route` / `rollback` / `freeze` / `resume` / `why` / `decisions` / `deploy` / **`confirm`**）。该契约随 contracts 包一起落地，**P1.2 做 `/env` 执行时就要把它加进去**，P2/P3 权限侧直接复用。

### 4.6 管理面

- **JWT 只证明身份**（`sub` = QQ 号 + 会话有效）；每个管理端点**声明所需权限点**，由求值器判定。**启动时校验所有端点都声明了权限**，漏声明即启动失败——避免"忘了加装饰器"这类回归。
- **认证与授权分离**：临时密码只解决"证明你是那个 QQ"，不再隐含管理员身份。
- **dev 登录默认关闭**，需显式开关；`ENVIRONMENT` 缺失时按 **prod** 处理（消除 C3 的降级敞口）。
- **登出写服务端撤销集合**（独立命名空间）；客户端门禁保持现状（它本来就是装饰，不作为防线）。
- 新增权限点用于管理面自身：`webui:logs:view` 等，避免"登录即看全部"。

### 4.7 单一写入点

**中控是唯一写入者**：

- QQ 面板命令仍在**节点内执行**（保证回复延迟与即时反馈），但写操作一律 POST 到中控权限服务，由中控校验、写库、审计、递增版本。
- 面板的**读取**走节点本地快照（快）。
- **插件 provisioning 改为声明式**：权限点与权限组写在 `PluginMetadata.extra["diting"]`，随 manifest 上报（契约见 `01-路由与灰度.md` §4.1、`03-插件契约与改造映射.md` §2）；节点只**声明**，由中控在节点注册时**对账与创建**；插件不再直写库。迁移期允许节点直写作为过渡，但必须走同一审计入口。

### 4.8 语义分离

### 4.10 与网关运维名单的边界

运维名单（环境切换 / 灰度 / 部署）由**中控维护**，网关只缓存（`ctl:ops_admins` + 版本号），中控不可达时用本地最后一次快照（`OPS_ADMINS_SNAPSHOT`）。**已拍板：与操作组完全独立**——

- **不做初始同步**：不再有"上线时从操作组成员灌一次"的动作，运维名单从第一刻起就是独立数据集（`OPS_ADMINS_SEED` 是人工填的初始名单，不是权限库的投影）。网关侧实现已经如此（`services/gateway/diting_gateway/ops_admins.py`：Redis → 本地快照 → 内联 env，全程不碰业务库）。
- **成员不互相牵连**：把某人设成操作员不会让他获得 `/env`；把某人加进运维名单也不会让他获得任何业务权限。两份数据不互相授权，避免"改一个忘一个"的第二个身份真相（D3）。
- **代价与必须补的护栏**（"完全独立"的直接后果，P1.2 起生效）：
  1. **名单为空 = 运维通道彻底关闭**。网关 `is_admin()` 对空名单一律返回 False（`ops_admins.py:63-67`），而这条路**再也回不到权限库兜底**。因此：中控侧写入必须拒绝"把名单清空"（与 §4.5 第 1 条的防自锁同类）；网关启动时名单为空必须**告警**而不是静默。
  2. **需要一条不依赖两条在线通道的恢复路径**：与 §4.5 第 3 条的离线恢复命令并列，运维名单也要有（例如直接写 `ctl_settings` + 重启中控）。否则最后一名运维退出登录后就永久锁死。
  3. **中控侧的持久化位置要定**：名单是控制面数据，落 `ctl_settings` 一条键（键值 JSON），变更写 `ctl_audit`（`action=ops_admins_update`）。仅靠网关本地的 `OPS_ADMINS_SNAPSHOT` 文件反推是错的——那是网关的缓存，不是真相。

**边界一句话**：**运维名单管基础设施动作**（`/env`、`/env deploy`），**权限库管业务命令**；审计分开记（运维名单 → `ctl_audit`，业务权限 → `permission_audit`），WebUI 上也是两个历史页。
