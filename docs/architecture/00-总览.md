# 00 · 总览

## 1. 现状事实（重构的起点）

技术栈：NoneBot2 2.4.4（`~fastapi` 驱动）+ OneBot V11 适配器 + FastAPI + MySQL(asyncmy) + Redis + React WebUI + APScheduler。
QQ 侧是 NapCat，以 reverse-WS 连到节点容器的 `/onebot/v11/ws`。

与本次重构直接相关的现状：

| 事实 | 出处 | 后果 |

| dev / prod 是两份独立 clone，各自一份 `.env` 与 systemd 执行器 | `docs/diting-deploy.md` §4.3 | 改配置/重启只能逐个环境做，没有统一入口 |

### 1.2 已拍板的前提（后续方案以此为准）

| 项 | 决定 |
|---|---|
| dev / prod 的 QQ 身份 | **同一个 QQ 号**。因此 `COMMAND_START=["dev-"]` 的前缀隔离可以直接删除，路由成为唯一的隔离手段 |
| 运维管理员名单 | **网关维护独立名单**（不查业务权限库），与操作组**完全独立**：不做初始同步、成员不互相牵连。代价是"名单为空 = 运维通道关闭"，需空名单护栏与离线恢复，见 `04-权限与授权设计.md` §4.10 |
| `diting_ctl` | 建在现有 MySQL 实例上（同实例、独立库名） |
| 监管与告警 | 告警目标只由 `ctl_settings` 给（群 / @ 名单 / 收件人）；出口是一条降级链 **L1 正常通道 → L2 NapCat HTTP 旁路 → L3 邮件**，规定"**只要还能发 QQ 消息就不用邮件**"；生产者按"谁先知道谁发"下沉（网关 / 中控 / 宿主 watchdog），节点不持有出口凭证（§6 决策 17、`01` §8.2） |
| `/diting` 部署命令 | 保留，P2 并入 `/env deploy` |
| 旧的两份 clone（服务器上现有的两个 NoneBot 容器） | **新架构验证通过之前不动**（含 NapCat 分流配置）；验证通过后整体废弃，全部服务转到新架构 |
| 白名单语义 | 并入管理员（`04` §2.1） |
| 群绑定语义 | 保留"绑定即全群管理员"，属刻意设计（`04` §2.2） |
| 群绑定到操作组 | **需二次确认**（引用回复确认，30s），与危险 `/env` 命令共用同一套 confirm token（`04` §4.5） |
| 原白名单群的功能开关 | **先对齐再渐进收紧**：迁移时逐 feature_key 置 `enabled=1` 保证行为不变，之后人工复核收紧；新增功能不自动开启（`04` §2.1） |
| 插件清单（manifest）的产生方式 | **内省导出 + 声明覆盖**，不做框架式 SDK；插件不改写法即可被路由与灰度（`03` §1～§3） |
| 调度的归属 | **排程元数据在中控（`ctl_jobs`），触发与执行在节点**；Redis 租约防双跑（`03` §6） |
| 网关的连接与投递语义 | 吸收 meta 事件；`lifecycle/connect` 由网关按节点连接**合成**且仅在上游可用时合成；上游断链则主动断开节点连接（带去抖）；事件**缓冲为主、丢弃兜底**（§6 决策 12、`01` §9） |
| 配置的存放 | **分四层**：编排进 git、启动与密钥进"每环境一份源 + 每服务投影"的 env、业务配置与插件参数进中控库（秒级热生效）。判定规则：要重启 → env，不要 → 中控库（§6 决策 14、`02` §2.0） |
| 默认节点故障时的取向 | **自动全量接管到 dev**，不要人工确认；用 `canary_deny_plugins` 的**运行期过滤**保住"不可逆动作不被未验证代码执行"这条底线（§6 决策 15、`01` §5.4） |
| 发布通道 | 节点由中控编排（`/env deploy`）；**网关与中控自身必须带外**（宿主机执行器 + systemd）；协议只允许向后兼容的变更（§6 决策 16、`02` §5.6/§9.1、`01` §9.10） |
| 事件流水的归属 | **网关采集、中控落库**：`event_logs` 覆盖除 `meta_event.heartbeat` 外的全部上报事件（含机器人自己发的消息）；`logging_info` 废弃删除，`messages_event_logs` 冻结为历史档案、不清理（§6 决策 13、`01` §8.5） |

## 2. 目标与非目标

**目标**

1. 双节点常驻、共用一套业务库，节点版本可以不同。
2. 按群、按插件、按群+插件三种粒度把流量引到指定节点；**群规则优先级高于插件规则**。
3. 命令行与 WebUI 两条切换途径，秒级生效，全量审计。
4. 节点异常（插件启动失败 / 心跳失联）自动回滚，且**只影响命中灰度规则的流量**。
5. 发布与引流解耦，让"上新功能—小范围试—全量/回滚"成为常规操作而非事故处理。

**非目标（本期明确不做）**

- 不做 k8s / 服务网格 / 多机分布式；单机 Docker Compose 足够。
- 不做特性开关（feature flag）体系——回滚后 dev 独有功能就是不可用，见 §6 决策 2。
- 不做 QQ 号级别或用户级别的灰度（粒度只到群与插件）。
- 不换掉 NoneBot 与 OneBot V11 适配器，节点仍是 NoneBot 应用。
- 不做数据库读写分离 / 分库分表。

## 3. 设计原则

1. **发布 ≠ 引流**。部署到哪个节点是一个动作，谁处理这条消息是另一个动作；两者可以独立进行、独立回滚。
2. **排他投递**。一条事件**物理上只进入一个节点**，不存在"两边都收到、各自判断该不该处理"的模糊状态。
3. **决策权不依赖被决策对象**。切换与回滚由网关/中控执行，节点全挂也能操作。
4. **节点无状态**。节点唯一的持久化依赖是共享 MySQL 与 Redis；容器可以随时删掉重建、按同一镜像起第 N 个。
5. **单一真相**。规则只有一个写入点（中控），管理面只有一个（中控 WebUI），节点之间的行为差异只能来自"版本"与"规则"。
6. **默认保守**。规则冲突、健康存疑、目标不可达时，一律选择对生产影响最小的那一侧。

**网络边界**

- NapCat 只能访问网关的 OneBot 入口，**不允许**再直连任何节点。
- 节点只暴露 `/healthz`、`/internal/manifest`、`/internal/job`、`/internal/selftest` 与 OneBot forward-WS 出站连接；节点不再对公网提供管理 API。
- 网关不写业务库（除决策日志），保持热路径轻量；它读 Redis 中的规则快照，重启即可恢复。

## 6. 关键决策记录（ADR 摘要）

### 决策 1：网关代理 OneBot（而不是两节点各自直连 NapCat）

- **选择**：NapCat 只连网关；节点以 forward-WS 主动连网关；网关把每个事件只投给一个节点，并代理节点发出的全部 API 调用。
- **理由**：切换与自动回滚必须在节点故障时仍然可用；排他投递从物理上消灭双跑；健康判定获得秒级传输层信号。
- **被否方案**：两节点都连 NapCat，各自查共享路由表决定是否处理。缺点：依赖 NapCat 多路 reverse-WS 的支持与广播行为（本项目无法在仓库内验证）；每个节点都要处理全量事件；控制命令必须依赖某个节点存活。
- **可行性依据**（已核对适配器源码）：forward-WS 的 URL 原样使用，可带自定义路径与查询串；连接握手带 `Authorization: Bearer`；API 调用用 `echo` 关联请求与响应，因此单条 NapCat 连接上多路复用两个节点是安全的；适配器只在收到 `lifecycle/connect` 元事件时才建立 `self_id` 与 Bot 实例，网关必须在投递业务事件前先下发该事件。

### 决策 2：简单回滚（不做特性开关）

- **选择**：dev 跑新代码，prod 跑上一个稳定版本。回滚 = 把流量引回 prod；dev 独有功能在它上线 prod 前不可用，用户侧看到统一话术。
- **理由**：不需要给每个新功能加开关，落地快，与现有发布方式一致。
- **代价与护栏**：回滚解决的是**稳定性**，不是**可用性**。因此必须配：(a) prod 侧未知命令的兜底话术；(b) 高危插件禁止被引流（`canary_policy=deny`）；(c) 回滚后自动通知受影响群的负责人。
- **升级路径**：若日后需要"回滚后功能仍可用"，再引入"新代码先上 prod、开关关闭"的暗发布模式，届时路由与 override 模型不需要改动。
- **例外**：这条取向在"默认节点自己挂了"时不适用——那时没有"稳定版本"可回，取自动全量接管（决策 15）。

### 决策 3：取消 env_tag，单一数据集

- **选择**：灰度期间写的就是真实数据；新表不带环境标记，老表随插件重写逐步摘除。
- **理由**：否则"灰度 → 回滚"会让用户在灰度期间产生的数据（订阅、记录、统计）全部消失，体验断裂，也让灰度验证失真。
- **风险与护栏**：dev 代码会直接写生产数据。护栏 = 变更前自动逻辑备份 + 高危插件禁灰度 + 灰度范围先小后大 + 回滚后数据一致性巡检。
- **过渡**：仍带 `env_tag` 的老表，由运行时的 DB 封装统一注入固定值（`prod`），使两节点读到同一份数据；列本身在对应插件重写完成后再删。

### 决策 4：管理面全部迁到中控

- **选择**：WebUI、权限管理 API、日志/统计接口全部由中控托管；节点只保留业务与内部接口。
- **理由**：管理面与业务面解耦，节点宕机不影响看状态、改规则、查日志；避免"两个 UI、两个真相"。
- **代价**：现有 `src/api/**` 与 `webui/` 需要迁移，工作量集中在 P2。

### 决策 5：节点以 forward-WS 主动连网关

- **选择**：节点配置 `DRIVER=~fastapi+~websocket` + `ONEBOT_V11_WS_URLS=["ws://gateway:8100/onebot/v11/node?node=dev"]`。
- **理由**：节点自己负责重连与注册，网关不需要知道节点的地址；节点身份由其连接时声明的 `node` 参数确定；节点重启后自动回归，无需网关侧干预。
- **备选**：网关主动连节点的 reverse 路由（协议等价，但网关需要维护节点地址表与重连逻辑）。实现时若发现 forward 模式在适配器上有阻塞（详见 §8 待验证项），切到该备选不影响其他设计。

### 决策 6：控制命令由网关本地执行

- **选择**：`/env ...` 系列命令在网关拦截并执行，不投递给任何节点。
- **理由**：这是"节点全挂也能切回 prod"的前提；也避免控制命令本身被路由规则影响（否则可能出现"dev 的规则把回滚命令送到了 dev"的死锁）。
- **代价**：网关需要一份管理员名单（由中控下发并缓存），以及一个最小的命令解析器（见 `01-路由与灰度.md` §6）。

### 决策 7：单仓多服务（monorepo），不做多仓拆分

- **选择**：网关、中控、节点、契约包（`contracts` / `plugin-kit`）、WebUI 全部在现有仓库内，按 `services/` `packages/` `apps/` `webui/` `deploy/` `docs/` 划分；**单仓不等于单部署单元**——每个服务独立镜像、独立 tag、独立 CI job、独立重启。
- **理由**：
  1. 契约（路由规则模型、manifest schema、决策 DTO）在 P1~P3 会反复改，跨仓会在最不稳定的阶段引入"发版 → 升版本 → 三仓对齐"的成本。
  2. 规则引擎必须只有一份实现（见决策 8），跨仓就得靠版本对齐保证一致。
  3. 业务插件是同进程加载进节点的，**不是独立部署单元**，多仓在这里买不到任何独立性。
  4. 现有部署链（`scripts/diting-agent.sh` 是"单目录 git pull + build"）多仓会让 checkout、`pull.lock` 哨兵、systemd 单元成倍增加。
- **单仓必须守的边界纪律**（由 CI 强制，否则以后想拆也拆不动）：
  - `services/*` 不得 import `apps/*`；业务插件只允许 import `packages/sdk`。
  - `packages/contracts` 单独成包（规则模型、决策 DTO、manifest schema），改它必须同时改网关/中控/节点三处调用方。
  - 禁止跨层直接读写对方的表或文件：中控与网关之间只有 Redis 快照 + HTTP 两种交互。
- **拆仓触发条件**（满足任一再拆）：出现第二个消费方（同工作区的 `course-bot` / `QingLuan` / `Shiro` / `maomao-bot` 等若接入同一套网关 + 中控 + plugin-kit）；网关/中控进入冻结期而插件高频变更；多人并行出现"改网关必须等插件仓合并"的互相阻塞；CI 时长成为实际痛点。
- **真要拆时的拆法**：只拆**两仓**——`diting-platform`（gateway + control + contracts + plugin-kit + webui）与 `diting-bot`（node 运行时 + 业务插件）；前提是 contracts 已冻结、plugin-kit 可发版、bot 仓 pin 平台版本。**禁止按服务数量拆**（gateway 一仓、control 一仓……），那会让一次契约变更牵扯四个仓。

### 决策 8：全栈 Python，不给网关换语言

- **选择**：网关、中控、节点全部 Python；重型计算也用 Python，但放在**独立进程或独立服务**里。
- **理由**：
  1. **量级不成立**：Python 网关单事件约 0.2~0.5 ms，Go 约 0.05~0.1 ms，省下约 0.3 ms；而端到端里 QQ ↔ NapCat 往返是数十到数百毫秒、渲染 0.3~2 s、LLM 秒级。用户不可测也不可感。
  2. **单实现原则**：规则解析要被三处使用且必须逐位一致——网关执行路由、中控的生效预览、`/env why` 决策解释（见 `01-路由与灰度.md` §7）。跨语言等于把层级排序、冲突裁决、override 叠加写两遍，漂移的后果是"预览说走 dev、线上走 prod"。
  3. **网关必须单进程**（WS 连接与 `echo` 映射都在进程内），用不上多核，所以"换编译型语言吃满多核"这个理由在这里不适用。Python 单进程 asyncio 纯路由可处理几千事件/秒，而单账号群机器人峰值通常只有个位数到几十事件/秒。
- **代价与配套约束**：性能工作转移到"把阻塞移出 NoneBot 事件循环"，硬要求、存量问题清单与镜像瘦身收益见 `02-部署与运维.md` §1.3；事件循环延迟纳入心跳指标，见 `01-路由与灰度.md` §5.2。

### 决策 9：权限系统保留模型、重写求值与管理面

- **选择**：删掉两张白名单表（语义并入"操作员"），保留 7 张表并加列（`role` / `effect` / `expires_at`），新增 `group_features` / `subscriptions` / `permission_audit`；重写求值链（五步 + 一次快照 + 可解释）、缓存（节点内存快照 + 版本号）、审计、管理面鉴权（JWT 只证明身份）；中控成为唯一写入者。三个对外入口 `check_permission` / `permission_checker` / `blacklist_guard` **签名不变**，38 个业务插件零改动。
- **理由**：
  1. 模型本身够用（权限点 / 权限组 / 成员 / 绑定 / 黑名单），且数据必须保留；问题全在求值路径与管理面。
  2. 现缓存是进程内的（`cache.py:4` 明写单进程假设），双节点下同一用户判定可不同长达 60s——这是硬伤，不是优化项。
  3. 权限变更是**零审计**的（REST/WebUI 写入完全无日志），而它决定"谁能执行部署命令"，重要性与路由变更相当。
  4. 白名单与管理员语义重复，合并后求值链从七步降到五步，同时消掉一条"加白名单即可通过管理员门槛"的链路。
- **已定的两条策略**：白名单 = 管理员；群绑定 = 全群管理员（刻意设计）。二者都要求审计，详见 `04-权限与授权设计.md`。
- **不做的**：不推倒数据模型、不引入 RBAC/ABAC 之类的新范式、不改插件侧调用方式。

### 决策 10：插件清单由内省导出，不做框架式 SDK

- **选择**：节点启动时遍历 NoneBot 注册表（`Plugin.matcher` → `Matcher.rule.checkers` → `Dependent.call` → `CommandRule.cmds` / `KeywordsRule.keywords` / `RegexRule.regex`）自动生成 manifest；语义元数据（`canary_policy` / `critical` / `topics` / 权限点 / opaque 补声明）写在 `PluginMetadata.extra["diting"]`；横切能力（权限闸、trace、限流、慢 handler 计时、兜底话术）由**全局中间件**提供。**插件不 import 任何 diting 包也能被路由与灰度。**
- **理由**：
  1. **声明与行为不可能漂移**。框架式 SDK 的 `business_command()` 是手写的第二份真相；漏声明/忘同步的失败模式正好打在核心目标上——新命令网关不认识 → 流量回 prod → 灰度期用户看到"功能不存在"，灰度验证失真。内省从 matcher 本身读，不存在这个失败模式。
  2. **插件级灰度不再以"重写 38 个插件"为前置条件**。内省覆盖约 97% 的 matcher，P2 即可开始插件级灰度；P3 从"必做重写"降级为"按需改造"，重写只在有具体能力/性能理由时做（`03 §7`）。
  3. **生态与可逆**：第三方插件用标准 matcher 就自动可路由；插件不被锁死在 diting 平台上，平台也不必维护一套与 NoneBot 官方文档对不上的 API。
  4. 框架式 SDK 的其余职责（权限闸、trace、限流、兜底话术、幂等键）用中间件实现——一次生效、无法被插件作者遗忘。
- **代价与护栏**：内省依赖 NoneBot 内部结构（清单见 `03 §3.4`）→ pin 版本 + CI 断言测试（`tests/test_manifest_exporter.py`）+ 启动覆盖率报告（message 类 opaque 会告警）；真断裂时退回 `extra` 声明，**manifest schema 与整体架构不变**。网关分类器必须与节点判定逐位一致 → 对拍测试 + 影子期真实流量回放（`01 §4.4`）。
- **被否的是"框架"，不是"契约"**：薄契约（manifest schema、`extra` 字段、`resolve_route`、幂等键 helper）保留，`packages/plugin-kit` 仍在，只是它不再要求插件改变写法。

### 决策 11：调度取混合形态（排程在中控，触发与执行在节点）

- **选择**：`ctl_jobs` 在中控登记 cron 与目标群来源（可审计、WebUI 可改可启停）；**触发与执行在节点**（本地 APScheduler，进程内调用）；目标群按**与网关同一份路由决策**筛选"归我的群"；Redis 按 `(job_id, group_id, run_key)` 租约防双跑；结果上报中控。动态 `run_date` 任务保持进程内写法。
- **理由**：
  1. 拿满"中控持有 cron 并派发"的关键收益：可运维、可审计、**被灰度的群其定时推送跑 dev 的代码**（这才是细颗粒度灰度在定时任务上的延伸）；
  2. 但**不把中控放进"任务能否发生"的关键路径**——中控挂掉时任务照常触发，只是改不了排程，与 `02 §10` 的可用性设计一致；
  3. 避免"中控派发 + 节点兜底调度 + 切换判据"这套**两套实现**（原设计的节点兜底"默认关闭以防双跑"，等于承认中控长时间挂掉时任务不跑）；
  4. 改造量小：现有注册点已带显式 `id=`，取群统一走 `get_bound_group_ids`（8 个插件 13 处），替换为 `my_groups` 即可，动态任务写法不动。
- **代价**：节点多读一份规则快照（与权限快照同机制）；Redis 故障时租约不可用 → 默认 **fail-closed**（跳过 + 告警 + 可手动补跑），`ctl_settings.job_lease_fail_mode` 可切 fail-open。
- **顺带废弃**：用 env 开关错开调度（`.env.dev` 的 `CHECK_UP_ENABLE=false`、`CLIST_SCHEDULE_JOB_ENABLE=false` 等）——它与"灰度期间 dev 要跑它负责的群"直接冲突，由 `ctl_jobs.enabled` 取代。

### 决策 12：网关的连接与投递语义

- **选择**：网关独占上行链路，并对每条节点连接维护一套状态机（`connecting` / `handshaking` / `online` / `draining`），其中四条语义一次定死：
  1. **meta 事件全部由网关吸收**（`heartbeat` / `lifecycle.enable` / `lifecycle.disable` / 未知类型），不投递；
  2. 节点侧需要的 `lifecycle/connect` 由网关**按节点连接合成**，且**只在上行可用时**合成；
  3. 上行断链超过去抖窗口（`NAPCAT_LINK_DEBOUNCE_SECONDS`，默认 10s）则**主动断开全部节点连接**，让节点走重连；
  4. 目标节点不在 `online` 时，事件进**缓冲**（`NODE_BUFFER_SECONDS` / `NODE_BUFFER_MAX_EVENTS`），超限或过期才丢弃并计入 `dropped`；flush 时**重算路由**。
  完整状态机、`echo` 重写规则与失败结算见 `01-路由与灰度.md` §9。
- **理由**：
  1. **这些不是可自由设计的部分**。节点在收到 `lifecycle/connect` 之前不建 Bot、不设 `self_id`，且此前到达的一切被静默丢弃（`adapter.py:349-364`）——所以"先连上就投递"是全部丢且不可观测；而两个节点进程的 API 计数器都从 1 开始（`store.py:13`），共享一条上行链路时 `echo` **必然重复**，重写是正确性要求而非优化。
  2. **吸收 meta 是安全的**：全包核查确认 nonebot 里没有任何代码消费 `heartbeat`/`lifecycle`，本项目也没有 meta 订阅；把它们投给节点只会污染事件量指标。
  3. **断链即断开节点连接，是为了保住今天的自愈语义**：群名册同步、群名片重设、全量文件爬取、`daily_crawl` 刷新 bot 实例这四件事都挂在 `on_bot_connect` 上（`group_file_manager/hooks.py:47-104`、`group_card_changer/__init__.py:100-107`、`rate_limiter_middleware/middleware.py:357-360`），靠"重连"这个动作触发。保持连接不断开会把它们退化成"仅进程启动时一次"，并且群名册是**静默**变旧。
  4. **缓冲为主是"不丢消息"与"不乱序"之间的最小代价**：重连窗口只有 3s（`RECONNECT_INTERVAL`），缓冲能覆盖；而丢弃兜底保证网关不会因为一个卡死的节点把内存吃满。
- **被否方案：保持节点连接不断开**。节点完全无感、不放大抖动，但那四项自愈机制同时失效，需要另建定时机制补上——那是 P3 的插件改造工作量，与"不改插件就能灰度"的取向冲突。
- **代价与护栏**：
  - 断链会放大抖动（NapCat 反复抖 → 两端反复全量爬取）。今天的直连模式同样如此，去抖窗口只是把秒级抖动挡在外面。
  - `NODE_BUFFER_SECONDS=10` 意味着最坏情况下用户会晚 10s 收到回复；缓冲溢出与过期的计数进 `gateway_events_dropped_total{reason}` 并告警。
  - **已知例外**：`group_send` 与 `shit_transport` 直连 NapCat 的 HTTP 控制 API（6097），绕过网关的 trace / 限流 / 决策日志；P1~P3 保留，P3 评估改造（`01` §9.8）。

### 决策 13：事件流水由网关采集、中控落库

- **选择**：新增 `event_logs`（业务库，中控唯一写入者），覆盖**除 `meta_event.heartbeat` 以外的全部上报事件**，含机器人自己发送的消息；网关在事件终结时批量上报，中控落库。`messages_event_logs` 冻结为历史档案（"时光机"），`logging_info` 插件在新链路稳定后删除。
- **理由**：① 只有网关看得全——被丢弃、降级的事件（`no_target` / `buffer_overflow` / `buffer_expired`）在任何节点上都不存在，今天是纯空白；② 双节点写同一张表只能靠 `message_id` 唯一约束兜底，而 `logging_info` 的 `IntegrityError` 分支是注释掉的（`message_dao.py:68-70`），重复投递会变成错误日志刷屏；③ 机器人自己发的消息只有这一层拿得到（`reportSelfMessage` 按连接开关，网关只有一个连接）；④ 落库不进网关，热路径不受 DB 抖动影响，与"网关不写业务库"的既有边界一致。
- **被否方案**：① 保持节点写入、只扩展覆盖率——被丢弃的事件永远记不到，且两个节点都是写者；② 网关直连业务库——要给网关发业务库凭证、把迁移纪律搬到网关，还让慢查询顶在事件循环上；③ 就地扩展 `messages_event_logs`（改列 + 放宽唯一约束）——要连带改 `src/api/groups.py` 的聚合（它没有 post_type 过滤，notice 混入会让群活跃度静默虚高）与 `src/api/logs.py`，还要给 46 万行的表加列，代价高于新建一张宽表。
- **代价与护栏**：流水滞后于投递（最多一个缓冲窗口），网关崩溃时在途事件丢失——而那些事件本来也没投递出去，不影响行为；`event_logs` 覆盖全事件后增长按 1.5~3 倍预期，**保留期尚未定**（建议先跑一个月看增速，`01` §8.5）。

### 决策 14：配置分层（编排进 git、密钥进每服务 env、业务配置进中控库）

- **选择**：配置分四层——A 编排（compose + 键清单，进 git）、B 启动与密钥（每服务一份 env，不进 git）、C 业务配置（中控库 `ctl_*` + WebUI / `/env`，秒级热生效）、D 插件参数（同上，P3 从 B 迁入）。判定规则：**要重启进程 → env；不要 → 中控库**。B 层由"每环境一份人工维护的源文件"渲染成每服务一份，服务只拿到自己的键（`02` §2.0）；源文件放在**主机上的无远端 git 仓**——有版本、有 diff、可回滚，但没有远端就没有扩散面（`02` §2.4），需要跨机分发时才评估加密的私密仓库。
- **理由**：① **服务边界要落在进程里**——网关不持有 `BIZ_DB_*`，否则"网关不写业务库"只是文档承诺；② 今天 114 个键的 env 里绝大多数是运行期可变的业务参数（`CHECK_UP_ENABLE`、`LIKE_AUTO_SEND_LIKE`、`AUTO_MANAGE_*`……），改一次要重启、两端各改一遍、无审计，这正是"配置"变成负担的原因；③ 单仓多服务后同目录跑多环境，"读到哪份 env"需要结构性护栏而不是靠人记得——今天不冲突，只是因为两份 clone 是两个目录；④ 现状已经出了真问题：dev/prod 键集合漂移（5 个死键只存在于 prod）、缺 `WEBUI_JWT_SECRET` 导致重启即掉登录态、三套加载器、基础 `.env` 压过 `.env.<env>`（`02` §2.4）。
- **被否方案**：① 保持"一份共用 env"——边界靠自觉，任一处笔误影响全部服务；② 换成 YAML/TOML——不解决分层问题，只多一个解析层，而 `.env` 有 `--env-file` / `EnvironmentFile=` 的原生支持；③ 引入 Vault——单机单账号场景不值得多一个"必须活着否则机器人起不来"的组件，升级路径留在 `02` §2.4。
- **代价与护栏**：多一层"源文件 → 每服务 env"的渲染，必须封进脚本而不是手工执行；护栏是启动指纹上报（只含键名与非密值哈希）+ `NODE_NAME` 冲突告警——同机双环境最可能的错是"dev 读了 prod 的 env"。

### 决策 15：默认节点故障取自动全量接管（反转原取向）

- **选择**：默认节点（prod）`unhealthy` / `not_ready` 时**自动**把全量流量接管到 dev，不再要求人工确认，也不再需要"是否允许接管"的许可开关（`emergency_takeover` 降级为 kill-switch，默认 `true`）。三道护栏：接管者必须 `ready`；接管期间把 `canary_deny_plugins` 从"写规则时校验"扩展为**运行期过滤器**（执行点在网关），不可逆动作一律不交给未验证代码；回切取**自动 + 单向粘滞**（默认节点恢复且稳定 60s、未 `locked` 才回切；再次异常则保持接管并标 `locked`，转人工）。**计划内重启（部署窗口）不触发接管**（`02 §5.0`）。完整语义见 `01 §5.4`。
- **理由**：① 群机器人的"完全沉默"会被当成机器人挂了/被封了，报障与影响面大于"能回话但可能在未验证代码上出错"；② 灰度的价值是**不可逆的错误不会第一次就发生在生产**——全量接管会让所有人跑未发布代码（这一条无法避免），但这条底线可以用拒绝清单保住；③ 决策 3（取消 `env_tag`、单一数据集）让接管在数据层面是安全的：两节点本来就操作同一份真实数据；④ 1 小时人工确认把自动化退化成半自动——凌晨三点没人确认，等于没接管，还留下"接管晚了一小时"的常态。
- **被否方案**：① 保持原设计"不让 dev 接管 + 降级话术"——完全沉默，而且"无路可走的流量回降级话术"在默认节点进程已死时根本发不出去（兜底话术 matcher 在节点侧，`01 §5.6`）；② 自动接管但不禁高危插件——未验证代码在 `mass_kick` / `group_ban` / `group_send` 上一次失误就不可撤销，等于拿不可逆错误换可用性；③ 把常驻第三节点 `standby-1` 作为唯一接管路径——最安全（同 tag），但单账号场景不值得常驻一个容器，留作上 prod 前的建议项（`02 §5.4`）。
- **代价与护栏**：接管期间灰度保护失效，且**接管窗口的运行数据不能当作灰度验收证据**（被拒绝的插件路径未被验证、用户报障会被归因到"prod 挂了"而不是新代码）；被拒绝插件的定时任务在接管期间同样跳过（`03 §6.6`）；接管与回切都带粘滞，"接管后停很久"是预期行为而非遗漏。

### 决策 16：发布通道的边界与跨版本契约

- **选择**：① **节点的发布可由中控编排**（`/env deploy`，P2 起），**网关与中控自身的发布必须带外**（宿主机执行器 + systemd，不经中控也不经 `/env`）；② 服务间协议只允许**向后兼容**的变更（加可选字段、加接口），必须成对变更时网关只能在灰度窗口之外发布；③ 发布顺序取**中控 → 网关 → 节点**（在兼容前提下）。
- **理由**：① 用一个可能已经挂掉的组件去发布它自己是不成立的——`/env` 命令由网关本地执行、中控编排与告警都经网关，所以"中控编排一切"在中控或网关故障时正好失效；② 灰度窗口里两个节点本来就可能跑不同 tag，而发布是逐服务替换容器，**任意两个版本一定会在某个时刻共存**，兼容性是常态要求；③ 网关重启会断开全部节点连接（`01` §9.9），顺序错了等于把两次影响叠在一起。
- **被否方案**：① 全部由中控编排（含它自己）——中控挂着时无法发布任何东西，还得给它打"重启后自我豁免"这类补丁；② 要求"一次发布必须同时替换所有服务"——与灰度目标（让版本共存）直接冲突；③ 发布前先 freeze 全部流量换确定性——那是拿可用性换，而 `02 §5.0` 的部署窗口用更小的代价解决了同一个问题。
- **代价与护栏**：带外发布的可见性弱于 `/env`（没有命令回执）→ 靠 `ctl_deployments` 记录与心跳里的 `git_sha` 兜住（发布后必须核对一次，`02` §5.6）；兼容性靠 CI 契约测试兜底（`02` §9 第 5 条），**升级 nonebot 或改协议必须先过**。

### 决策 17：监管与告警改成"分级 + 出口降级链 + 生产者下沉"

- **选择**：① **只要还能发出 QQ 消息就不用邮件**——网关挂了而 NapCat 还活着，就直接从旁路 HTTP 控制口发到群；邮件只在 QQ 通道自身不可用时使用（NapCat 挂、账号被禁言或风控、发送拿不到回执）。② 出口是一条固定降级链 **L1 正常通道 → L2 NapCat HTTP 旁路 → L3 邮件**，**降级判据是回执**（`retcode=0` 且有 `message_id`）而不是"请求已发出"。③ 生产者按"**谁先知道谁发**"下沉：网关管链路与投递、中控管语义与对账、宿主 watchdog 管进程与整机，**节点只上报事实、不持有出口凭证**。④ 告警是**状态**不是事件流：`dedup_key` 进入/恢复各通知一次，配三条抑制（启动静默期 60s、父子抑制、同源合并）。⑤ 分级路由：`critical` 到管理群 + @ 告警名单、`warning` 到管理群不 @、`info` 到管理群（可降为仅 WebUI），群不可达才退邮件；**告警目标只有 `ctl_settings` 一个来源**（env 里的 `ALERT_GROUP_IDS` 取消），@ 名单不复用 `ops_admins`。出口凭证收口到宿主侧的 `diting-notify`。
- **理由**：① 原设计是"中控生成 → 网关投递"，**中控挂或网关挂都会让告警整体沉默**，而这两种恰恰最需要告警（网关挂时连降级话术都发不出去）；② 原来的"带外"等于"离开 QQ"，只要 NapCat 活着就没道理绕开它——带外应当定义为"离开**出故障的那个组件**"，三个组件各有一条出口就覆盖了所有单点组合；③ 没有回执判据，"NapCat 活着但账号被禁言"会变成静默失败，正是最该被告警的那类；④ 没有状态与抑制，一次 NapCat 抖动会让群里同时出现三四条因果相扣的告警，最后没人看。
- **被否方案**：① 保持"中控生成 + SMTP 兜底"——正好在最需要它的两种故障下失效；② 让节点也能发告警——跑业务代码的容器最不该握着能对外发消息的令牌；③ 把出口实现在网关里（它本来就连着 NapCat）——网关自己挂时又没了，而且会把控制面代码混进热路径进程；④ 告警按事件流逐条发——一条心跳缺失每 5s 报一次，群里没法看。
- **代价与护栏**：多一个宿主侧组件与一处要维护的凭证位置（`diting-notify`，`02` §2.5）；旁路出口沿用 §9 那条"已知例外"（绕开 `trace_id`、限流与决策日志，`01` §9.8），因此只允许它发固定文案、不与业务旁路混用；**整机与网络故障仍然覆盖不到**（SMTP 客户端与 NapCat 同机），只有外部探针（L0）能发现。触发清单、抑制表与收件人见 `01` §8.2。

## 7. 一条消息的完整旅程

```
QQ 群消息
  │
  ├─① NapCat 经 reverse-WS 送到网关
  │
  ├─② 网关分拣
  │     ├─ 是控制命令 且 发送者在管理员名单 → 网关本地执行 → 直接回执（结束）
  │     └─ 否则继续
  │
  ├─③ 规则解析
  │     群规则 → 插件规则 → 默认节点，叠加 override（人工冻结 / 自动回滚）
  │     产出：{target_node, rule_id, trace_id}
  │
  ├─④ 投递（状态机见 01 §9）
  │     ├─ 目标节点 online → 经该节点的 forward-WS 连接下发事件
  │     ├─ 目标在 connecting / handshaking / draining → 进该节点的事件缓冲，恢复后重算路由再投（01 §9.5）
  │     └─ 目标不可用（不健康 / 被禁用）→ 灰度的改投默认节点；**默认节点自己故障时全量接管到 dev**（拒绝清单命中的不投、回"故障恢复期间暂停"，01 §5.4）；无接管者则回网关话术；其余丢弃并记 dropped（01 §5、§9.5）
  │
  ├─⑤ 节点处理（NoneBot 插件）
  │     业务逻辑 → 发送动作经同一条 WS 回到网关 → 网关改写 echo 后转发给 NapCat → 响应按映射回传节点（01 §9.6）
  │     权限闸 / trace / 限流 / 慢 handler 计时 / 幂等键由全局中间件挂载，插件写法不变
  │
  └─⑥ 记录
        网关写决策日志（trace_id、命中规则、目标节点、耗时、是否降级、delivery_result 含缓冲与丢弃原因）
        网关把事件原文与投递结果上报中控，中控写事件流水 event_logs（01 §8.5）
        节点写运行日志（service / node / version / plugin / trace_id 由中间件注入，`01 §8.4`）
        中控聚合指标，并按 §8.2 的抑制规则产出告警（生产者按"谁先知道谁发"分工：链路级由网关、语义级由中控、进程级由宿主 watchdog；出口走 L1→L2→L3 降级链）
```

## 8. 待验证项与影子期（P1.0）

**已核实的前提**：这个版本的 NapCat 原生支持多路 reverse-WS —— `network.websocketClients` 是**数组**（每个元素含 `name` / `enable` / `url` / `token` / `messagePostFormat` / `reportSelfMessage` / `reconnectInterval` / `heartInterval`，见 NapCat 源码 `packages/napcat-onebot/config/config.ts:74-79`）。

因此 P1.0 可以做成**零风险的影子期**：在保留现有 prod 节点连接的同时，把网关作为**额外的** `websocketClient` 加进 NapCat，网关以 **observe-only** 模式运行——接收事件、算路由决策、写决策日志，但**不投递**给任何节点、不发任何消息。真实流量下验证协议与决策，线上行为完全不变。

下表 10 项全部通过（并连续跑 2~3 天无异常）才进入 P1.1 接管入口：

| 项 | 影子期的验证动作 | 若失败的退路 |
|---|---|---|
| 节点 forward-WS 与 `/onebot/v11/ws` reverse 路由并存时的行为 | 起一个临时节点同时配两者，观察 bot 实例与 self_id 是否唯一 | 关闭 reverse 路由（应急注入改为别的通道） |
| 适配器对事件 JSON 中未知扩展字段的容忍度 | 在投递给临时节点的事件里加 `_gateway` 字段，并在节点侧确认**能读回**（`extra="allow"` 已核实，不会解析异常；要验的是可用性） | trace 只留在网关侧，节点中间件换通道取 trace |
| 网关代理连接期 API 的时序（真实场景是 `get_group_list`——`group_file_manager/hooks.py:53` 在 connect 时立刻调用） | 临时节点启动后立刻调 `bot.call_api`，观察响应与 echo 关联 | 合成 connect 前先自行探活 NapCat，确认可代理再发 |
| 上游断链 → 节点连接断开 → 重连后自愈钩子重跑 | kill NapCat 超过 `NAPCAT_LINK_DEBOUNCE_SECONDS`，观察两节点各自重连、三处 `on_bot_connect` 副作用各跑一次且无重复爬取风暴 | 延长去抖窗口；必要时在 P3 把全量爬取移出 connect |
| `echo` 重写映射（**冲突是确定的**：两个节点进程的 `_seq` 都从 1 开始，`01 §9.6`） | 两节点各 250 次并发调用，并构造乱序、超时、上行断链，验证回包全部归位、无孤儿、在途请求被主动结算 | **无退路**——重写是正确性要求，不过就不能接管入口 |
| `lifecycle/connect` 的合成时序 | 让节点先连网关、NapCat 后连（以及反过来），确认节点在收到 connect 之前不建 Bot、期间事件进缓冲而非丢失 | 上游未就绪时不合成 connect，节点保持 `handshaking`（`01 §9.3`） |
| 缓冲与丢弃的边界 | 停掉一个节点 30s 后恢复：事件按序投递、`buffered_ms` 正确、超限部分记 `dropped:buffer_overflow` 并告警 | 调整 `NODE_BUFFER_SECONDS` / `NODE_BUFFER_MAX_EVENTS` |
| meta 事件吸收后节点行为不变 | 确认节点侧收不到 meta 事件，但读写、群列表刷新、限速补丁全部正常 | 若发现某插件依赖 meta（当前全仓无订阅），改为转发 `heartbeat` |
| 配置隔离与指纹 | 按 `02` §2.0 的布局在同一台机器上起两套（或至少两个节点实例）：各自读到正确的 env（指纹与 `env_file` 上报一致）、`/healthz` 的指纹不含任何密钥值、故意把 dev 的 env 指向 prod 时报 `NODE_NAME` 冲突告警 | 退回"每环境独立目录"（今天的形态），接受手工同步成本 |
| 监管出口的可用性 | 按 `02` §12 的演练 23 / 27 / 28 / 29 跑一遍：`alert_sent_total{channel}` 的三种取值都出现过、kill 网关时告警经**旁路**到达群而不是邮件、去重与父子抑制生效、网关自报不污染 `gateway_api_proxy_orphan_total` | 至少保住 L2；退路是"邮件兜底"并把该限制写进 runbook（`01` §8.2） |

影子期同时产出三件副产品：**决策日志**（用真实流量验证规则解析，可与 `messages_event_logs` 回放结果对账，并用于分类器对拍）、**节点 manifest 的真实样本**（内省导出，供插件级路由在 P2 直接使用）与**覆盖率报告**（列出无法内省的 matcher，据此决定哪些插件需要补声明）。

## 9. 术语表

| 术语 | 含义 |
|---|---|
| 节点（node） | 一个跑业务插件的 NoneBot 实例，逻辑名如 `prod` / `dev` / `standby-1` |
| 网关（gateway） | 独占 QQ 连接、按规则把事件投递给唯一节点的常驻服务 |
| 中控（control） | 规则、健康、审计、调度、管理面的唯一宿主 |
| 规则（route rule） | 「什么流量走哪个节点」的一条声明，见 `01` §2 |
| override | 在规则之上叠加的强制改投（人工冻结 dev / 异常自动回滚） |
| 灰度（canary） | 把一部分流量（某个群或某个插件）引到 dev 节点的状态 |
| manifest | 节点上报的插件清单：触发词（内省导出）、语义声明（`extra`）、覆盖率自述与定时任务索引；网关据此把消息归类到插件（`01` §4） |
| 内省导出 | 节点遍历 NoneBot 注册表自动生成清单的机制；触发词来自 matcher 本身，不是手写声明，因此不会漂移（`03` §3） |
| 覆盖率报告 | manifest 的 `coverage` 段：多少 matcher 已归类、哪些是 opaque（无法内省，需补声明或标不进灰度） |
| 分类器（classifier） | 网关侧复刻 NoneBot 匹配语义的"消息 → 插件集合"实现，必须与节点判定逐位一致（`01` §4.4） |
| 租约（lease） | 定时任务的跨节点互斥：`ctl:job_lease:{job_id}:{group_id}:{run_key}`（`03` §6.3） |
| 兜底话术 | 回滚期间对"仅存在于另一节点的插件命令"的统一回复，由全局 matcher 提供，不是每个插件的义务 |
| trace_id | 一条事件从入站到回包的唯一标识，用于串联决策日志与运行日志（`01 §8.4`） |
| 上行链路 / 下行连接 | 上行链路指网关到 NapCat 的那一条独占连接；下行连接指每个节点连到网关的 forward-WS（`01` §9.1） |
| 握手（handshaking） | 节点 WS 已建立、但网关**尚未**合成 `lifecycle/connect` 的状态；期间到达的事件进缓冲而不是投递（`01` §9.3） |
| 事件缓冲 | 目标节点不在 `online` 时的事件等待区，每节点一条 FIFO，超时或超限即丢弃并计数（`01` §9.5） |
| echo 重写 | 网关代理节点 API 调用时替换 `echo`，使一条 NapCat 连接上两个节点的请求互不干扰（`01` §9.6） |
| 旁路 | 节点直连 NapCat HTTP 控制 API 的通路（`group_send` / `shit_transport`），绕过网关，已知例外（`01` §9.8） |
| 键归属表 | 每服务一份的配置模型：声明该服务**允许拿到**哪些键。渲染脚本据此生成每服务 env，服务启动时按它校验（`02` §2.0） |
| 配置指纹（config_fingerprint） | 启动时对生效配置的键名与非密值算出的哈希，随心跳上报并出现在 `/healthz`，用于发现"两环境配置是否一致"与节点身份冲突（`02` §2.4） |
| 隐式发现 | 框架自动加载固定文件名（`.env`、compose 的 `./.env`）的行为。新架构里一律改为显式指定，让"读错文件"从静默变成启动失败（`02` §2.4） |
| 部署窗口 | 由执行部署的一方声明的**计划内重启**窗口：窗口内不计故障、不触发接管与自动回滚，该节点的引流自动改投并自动恢复，TTL 到期即恢复正常判定（`02` §5.0） |
| 接管（failover） | 默认节点故障后，全量流量自动交给另一个 `ready` 节点代管；期间按拒绝清单过滤不可逆动作，默认节点恢复稳定 60s 后自动回切（`01` §5.4） |
| 带外（out-of-band） | **离开出故障的那个组件**的通路：告警的 L2 / L3（NapCat 旁路、邮件）、发布网关与中控时的宿主机执行器（`01` §8.2、`02` §5.6）。原定义"离开 QQ（只剩邮件）"已随决策 17 废弃 |
| 告警出口 / 降级链 | 告警往哪发：L1 正常通道（经网关与上行链路）→ L2 NapCat HTTP 旁路 → L3 邮件，判据是**回执**而不是"请求已发出"；规定"只要还能发 QQ 消息就不用邮件"（`01` §8.2） |
