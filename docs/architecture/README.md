# 谛听架构重构设计（P0 设计定稿）

本目录是「网关 + 中控 + 双节点灰度」重构的**设计文档集**，不是实现说明。
实现按 `02-部署与运维.md` 的 P1~P4 批次推进，每批单独出方案。

---

## 要解决的问题

| 需求 | 现状 |
|---|---|
| 常驻 dev / prod 双节点，**共用一套业务数据库** | 已是两份 clone 双节点，但共享的只有数据库实例，逻辑上仍靠 `env_tag` 隔离 |
| 上新功能时用命令 / WebUI 切到 dev 节点 | 靠 `COMMAND_START=["dev-"]` 前缀隔离，只能隔离命令，切不了流量 |
| 测出错能方便切回 prod | 手工改配置 + 重启，无路由概念 |
| 节点异常自动回滚 | `docs/diting-deploy.md` 明确列为已知限制：**无自动回滚** |
| 群规则优先级高于插件规则 | 不存在灰度规则模型 |
| **按插件做细颗粒度灰度** | 不存在插件清单（manifest）概念，网关无从知道"这条消息属于哪个插件" |
| 仅命中灰度规则的流量切回 prod | 不存在 override 概念，只能整体切 |

## 设计结论（一句话）

**把「发布」和「引流」彻底解耦**：代码部署到哪个节点 ≠ 谁处理这条消息。
路由决策集中在一个不随节点生死的常驻入口（网关 + 中控），节点降级为可随时重启、可随意增删的无状态业务执行体。
于是「上新功能 → 测 → 回滚」变成改一条路由规则，而不是改配置重启服务。

**两条贯穿全局的取向**（详见 `00-总览.md` §6 决策 10 / 11）：

- **插件清单由内省导出，不做框架式 SDK**：节点遍历 NoneBot 注册表自动生成 manifest，插件**不改写法**即可被路由与灰度；声明只用于补内省看不到的语义；横切能力走全局中间件。
- **调度取混合形态**：排程元数据在中控（可审计、WebUI 可改），**触发与执行在节点**（Redis 租约防双跑），中控挂掉不影响定时任务发生。

## 核对状态与可信度边界

`00`~`04` 的全部结论经过一次独立复核（四组并行，约 80 条引证逐条对到源码，关键结论二次实测）。**下面这些可以直接引用，不必再验**：

| 已确认的结论 | 核对方式 |
|---|---|
| 群级缓存失效是死代码（`clear_pattern("perm::{gid}:")` 匹配不到 `perm:{uid}:{gid}:{key}`） | 实测子串匹配为 False |
| `.env.dev` 与 `.env.prod` 差 6 键，其中 5 个是死键且只在 prod | 完全正确。注意其中 3 个写成 `KEY = value`（等号带空格），用严格正则统计会漏——这本身就是"无 schema、靠 `os.getenv` 散读"的实证 |
| 38 个插件；12 个注册定时任务；8 个插件 13 处 `get_bound_group_ids` | 逐项精确匹配 |
| 内省覆盖 ~97%（74 个 message 类 matcher，仅 2 个 opaque） | 实测 `on_command` 67 + `on_regex` 5 + `on_message` 2 = 74，与 manifest 示例的 `74/72` 一致 |
| 适配器无 `message_sent`；`Event` 是 `extra="allow"`；`lifecycle/connect` 之前的事件被静默丢弃 | 全部确认——`01 §9` 的可行性论证建立在这三条上 |
| meta 事件在 NoneBot v11 中无任何消费方 | 确认（v12 才有 status update 机制） |
| 48 个注册权限点中 8 个从未被校验；4 处手搓 provisioning | 确认 |
| 容器无 `restart` / 无 `logging` 段 / 硬编码 Redis 口令 / `Dockerfile` 为 `COPY . .` 且 `.dockerignore` 未排除 `.env*` / `logs/nonebot.log:3` 明文转储密钥 | 全部确认 |
| 无迁移工具（`create_all` 引导）；`src/api/groups.py` 的群活跃度聚合无 `post_type` 过滤 | 确认 |

**另外两条对设计有利的事实**：38 个插件里 **37 个已有 `__plugin_meta__`**（只有 `image_collection` 没有），`extra["diting"]` 有现成落点；内省真正依赖的规则类都在公开模块 `nonebot/rule.py`，比 `03 §3.4` 的风险描述更稳。

**以下四方面没有覆盖**——不要把 `00`~`04` 里相关的表述当成已验证的结论：

- 未运行系统、未连数据库：`messages_event_logs` 的"46 万行"转引自 `docs/webui-upgrade-deploy.md:143`，未独立验证。
- 未验证 NapCat 侧行为（多路 `websocketClients`、`reportSelfMessage`、HTTP 控制口的端点与鉴权方式）——这些正是 `00 §8` 影子期要验的。
- 未验证 forward-WS 与 reverse 路由并存、`echo` 重写、缓冲与丢弃等运行时语义——属 `00 §8` 与 `02 §12` 的范围。
- 未评估性能与容量结论（`02 §10` 的 1000 事件/秒、250 并发 API），属压测范围。

## 十七个关键决策（详见 00-总览 §6）

1. **网关代理 OneBot**，而不是两个节点各自直连 NapCat。
2. **简单回滚**：回滚 = 流量回 prod，不保证新功能仍可用（不做特性开关）。
3. **取消 env_tag**，灰度期间写的就是真实数据。
4. **管理面全部迁到中控**，节点只留业务与内部接口。
5. **节点以 forward-WS 主动连网关**，NapCat 侧只改一个 URL。
6. **控制命令由网关本地执行**，节点全挂也能切回 prod。
7. **单仓多服务**：一个仓库、硬目录边界、每服务独立镜像；拆仓触发条件与拆法见 00-总览 §6 决策 7。
8. **全栈 Python**：网关/中控/节点同一语言，规则引擎与分类器只保留一份实现；性能工作放在"把阻塞移出事件循环"上。
9. **权限系统保留模型、重写求值与管理面**：白名单并入管理员，缓存改节点内存快照 + 版本号，补审计与护栏；入口签名不变，38 个插件零改动。
10. **插件清单由内省导出，不做框架式 SDK**：manifest 从 NoneBot 注册表生成（不漂移），`extra` 只补语义，横切能力走全局中间件——插件不改写法就能被灰度。
11. **调度取混合形态**：排程元数据在中控、触发与执行在节点、Redis 租约防双跑；废弃"用 env 开关错开调度"的旧做法。
12. **网关的连接与投递语义**：吸收 meta 事件、按节点连接合成 `lifecycle/connect`（仅上游可用时）、上游断链则断开节点连接（带去抖）、事件缓冲为主丢弃兜底；`echo` 必须重写（两个节点的计数器都从 1 开始，`01` §9.6）。
13. **事件流水由网关采集、中控落库**：新增 `event_logs`，覆盖除心跳外的全部上报事件（含机器人自己发的消息，即"只记录、不路由"的 `message_sent`）；`logging_info` 插件废弃，`messages_event_logs` 冻结为历史档案（`01` §8.5）。
14. **配置分层**：编排进 git、启动与密钥进"每环境一份源 + 每服务投影"的 env、业务配置与插件参数进中控库；判定规则是"要重启 → env，不要 → 中控库"，服务只拿到自己那份键（网关不持有业务库凭证，`02` §2.0）。
15. **默认节点故障取自动全量接管**：prod 链路断开 >10s 或 `unhealthy`/`not_ready` 即自动把全量流量交给 dev（不要人工确认），用 `canary_deny_plugins` 的运行期过滤保证不可逆动作不被未验证代码执行（两个执行点：网关拦命令类、节点侧 `failover_guard` 拦被动 matcher——后者是必需的，`01` §5.4）；回切自动 + 单向粘滞，计划内重启（部署窗口）不触发（`01` §5.4、`02` §5.0）。
16. **发布通道的边界与跨版本契约**：节点由中控编排（`/env deploy`），网关与中控自身**必须带外**（宿主机执行器 + systemd）；协议只允许向后兼容的变更，必须成对变更时网关只能在灰度窗口外发；顺序取中控 → 网关 → 节点（`02` §5.6/§9.1、`01` §9.10）。
17. **监管与告警**：分级（`critical` / `warning` / `info`）+ 出口降级链（L1 正常通道 → L2 NapCat 旁路 → L3 邮件，按回执判降级）+ 生产者下沉（网关管链路、中控管语义、watchdog 管进程，节点不持有出口凭证）；规定"**只要还能发 QQ 消息就不用邮件**"，告警目标只由 `ctl_settings` 给（`01` §8.2、`02` §2.5、`00` §6 决策 17）。
